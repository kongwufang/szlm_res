# ③ 服务端看哪些字段

> 👈 回到 [主线](../mainline.md) ｜ 上一节 [② body 怎么解](02-body怎么解.md) ｜ 下一节 [④ 怎么认出设备](04-怎么认出设备.md)

---

## 方法

拿一份**真实抓到**的 body，**每次只改一个字段**，其余保持原样，看响应变化。

**两个前提必须满足，否则结论不成立：**

```
① 编解码自校验通过：encode(decode(raw)) == raw   （逐字节）
② 一次只改一个变量
```

约 100 次变体实验。

---

## 结论：只有 6 个字段必须正确

```
【必需】
  URL.v      与端点匹配
  body.DUv   精确 == "com.coolapk.market"（大小写敏感，末尾空格会被 trim）
  body.3mS   小写 "v" + 版本 ≥ 9.x
  body.2cO   "秒.纳秒"，纳秒非零；±24h 时间窗
  body.AAA   "v1.0"
  body.75c   apiKey（可省略；给了就必须精确匹配）

【完全不参与识别】
  其余 73 个 body 字段
  URL 的 p / r / n / l / h / t
  全部 HTTP 头
```

## 各项细节

### `URL.v` —— 唯一被校验的 URL 参数

```
原样          → 200 真 DUID
v=0           → 400 被拒
p/r/n/l/h/t   → 各 6~8 种变体全部通过
```

### `DUv` —— 包名，精确匹配

```
"com.coolapk.market"      → 真 DUID
改成别的包名               → n_a 立刻变成 36 个 0
大小写变化 / 末尾空格       → 失败（空格会被 trim）
```

**这是服务端判定"这是哪个应用"的依据。**

### `3mS` —— SDK 版本

```
"v9.0.1"   → 通过
"v8.0.1"   → 失败（版本太低）
"V9.0.1"   → 失败（必须小写 v）
"9.0.1"    → 失败（必须带 v 前缀）
```

### `2cO` —— 时间戳，格式严格

```
"1791105420.764024281"   → 通过
"1790969185.0"           → 失败（纳秒为 0）
"1790969185"             → 失败（纯整数秒）
±24h 内的其它纳秒值       → 失败（★ 见下）
```

> ⚠️ **曾经误解**：因为"换了子秒就失败"，早期把它判为"固定的设备键"。
> 实际它是**那一次注册**产生的值，服务端为每次注册都记了一条映射。
> 详见 [已推翻的结论](99-已推翻的结论.md#4-2co-的子秒是固定设备键)。

### `AAA` —— 协议版本

```
"v1.0" → 通过
```

### `75c` —— apiKey

```
省略 / 空 / null        → 通过
精确等于 apiKey         → 通过
给了但值不对            → 失败
```

apiKey 是一个硬编码常量：

```
11e7b222083a4b732b4b14811f6fc05995a01415eb
```

> ⚠️ **曾经误解**：它跨端点、跨时间取值相同，被当成"设备级主键"。
> 实际上"跨设备也相同"恰恰说明它是常量。
> 详见 [已推翻的结论](99-已推翻的结论.md#5-75c-是设备级主键)。

## 类型敏感：用数字替代字符串会 400

```
字段原本是字符串 "abc"，改成数字 123  → HTTP 400
```

**服务端会解析 JSON 类型。** 做变体实验时要注意这点 ——
用"哨兵串"（如 `ZZSENTINEL`）替换字符串字段，可能因为**格式不符**而不是**语义不符**导致失败，
从而误判为"这个字段是必需的"。

**正确做法：用「同类型的另一个合法值」替换。**

```python
# ✓ 好
v["sfOo"] = "ABCDEF1"              # 仍然是 7 位 hex
v["2cO"]  = "1790969200.123456789"  # 仍然是 秒.纳秒

# ✗ 差（类型/格式不符，失败原因不明确）
v["sfOo"] = "ZZSENTINEL"
v["2cO"]  = 424242
```

## 整类随机化：验证"真的不重要"

单字段扫描只能证明"单独改它没用"，**证明不了"多字段组合也没用"**。

所以补做了**整类随机化**实验：

```
5 个哈希（K5f/ne8/w91/gEd/6yY）整类随机化       → 仍返回真 DUID
15 个混淆串整类随机化                            → 仍返回真 DUID
4 个嵌套对象（iYB/7S2/G8U/msg）整类清空          → 仍返回真 DUID
设备属性（AYk/P1J MAC、R3d 机型、R37 厂商、wSK 内网IP、YWu hosts）整类随机化 → 仍返回真 DUID
时间戳（Qg1/LMi/za7）整类随机化                  → 仍返回真 DUID
```

**更强的验证** —— 只保留 6 个锚点字段，其余 72 个**全部随机化**：

```
只留 DUv + 3mS + 2cO + sfOo + foO + 75c，其余全随机
  → ★★★ 仍然返回真 DUID
```

**⇒ 整个 79 字段的 body，只有 6 个有意义。**

---

## 三种失败形态要分清

```
n_a = 真 DUID      成功
n_a = "0" × 36     值被判据否掉（进了业务逻辑，但字段不自洽）
n_a = ""           结构不合法（没进业务逻辑）
```

**做实验时务必区分**：改坏了必需字段会得到 `"0"×36`，
而 body 结构错误（比如字段类型不对）会得到空串。
