## 一句话结论

```
libdu 的字段"编码" = 由本次上报时间 2cO 决定参数的「mod-95 偏移 + 重排」

  P       = 2cO 最后 3 个字符去掉 '.' 后 atoi
  K       = P % 100 % 57 + 1               在 0x20..0x7E 内循环右移
  variant = P // 100 % 4                   四种重排之一

  编码 = shuffle(shift(value, K), variant)
  解码 = shift(unshuffle(value, variant), -K)
```

**完全可逆。** 服务器去掉 TLS 和固定密钥 XOR 之后，拿到的就是原始值。

## `P` 从哪里来

```
2cO = clock_gettime(CLOCK_REALTIME) 按 "%ld.%ld" 格式化，纳秒部分不补零
P   = 2cO 最后 3 个字符，去掉 '.'，atoi
```

**★ 关键特性：**

```
· P 在每次 query 开始时重置
  ⇒ 同一次查询的所有上报、所有字段共用同一个 P
· 真机上纳秒末三位基本随机
  ⇒ 每次上报的编码参数都不同
· 纳秒不足 3 位时会带上 '.' 和秒的个位
  例：…7  取 "4.7" → P=47
      …1（秒末位 0）→ P=1
```

**举例：**

| `2cO` | 末 3 字符 | P | K | variant |
|---|---|---|---|---|
| `1791105420.764024281` | `281` | 281 | **25** | **2** |
| `1791108030.968315068` | `068` | 68 | **12** | **0** |
| `1793367275.234000000` | `000` | 0 | **1** | **0** |

**⇒ 最后一行解释了为什么「裸 −1 偏移」曾经能用：那是 `P=0` 的特例。**

## 四种重排

`variant = P // 100 % 4`，n 为长度，m = n // 2：

```python
def shuffle(s, v):
    n, m = len(s), len(s) // 2
    if v == 0:
        # ① 奇数长度先放中间字符，再依次放 s[n-1-i]、s[m-1-i]
        return (s[m] if n % 2 else "") + "".join(
            s[n-1-i] + s[m-1-i] for i in range(m))
    if v == 1:
        # ② 依次放 s[n-1-i]、s[i]，中间字符最后
        return "".join(s[n-1-i] + s[i] for i in range(m)) + (s[m] if n % 2 else "")
    if v == 2:
        # ③ 从末尾起隔一个取一个，再从倒数第二个起隔一个取一个
        return s[n-1::-2] + s[n-2::-2]
    # ④ 先取偶数位，再取奇数位
    return s[0::2] + s[1::2]
```

**取逆：**

```python
def unshuffle(e, v):
    n = len(e)
    idx = shuffle("".join(chr(0x100 + i) for i in range(n)), v)
    out = [""] * n
    for pos, c in enumerate(idx):
        out[ord(c) - 0x100] = e[pos]
    return "".join(out)
```

## 偏移（mod 95）

```python
LO, HI = 0x20, 0x7E
MOD = HI - LO + 1            # 95

def shift(s, k):
    return "".join(chr((ord(c) - LO + k) % MOD + LO) for c in s)
```

**必须用 `mod 95`，不能用裸 ASCII 偏移** —— 字符落到 0x20 以下时会出界。

## mode 10：`foO` 那种少一位的

```
去掉第 (n-1-P%10) 个字符（长度 ≤ 9 时去掉最后一个）
再按 mode 2 编码
另在 "s"+键名 下放校验值：MD5_UPPER(str(全部字符码位之和 + P%100//10))[:7]
```

**恢复被去掉的那一位**：只有 16 个 hex 候选，逐个算校验值，只有一个对得上。

## 怎么发现的

### 第一步：从 [People-11](https://github.com/People-11) 的观察出发

他早期的分析指出：字段编码是「字符码位 +1 然后重排」，并给出了可用的解码函数。

**在他的样本上完全正确。** 我复现过：

```
foO = '4ege81284bfbcc8'  →  '7be317f3baa70dd'
补 16 个 hex 候选，只有 'b' 让校验值等于 sfOo '3BF55BB'
⇒ ANDROID_ID = 7be317f3baa70ddb   ★ 命中
```

### 第二步：换到我们的数据上，失效了

| 来源 | `foO` 用 −1 解码 |
|---|---|
| 他的样本 | `7be317f3baa70dd` ✅ 纯 hex |
| 我们的 D1H | `P}}NP{{Q\|HIJyPO` ❌ 含 `{}` |

**⇒ `chr(ord(c) - 1)` 对不上。**

### 第三步：发现偏移量不是 1

穷举偏移，得到 −12、−25 这样的值，不是 −1。

### 第四步：找到 mod-95

`D1C` 解出的 UUID 里有个空格，说明偏移在某处「回绕」了。

改成 `chr(((ord(c) - 0x20 - K) % 95) + 0x20)` 后，`K=25` 立刻得到完整正确的 UUID。

### 第五步：`K` 到底怎么来的 —— 由他解出

我只能穷举出 `K` 的值，说不清它从哪来。**是他找到了答案：**

```
K = (2cO 末 3 位 atoi) % 100 % 57 + 1
variant = (P // 100) % 4
```

**⇒ 偏移量就藏在同一份报文自己的时间字段里。**

### 第六步：四种重排，不是一种

我之前只发现了 `variant 0` 和它的逆，把另外三种误当成「不同的偏移方向」。

**他区分出了四种**，并明确它们由 `(P // 100) % 4` 选择。

**⇒ 这就是为什么我解 D1C 要「反着」、解 D1H 要「正着」——** 那其实是 `variant 2` 和 `variant 0`。

## 一个尚未解释的矛盾（我这台设备）

两份报文算出的 `ANDROID_ID` **不同**：

```
D1C (P=281)  →  288daec08ec17693
D1H (P=68)   →  288daec8ec176390
```

**同一台设备不该有两个 `ANDROID_ID`。**

### 用 `P1J` 反查的结果

按公开分析，`P1J` = `SHA1_UPPER(ANDROID_ID)` 取 `[1:7]:[13:19]:[7:13]`。

**在他的样本上验证成立：**

```
AID = 7be317f3baa70ddb
SHA1 = 2B191B533291E36B16A46E4A22C277C3ABC0C0BE
[1:7]:[13:19]:[7:13] = B191B5:36B16A:33291E
                      ↑ 与他 payload 里的 P1J 完全一致 ✓
```

**在我这里对不上：**

```
我的 P1J = 13A365:CCAF40:AD4AA9
⇒ 要求 SHA1_UPPER(AID) 形如 ?13A365AD4AA9CCAF40…
⇒ 我解出的两个候选都不满足
```

**我的怀疑**：D1 是一台廉价安卓手表（`TK Watch`，Android 8.1），
`ANDROID_ID` 可能不是标准 16 位 hex，所以「16 个 hex 候选补末位」这个套路对它不适用。

**⇒ 这条待后续用标准手机验证。**

## 各字段的真实含义

| 字段 | 含义 | 模式 |
|---|---|---|
| `foO` | ANDROID_ID 前 15 位 | 10 |
| `sfOo` | 上面那 16 位的校验值 | raw |
| `dLH` | 每次安装生成的随机 UUID（`boot_uuid`） | 2 |
| `mIS` | `/proc/sys/kernel/random/boot_id`（**每次开机变**） | 2 |
| `2cO` | 本次上报时间 —— **同时决定整份报文的编码参数** | raw |
| `ne8` | `libdu.so` 自身的 MD5 | raw |
| `w91` | `/system/fonts` 文件名列表的 MD5 | raw |
| `gEd` | `libreference-ril.so` 或 `libc.so` 的 MD5 | raw |
| `6yY` | Widevine `deviceUniqueId`（hex） | raw |
| `P1J` / `AYk` | `SHA1_UPPER(ANDROID_ID)` 取片段（**伪 MAC**）；有 `o_a` 后 `P1J` 改为 `o_a` | raw |
| `K5f` | `MD5(上报时间串 + pid + rand() + tid)` | raw |
| `UOv` | `CLOCK_REALTIME − CLOCK_BOOTTIME`（开机时刻） | 2 |
| `52J` | 10 个路径的 `inode:dev` | 2 |
| `YWu` | **hosts 文件内容** | raw |
| `iYB.Zne` | 当前网络的全部 IP | 2 |

**⇒ 这解释了我原来做的 73080 次组合穷举为什么零命中：**
`w91` / `gEd` 的输入不是报文里的字段，而是**文件系统里的内容**。

## `OW2` = 运行时快照

解开后的内容（多份）：

```
com.coolapk.market,com.coolapk.market:xg_vip_service,sh,ps,grep,10406
```

**⇒ SDK 上报了：宿主包名、一个已启用的服务（`xg_vip_service`）、
以及 `sh` / `ps` / `grep` 三个进程名和一个数字（疑似 PID 或端口）。**

其它几份是同样元素的**倒序**，说明不同报文的 `variant` 不同。
