> **本文档解决了我原来的「未解问题 #1 和 #2」。**

---

## 一句话结论

```
libdu 的字段"编码" = mod-95 环上的偏移 + shuffle 重排

  编码: e[i] = chr(((ord(p[i]) - 0x20 + K) % 95) + 0x20)   然后整体重排
  解码: 先反重排，再 chr(((ord(e[i]) - 0x20 - K) % 95) + 0x20)

  ★ 95 = 可打印 ASCII 的字符数（0x20..0x7E）
  ★ K 每份报文都不同，实测范围 5..56，需自动定位
```

**完全可逆。** 服务器去掉 TLS 和固定密钥 XOR 之后，拿到的就是原始值。

## 怎么发现的

### 第一步：从 **People-11** 的观察出发

**People-11** 公开了他的分析，指出字段编码是「字符码位 +1 然后重排」，
并给出了一个可用的解码函数：

```python
def unenc(e):
    # 反重排
    n, m = len(e), len(e) // 2
    s, k = [''] * n, 0
    if n % 2:
        s[m] = e[0]; k = 1
    for i in range(m):
        s[n - 1 - i] = e[k]
        s[m - 1 - i] = e[k + 1]
        k += 2
    # 再减 1
    return ''.join(chr(ord(c) - 1) for c in s)
```

**在他自己的样本上完全正确。** 复现：

```
foO = '4ege81284bfbcc8'  →  '7be317f3baa70dd'
补 16 个 hex 候选，只有 'b' 让校验值等于 sfOo '3BF55BB'
⇒ ANDROID_ID = 7be317f3baa70ddb   ★ 命中
```

### 第二步：换到我们的数据上，失效了

拿我们自己抓的报文跑同一个函数：

| 来源 | 版本 | `foO` 解码结果 |
|---|---|---|
| 他的样本 | 16.6.4 | `7be317f3baa70dd` ✅ 纯 hex |
| 我们的 D1H | 16.6.2 | `P}}NP{{Q\|HIJyPO` ❌ 含 `{}` |

**⇒ `chr(ord(c) - 1)` 对不上。**

### 第三步：发现偏移量不是 1

穷举偏移（`chr(ord(c) + delta)`，delta ∈ −128..128），出现了意外结果：

```
D1H  foO 'DEo?qBmCp=DoDq>'  delta=-12 → '288daec8ec17639'   ★ 校验命中
D1C  dLH ' NNzM~FRQKLFP{K|…' delta=-25 → 得到合法 UUID（但个别字符不对）
```

**⇒ 偏移量是 −12、−25 这样的值，不是 −1。**

### 第四步：找到真正的规则

`D1C` 解出的 UUID 里有个空格（`bc6 6c72-…`），本以为差一位：

```
'bc6 6c72'  →  那个空格本该是 hex 字符
```

**⇒ 说明偏移在某个位置「回绕」了。**

试 `mod 95`：

```python
plain = chr(((ord(enc) - 0x20 - K) % 95) + 0x20)
```

**⇒ `D1C` 用 `K=25` 立刻得到完整正确的 UUID：**

```
bc6f6c72-b27a-4322-8893-5e649a35651f
```

**⇒ 不是裸 ASCII 偏移，是在 95 个可打印字符组成的环上做偏移。**

### 第五步：验证 K 是逐报文变化的

把同一套规则套到 `OW2` 字段（一个明显的文本字段）上，17 份全部解开，
但每份的 `K` 都不同：

```
K= 5 : 2 次     K=16 : 1 次     K=25 : 3 次     K=33 : 2 次
K=10 : 1 次     K=17 : 1 次     K=28 : 1 次     K=35 : 1 次
K=12 : 3 次     K=20 : 1 次     K=29 : 2 次     K=38 : 1 次
K=22 : 1 次     K=30 : 1 次     K=56 : 1 次
```

**⇒ 这就是为什么写死 `-1` 只能对特定样本有效。**

## 完整算法

### 重排（shuffle）

```python
def shuffle(s):
    """编码时用：奇数长度先取中间字符，之后交替取首尾"""
    n = len(s)
    m = n // 2
    out = [s[m]] if n % 2 else []
    for i in range(m):
        out += [s[n - 1 - i], s[m - 1 - i]]
    return "".join(out)


def unshuffle(e):
    """解码时用：shuffle 的逆"""
    n = len(e)
    m = n // 2
    s = [""] * n
    k = 0
    if n % 2:
        s[m] = e[0]
        k = 1
    for i in range(m):
        s[n - 1 - i] = e[k]
        s[m - 1 - i] = e[k + 1]
        k += 2
    return "".join(s)
```

例（长度 4）：

```
原文  a b c d
shuffle → d b c a
```

### 偏移（mod 95）

```python
LO, HI = 0x20, 0x7E          # 可打印 ASCII 范围
MOD = HI - LO + 1            # 95

def enc(plain, K):
    s = "".join(chr(((ord(c) - LO + K) % MOD) + LO) for c in plain)
    return shuffle(s)

def dec(cipher, K):
    s = unshuffle(cipher)
    out = []
    for c in cipher_unshuffled:
        out.append(chr(((ord(c) - LO - K) % MOD) + LO))
    return "".join(out)
```

**验证**（`K=25`，`D1C` 的 `dLH`）：

```
' NNzM~FRQKLFP{K| |JOLRONLQFKMzKFPOO{'
  → unshuffle  → '{OFzKQNRO||{FKR~zNOPKMFLOLJ KPLQFMN '
  → mod95 -25  → 'bc6f6c72-b27a-4322-8893-5e649a35651f'   ✓ 合法 UUID
```

### 自动定位 K

`K` 未知，但每个字段都有**已知格式**可以校验，于是穷举 0..94 取通过的那个：

```python
def find_K(field_value, validator):
    for reorder in (unshuffle, shuffle):        # 两个方向都试
        for K in range(95):
            r = dec(field_value, K)
            if validator(r):
                return reorder, K, r
    return None
```

**各字段的校验器：**

| 字段 | 校验条件 |
|---|---|
| `dLH` | 合法 UUID（`8-4-4-4-12`，32 位全 hex） |
| `foO` | 解码后 15 位全 hex，且补出的第 16 位让校验值等于 `sfOo` |
| `OW2` | 解出的字符基本落在 `[a-z0-9.:,_-]` |
| `iYB.Zne` | 全是点分 IP 的字符集 |
| `UOv` | 形如 `秒.纳秒` |

**⇒ 一旦用某个字段定出 `K`，同一份报文里所有 mode 2/3/10 字段共用它。**

---

## `sfOo` 是校验值，不是标识

这是最容易误解的一点。

```
foO  = ANDROID_ID 前 15 位的编码（mode 10）
sfOo = MD5_UPPER(str(全部 16 位码位之和))[:7]
```

**为什么能确定第 16 位？** 因为只有 16 个 hex 候选，逐个算校验值，只有一个对得上：

```
候选            校验值
7be317f3baa70dd0  B571ECE
7be317f3baa70dd1  144A3F7
…
7be317f3baa70ddb  3BF55BB   ★ 等于 sfOo
```

**⇒ 7 位大写 hex = 28 bit，随机碰撞概率约 6×10⁻⁸，足够可靠。**

|---|---|---|---|
| `dJs` | `150100525831424d42…c400` | 同 | **eMMC CID，硬件不变** |
| `p1m` | `0x51004057` | 同 | **eMMC 序列号** |

| `Bos` | `1735690118.109999897,…` | 同 | **旧目录时间戳** |
| `IJK` | `…,1791108075.51…` | `…,1791105484.35…` | 第二段是**本次注册时间** |
| `dLH` | `c009c04e-…-0345988b` | `bc6f6c72-…-35651f` | **每次安装重生成** |

**⇒ 这也反证了解码是正确的**：如果 K 选错，不可能有 6 个字段同时对齐。

### `OW2` = 运行时快照

解开后的内容（多份）：

```
com.coolapk.market,com.coolapk.market:xg_vip_service,sh,ps,grep,10406
```

**⇒ SDK 上报了：宿主包名、一个已启用的服务（`xg_vip_service`）、
以及 `sh` / `ps` / `grep` 三个进程名和一个数字（疑似 PID 或端口）。**

**⇒ 也就是说，它连「设备上有什么进程在跑」都上报。**

其它几份是同样元素的**倒序**（`ecivres_piv_gx` = `xg_vip_service` 反写），
说明有些报文的重排方向是反的 —— 所以自动定位时两个方向都要试。

## 各字段的真实含义

破解编码后，结合公开分析，几个关键字段的语义已经明确：

| 字段 | 含义 | 编码 |
|---|---|---|
| `foO` | ANDROID_ID 前 15 位 | 10 |
| `sfOo` | 上面那 15 位的校验值 | raw |
| `dLH` | 每次安装生成的随机 UUID（`boot_uuid`） | 2 |
| `mIS` | `/proc/sys/kernel/random/boot_id`（**每次开机变**） | 2 |
| `2cO` | 本次上报时间 | raw |
| `ne8` | `libdu.so` 自身的 MD5 | raw |
| `w91` | `/system/fonts` 文件名列表的 MD5 | raw |
| `gEd` | `libreference-ril.so` 或 `libc.so` 的 MD5 | raw |
| `6yY` | Widevine `deviceUniqueId`（hex） | raw |
| `P1J` / `AYk` | `SHA1_UPPER(ANDROID_ID)` 取片段（**伪 MAC**）；有 `o_a` 后 `P1J` 改为 `o_a` | raw |
| `K5f` | `MD5(上报时间串 + pid + rand() + tid)` | raw |
| `UOv` | `CLOCK_REALTIME − CLOCK_BOOTTIME`（开机时刻） | 2 |
| `52J` | 10 个路径的 `inode:dev` | 2 |
| `YWu` | **hosts 文件内容** | raw |
| `iYB.Zne` | 当前网络的全部 IP | 2 |

**⇒ 这解释了我原来做的 73080 次组合穷举为什么零命中：**
`w91` / `gEd` 的输入不是报文里的字段，而是**文件系统里的内容**。

## 与「裸偏移」方案的差异

| | 裸偏移方案 | 本文的完整解法 |
|---|---|---|
| 公式 | `chr(ord(c) − 1)` | `chr(((ord(c) − 0x20 − K) % 95) + 0x20)` |
| 偏移来源 | 写死 | 自动定位 |
| 适用范围 | 只在特定样本上成立 | 全部样本 |

**⇒ 裸偏移是 `mod 95` 在「不发生回绕」时的特例。**

**⇒ 当字符偏移后落到 0x20 以下时，两者开始分歧 —— 这就是换一份报文就失效的原因。**
