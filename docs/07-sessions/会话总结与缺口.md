## 一、这一轮确立的结论（有实测背书）

### 1.1 客户端侧：算法全解出

| 项 | 值 | 证据 |
|---|---|---|
| `p` | `MD5(包名 + "." + "37be8a1ee106979a").upper()` | 池模板 `0x102b20` + 逐字符 |
| `h` | `MD5(DUID + "." + "889e0b01").upper()`，首次为 `"0"` | **三条独立证据**（池模板 `0x0feb2c` / 运行时 MD5 输入 / 离线试算） |
| `r` | 32 位小写 hex，每次随机 | 5 样本 |
| URL | `%s%s&p=%s&r=%s&n=%d&l=%d&h=%s`（池 `0x105374`） | 静态 + 逐字段 |
| body | `zlib.compress(JSON) XOR 池常量`（周期 46/53/45/46/48） | **4/4 双向自证** |
| JSON 序列化 | 紧凑 + `/` → `\/` | 4/4 逐字节 |
| 响应 | 同一池常量 XOR → JSON | 3 个端点解出 |

**四条字符串在池里紧邻**（`slot_strings.txt:2566-2569`）：

```
0x15c728  v9.0.1
0x15c730  37be8a1ee106979a        ← p 的盐
0x15c738  %s.889e0b01             ← h 的模板
0x15c740  %s%s&p=%s&r=%s&n=%d&l=%d&h=%s
```

### 1.2 两台设备对照

| | D1 `TK_Watch`（Android 8.1） | D2 `XTQ_Watch`（Android 9） |
|---|---|---|
| DUID | `DUaVFlbAMrmH2Z57PEhm_N9EO4RoUdvNstg5` | `DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9` |
| `h` | `CA0D929678DB1B51E3B5F2FBFA582002`（公式） | `F7AAD8CD5824603F7F2200731D8C045D`（实抓） |
| `p` | `F9BD0FBDACFE80FCF34370FBCFEE1A98` | **相同** |
| `device_label` | `6KYDnLSlcZQV83Yq2P63w==` | **相同** |

⇒ `h` 绑设备、`p` 与 `device_label` 只绑「包名（+签名）」。

### 1.3 ★ 服务端判据：87 个字段只用到 5 个

```
URL:   只有 v 被校验（v=0 → 400）；p/h/r/n/l/t 全不解析
body:  结构必需 2 个：AAA、3mS
       值必需   3 个：DUv、BBB、2cO
       其余 73 个（含 75c）：删掉、改 1 字符都不影响
```

各字段的精确要求：

| 字段 | 要求 |
|---|---|
| `URL.v` | 与端点匹配 |
| `DUv` | 精确 == `com.coolapk.market`（大小写敏感 / 前缀不匹配 / 末尾空格被 trim） |
| `3mS` | 小写 `v` + 版本 ≥ 9.x（`v8.0.1`、`V9.0.1`、无 `v` 都失败） |
| `2cO` | `"秒.纳秒"` 且**纳秒非零**；±24h 时间窗（`"xxx.0"`、纯整数秒都被拒） |
| `75c` | **可删**（缺省/空/null 都通过）；给了就必须精确等于 apiKey |
| 任何字段 | 用数字替代字符串 → **HTTP 400**（服务端解析 JSON 类型） |

### 1.4 ★ `75c` = 数盟 apiKey（早先定为「未解出、决定性」）

```
dump/wire_m58_REQ_9 →  "75c":"11e7b222083a4b732b4b14811f6fc05995a01415eb"
ShuzilmProbe.kt:97  →  API_KEY = "11e7b222083a4b732b4b14811f6fc05995a01415eb"
```

42 字符逐字符相同 ⇒ 它是**常量**，不是「native 算出的设备级主键」。
「三端点取值相同」「跨 95 分钟相同」都自然成立。

### 1.5 三种「失败形态」是不同的东西

```
n_a = 真 DUID     成功
n_a = "0"*36      值被判据否掉
n_a = ""          结构不合法（服务端没进业务逻辑）
```

### 1.6 `ShuzilmSDKManager`（酷安侧封装层，此前从没看过）

```
com.coolapk.market.manager.ShuzilmSDKManager extends DelayInitSDK
11 字段 / 22 方法 / 13 嵌套类
```

- `initID$validIdOrNull`：客户端**自己会校验**缓存 ID，不合法就重取
- `initSDKAndID$1` 带 `$forceReloadID`：存在强制重载路径
- `onLoginEvent` / `onWifiEvent`：把登录/WiFi 变化转给数盟
- **没有密钥材料**（apiKey、包名声明都不在 Java 层）⇒ 在 native
- **`ހ()` 可运行时读 DUID**（不用 root、不用读 prefs）
- **`އ(boolean)` 调用后进程退出**（危险）

### 1.7 `didCode` —— SDK 上报的设备指纹结构（新发现）

```
{"x2":UUID, "x3":"samsung,SM-F731N", "x8":"wlan0,0,<IPv6>-<gw>-",
 "x12":"com.coolapk.market", "x13":"v8.9.7",
 "x7":"<MD5(UUID)>+<UUID>", "x11":"<MD5('0')>+'0'", ...}
```

- `x7` / `x11` 都满足 `MD5(内容)+内容` ✓ 两处验证通过 —— 这是该封装的**第四处独立印证**
- `x8` 里带**出口 IP 与网关**（客户端会主动上报网络位置）

## 二、这一轮排除掉的东西（全部有实测）

| 假设 | 实验 | 结果 |
|---|---|---|
| 服务端按出口 IP 认设备 | `ip_switch_probe.py`：走代理换出口重放 | ✗ 无关 |
| 服务端用设备指纹字段认设备 | 删掉 / 改 1 字符（MAC、机型、内网IP…） | ✗ 无关 |
| 服务端拿整份 body 内容当 key | 32 个字段各改 1 字符 | ✗ 无关 |
| URL 的 `p`/`h`/`r`/`n`/`l` | 逐项变（各 6~8 变体） | ✗ 全不校验 |
| 任何 HTTP 头 | 21 组变体（含最小头集、UA 换 curl） | ✗ 全无影响 |
| 请求侧存在签名 | 上述全部 | ✗ **不存在** |

**由此作废的三条旧表述**：

```
✗ 「服务端做 URL↔body 完整性绑定，改任一字节即 400」
✗ 「75c 是设备级主键，服务端用它索引 DUID」
✗ 「除 75c 外几乎都可伪造」（应为：必须对的只有 5 个字段）
```

## 三、★★ 新增缺口（本轮发现或加剧的）

### 缺口 1（最高优先）★ 核心矛盾：「逐设备唯一的 DUID」对不上「请求里没有设备标识」

> ⚠️ **本节后来被 `FIELD_TYPES_AND_MIS.md` 部分解答** ——
> 找到了 `mIS` 字段，**它的值就是设备标识种子**。
> 详见该文档 §三/§四；下面的原始描述保留作为背景。

```
三星 SM-F731N（跑 c001apk）-> DU1aXs5bbgJWPceuTiqkk7KwFezP72yRDrg7
我们的手表 XTQ_Watch       -> DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9

两台设备在 x12 都声明 com.coolapk.market，拿到不同 DUID
但已实测：请求里没有任何逐设备唯一的东西被服务端使用
```

**被排除的解释**：IP ✗ / 指纹字段 ✗ / body 内容 ✗ / URL 参数 ✗ / 请求头 ✗。

### ★★ 已找到的答案（2026-10-03 追加）

```
mIS 字段（原值 "W(W(\&&&T+\Z*)W&\QT*ZTX'Q\TQ*X')&&Q)"，长 36）：
  · 缺了它        -> n_a 全 0（功能必需）
  · 换成 dLH 的值 -> n_a = DUnkGC0m8phaJExl5EHNnMnt5YNydzbH_3g0（★ 另一个 DUID）
  · 连发 3 次      -> 完全相同（确定性）
  · 自造 36 字符串 -> 全 0（服务端只认它记录过的种子）

⇒ 【mIS 的值就是那个「逐设备唯一」的东西】
   真机发的是对应本机手表的值，所以服务端返回手表的 DUID；
   换成别的已知值，就返回别的设备的 DUID。
```

**之前为什么没测出来**（三种改法都指向「全 0」，被误读为「该字段无关」）：

```
改值      -> 变成未知种子 -> 全 0
用哨兵值  -> 未知种子     -> 全 0
单独删    -> 缺必需字段   -> 全 0
```

**剩下未解的**：
```
· mIS 的值怎么算出来的？（不在池里，常见编码规则都解不出 ⇒ 原生层不透明输出）
· 派生算法（MD5/SHA1/加盐 都试过，未命中）
· 换种子的敏感性是【精确查表】还是【模糊匹配】（已知改 1 字符就失败 ⇒ 偏查表）
```

**判定实验**：在 D1 上抓一次真机请求，它的 `mIS` 值应当与 D2 不同 ——
这一条能同时解答「缺口 1」与「D1 的实抓」。

### 缺口 2 ★ 必需字段的**类型**要求从未系统测过

```
已知：把某个字段的值用【数字】替代【字符串】→ HTTP 400（19 个字段一起改时触发）
未知：是哪些字段要求字符串？哪些允许数字？
      87 个字段的类型约束表完全没有
```

**为什么重要**：要构造一份能被接受的请求，必须知道每个字段的类型。
**成本**：低（逐字段改类型，约 90 次请求）。

### 缺口 3 ★ 「73 个字段服务端不读」的**适用范围有限**

```
本实验只测了：改了之后【本次响应】是否变化
没测的：    服务端是否【记录/存储】它们（供后续风控或下次响应使用）
```

这 73 个字段携带完整设备指纹（MAC/机型/应用列表/网络环境）。
`DUID_UNIVERSALITY_REPORT.md` 早就怀疑「真正的锚点是签名证书 + 已安装应用集合 +
网络出口的组合指纹」——本轮没能否定这一点，只是证明了**它们不影响本次响应**。

### 缺口 4 ★ 「+1 个字段就 400」的机制不明

```
minimal_body_probe 变体②：把 19 个字段改成字符串 -> HTTP 400
key_probe：逐个改 1 个字符（保持类型）-> 全部 200
```

⇒ 400 是**类型**问题，不是内容问题。但**哪些字段有类型约束**没测（= 缺口 2）。
另外：**多出来的字段**（不在 87 个里）会不会也被拒？未测。

### 缺口 5 ★ 三星设备那个矛盾（`v8.9.7` 能过，`v8.0.1` 被拒）

```
本轮实测：body.3mS = "v8.0.1"  ->  n_a 为空（被拒）
§六点一百六十 日志：三星设备 didCode.x13 = "v8.9.7"  ->  拿到了 DUID
```

「下界 ≥ 9.0.0」这个结论**只对回放场景成立**，对真机注册不成立（或下界其实是 8.x）。
**未解** —— 需要一个 `v8.x` 的真机抓包才能定。

### 缺口 6 `d2api` / `daa` 的 body 至今一个字节都没抓到

```
d2api  CL=4001  捕获 0  ★ 缺 4001
daa    CL=4218  捕获 0  ★ 缺 4218
```

原因：`SSL_write` 采样被截断（只拿到 383/381 字节的头部）。
⇒ 缺这两个端点的**池常量**、JSON 结构、字段表。

> **2026-10-03 追加**：管线已重写为「全量不截断 + 分块回传」，
> 并修掉了两个真 bug（漏挂 `libjavacrypto.so`；多进程消息 ID 撞车导致落盘覆盖）。
> 详见 `CAPTURE_PIPELINE.md`。
> **`mdna` 已能全量抓到（1413 字节）**，但 `d2api`/`daa` 仍未拿到 ——

> attach 式注入覆盖不住。**需要 spawn + gating，而 D2 上 spawn 不可用。**
> ⇒ 留给 D1（USB 时序可控）。

### 缺口 7 「服务端如何建立设备记录」这一环完全空白

## 五、这一轮的方法论沉淀（可迁移）

### 5.1 三次「结论无效」都是构造/观测的错，不是分析的错

```
① leaf 路径 vs 真实键名     —— 23 个用例全在新增字段，不是改写
② 浮点往返丢精度           —— float 重建时间戳，纳秒丢了 36 位
③ setTimeout 在 frida 不触发 —— 脚本装上了却一声不响，被误读为「没有该类」
```

已固化进脚本的两条断言（每个探针发请求前先跑）：

```
① encode(decode(原始body)) == 原始body      （编码可信）
② 目标键名真实存在于 body                    （改到了正确位置）
```

### 5.2 失败形态要分类，不能只看「成/败」

`n_a` 的三种形态（真值 / 全 0 / 空）对应三种完全不同的语义。
**前几轮只看「变没变」，所以漏掉了「结构必需字段」这一整类。**

### 5.3 挂钩位置要覆盖全部通道，且不截断

- 头（21 变体）+ URL 参数 + body 字段 + 全部发送家族（`sendto/send/sendmsg/write/writev/syscall`）
  + `SSL_write` —— 只有覆盖全了才敢说「不在这里」
- D2 上 `SSL_write` 抓到 QQ 请求 ⇒ 证明钩子有效；D1 上零命中 ⇒ 问题在时机不在钩子

### 5.4 反射比静态反编译更快（某些场景）

没有 jadx 的情况下，运行中的 `ShuzilmSDKManager` 用 frida 反射拿到
字段值、方法签名、嵌套类清单 —— 比 decompile APK 快得多，且拿到的是**运行时真值**
（例如 `ԭ = 127470393`、`ׯ = 1790989016261` 这些字段的实值）。
