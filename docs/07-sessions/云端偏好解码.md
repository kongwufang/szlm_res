## 三、这些发现对目标的意义

### 3.1 好消息：DUID 确实「就躺在设备上」

```
两处明文 XML：
  dna.xml                     <device_id>
  coolapk_preferences_v7.xml  <SHUZILM_DID>

⇒ 在【已 root】的设备上，「取回该设备的 DUID」= 读一个 XML，无算法、无网络
⇒ 你提出的方案（手机装了酷安 → 取回它申请的 ID）在 root 设备上完全可行
```

### 3.2 仍然没找到的：`mIS` 与 `2cO` 的种子

```
· 本轮把 prefs 全部 33 个云控键 + 3790 个键名都扫了一遍
· 没有出现 mIS 的值（"W(W(\\&&&T+…"）或 2cO 的纳秒（"997397935"）
· 结论：种子【不落盘】，只在内存/网络里
```

### 3.3 反射扫描的结果（另一个否定结论）

```
在 D2 上扫了 80 个候选类（cn.shuzilm.* + ShuzilmSDKManager 家族 + util 包）：
  无任何类的【Java 字段名】同时含 ≥3 个 body 字段名（DUv/3mS/2cO/mIS/AAA…）

⇒ body 的字段名不是 Java 字段名 —— 它们是
   ① 运行时构造的字符串（native 或反射拼装），或
   ② Map 的键（序列化时临时填）
⇒ 想拿 body，钩【序列化点】比扫类更实际
```

## 五、下一步的两条路（按性价比）

### 路 A：补上「未 root 设备」的取法（对接你的目标）

```
已 root  -> 直接读，已完成
未 root  -> 只能靠服务端，就需要提 mIS / 2cO 的种子
   · 种子的来源只有一个窗口：mdna 请求的 body
   · 钩【序列化点】而不是扫类：
       钩 zlib 的 deflate（在压缩前拦到明文 JSON）
       或钩 native 的 JSON 构造
```

### 路 B：把已有成果落地到 c001apk

```
已知：c001apk 只需在 prefs 里写对两个键
       dna.xml          <device_id>
       coolapk_preferences_v7.xml  <SHUZILM_DID>
     （若 SDK 会自己读，则只写 dna.xml 即可）
⇒ 在已 root 设备上，把酷安的这两处值搬过来即可对齐
```

## 六、教训

```
① 「数据在哪」比「怎么算」更值得先问。
   DUID 一直是明文，我却先追了好几轮网络上报。
② 云控落盘是「32hex 键 + base64 值」，解出来结构很规整：
   <32 hex><时间戳> / <MD5(内容)><内容> —— 后者已经第 5 次出现，
   说明这是数盟 SDK 的通用封装约定，以后见到 32 hex + 尾串就该先按它套。
③ 反射扫类要【收窄】。第一版扫 1540 个类把 app 拖崩；
   第二版只扫 80 个类，虽然无命中，但过程稳定。
```
