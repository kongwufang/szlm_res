## 为什么要抓包

取 DUID 的关键是拿到**注册瞬间**那一份 `mdna` 报文，而它：

```
· 只发一次
· 在 App 启动后几秒内
· 且走 HTTPS
```

所以必须**在目标进程里挂钩子，并且赶在那几秒之前挂上**。

这一节记录为此踩过的全部坑。

---

## 坑 1：App 检测到注入

```
现象：提示「该应用被注入 so」，然后闪退
原因：App 读 /proc/self/maps，扫 frida-agent 的特征行
```

### ✗ 错误的解法

挂钩 `read()`，过滤掉 maps 里含 `frida` / `gum` / `gadget` 的行。

**为什么不行**：

```
read 是【极高频】函数 —— 全 App 每一次读都进 JS 回调
⇒ 目标 App 直接 ANR
```

### ✓ 正确的解法：maps 重定向

```
在 open/openat 层拦截对 /proc/*/maps 的访问：
  ① 现场生成一份【滤掉 frida 行】的副本
  ② 把副本的真实 fd 返回给调用方
⇒ 完全不碰 read，零高频开销
```

实测生效：

```
[ok] open（maps 重定向）
[ok] openat（maps 重定向）
★★ 重定向 maps: /proc/self/maps -> fd=178
```

**这是整个抓取链路的关键突破。**

## 坑 2：反调试（四层）

| 层 | 手段 | 应对 |
|---|---|---|
| ① | 检测文件名叫 `frida-server`、监听默认端口 | 改名为 `fs`、换端口（如 31337） |
| ② | 检查 frida-server 权限 | root 下用 `setsid` 启动 |
| ③ | `prctl(0x53564D41)` = `"SVMA"` | 拦截并返回 0 |
| ④ | `tgkill` 发 `SIGTRAP` | 拦截 SIGTRAP(5) / SIGABRT(6) |

另外常见的还有：

```
strstr 命中关键词      → 置 0
ptrace                 → 置 0
_exit / exit / abort   → 只记录，不拦截（拦截会导致状态不一致）
Java 层的 Process.killProcess / Process.exit / System.exit
```

## 坑 3：反复 ANR（五个坑）

| # | 触发原因 | 后果 |
|---|---|---|
| ① | 无差别 hex 转换 —— 每条 SSL 记录都转 16KB | 4221 条 ≈ 7000 万次 JS 操作 → ANR |
| ② | 挂钩 `read()` 过滤 maps | read 极高频 → ANR |
| ③ | 放宽 SSL 过滤条件 | 转 hex 的量暴涨 → ANR |
| ④ | SOCK 一律 hex，且钩了 `write` | write 频率极高 → ANR |
| ⑤ | 缓存的按钮坐标点按 | 页面一变就点到《用户协议》链接 → 跳浏览器 |

### 统一规律

```
热路径上的活越少越好。

· 高频函数（read / write / 每次 SSL 记录）绝不挂重钩子
· 必需的转换必须加条件筛选，不能无差别执行
· 用【缓存坐标】做 UI 操作，一定要在动作前重新确认目标还在
```

### 具体做法

```js
// SOCK：只对「像 HTTP」的记录做 hex
if (src === 'SOCK') {
    const b = new Uint8Array(arr.readByteArray(4));
    keepHex = (b[0]===0x50 && b[1]===0x4f && b[2]===0x53 && b[3]===0x54)   // POST
           || (b[0]===0x47 && b[1]===0x45 && b[2]===0x54 && b[3]===0x20)   // GET
           || (b[0]===0x48 && b[1]===0x54 && b[2]===0x54 && b[3]===0x50);  // HTTP
}

// 刻意【不】挂钩 write / read
// 只挂 send / sendto —— 它们已覆盖 socket 出站
```

## 坑 4：最隐蔽的一个 bug —— `toHex` 类型错误

### 错误代码

```js
// ✗ 错
function toHex(arr, n) {
    const b = new Uint8Array(arr);     // ← 问题在这里
    ...
}
```

### 为什么会错

```
new Uint8Array(pointer)  并不会读取该指针指向的内存。

它只对 array-like 有效：
  · Java byte[]      → 可用
  · NativePointer    → 得到长度 0
```

### 后果

```
Cipher 钩子传的是 Java byte[]        → 老写法能用 → hex 正常
SSL / socket 钩子传的是 NativePointer → hex 恒为空

⇒ 所有 SSL 与 socket 数据被【静默丢弃】
```

### 为什么难发现

```
表象是「抓不到包」
很容易误判为「过滤条件太严」
⇒ 于是去改过滤条件 —— 反而引入 ANR
```

**这个 bug 困扰了整个采集阶段。** 期间反复调整过滤条件、反复 ANR，
直到写了一个专门的诊断脚本（`diag_ssl.js`）打印指针可读性，才定位到。

### 正确写法

```js
function toHex(arr, n) {
    let b = null;
    try {
        if (arr && typeof arr.readByteArray === "function") {
            const ab = arr.readByteArray(n);       // NativePointer 路径
            if (ab) b = new Uint8Array(ab);
        }
    } catch (e) { }
    if (!b || b.length === 0) {
        try { b = new Uint8Array(arr); } catch (e) { }   // Java byte[] 路径
    }
    if (!b || b.length === 0) return '';
    ...
}
```

### 修复后立刻见效

```
REC p25185 t=24213 SSL n=1977 hex=504f5354202f736572766963...
= POST /service/2/app_log/?version_code=2609151&... HTTP/1.1
  Host: log.zijieapi.com
  User-Agent: Dalvik/2.1.0 (Linux; U; Android 8.1; …)
  Content-Length: 1590
```

**完整的请求行 + 请求头 + body 都拿到了。**

## 坑 5：attach 太慢，错过注册瞬间

```
现象：钩子在 10~21 秒后才装上，而注册在第 2~5 秒就开始了
原因：用 enumerate_processes() 遍历全部进程再筛选，每次调用很慢
```

### 解法

```python
# ✗ 慢：遍历全部进程
for pr in dev.enumerate_processes():
    if pr.name == PKG: ...

# ✓ 快：直查目标进程
pr = dev.get_process(PKG)
```

**attach 时间从 10~21 秒降到 2.4 秒。**

另外：**轮询线程要在 `am start` 之前就启动**，否则第一轮已经错过了。

## 坑 6：关键请求被淘汰

```
记录数组有环形缓冲：超过 2000 条就丢掉最老的 800 条
而 mdna 在注册最早期（t≈77 秒）发出 → 一直被冲掉
```

### 解法：给关键请求做永久保留

```js
const KEEPS = [];   // 不参与淘汰

// push 时如果是 szlm 的 HTTP 请求，额外存一份
if (rr.hex && (src === 'SSL' || src === 'SOCK')) {
    const h0 = rr.hex.slice(0, 8);
    if (h0 === '504f5354' || h0 === '47455420') {          // POST / GET
        if (rr.hex.indexOf('74656c65636f6d65') >= 0         // "telecome"
            || rr.hex.indexOf('6d646e61') >= 0              // "mdna"
            || rr.hex.indexOf('61756e69') >= 0) {           // "auni"
            KEEPS.push(Object.assign({}, rr));
        }
    }
}
```

dump 时以 `KEEP p<pid> t=…` 行输出。

**加上这个之后，`mdna` 立刻就被抓到了。**

## 坑 7：UI 操作误触

```
现象：点按"同意协议并继续"之后跳到了浏览器
原因：用的是【缓存的按钮坐标】，
      而页面状态变了 —— 同一个坐标此时落在《用户协议》链接上
```

### 解法

```
① 每次点按前【重新 dump UI】，确认目标按钮在场
③ 目标不在场就绝不点
```

### 配套：弹窗处理

```
白名单（安全的）：取消 / 以后再说 / 稍后 / 关闭 / 我知道了
黑名单（危险的）：立即更新 / 更新 / 下载 / 安装
  → 检测到黑名单按钮时，按 BACK 回避，绝不点它
```

**更新提示弹窗会挡住界面**，干扰"是否在协议页"的判断 —— 这个问题是靠**周期截图**发现的。
