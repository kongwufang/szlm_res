# DUID 锚点排查报告（收尾）

## 一、这一轮确立的事实

### 1. `pm clear` 之后 DUID 不变

```
pm clear com.coolapk.market  -> Success
残留 prefs 文件数: 0（dna.xml / v7.xml / prefs.xml 全部消失）
启动酷安 -> 协议页 -> 同意 -> 数盟初始化
[getQueryID] = DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9    ← 与清空前完全一致
dna.xml 于 09:10 重新生成（pm clear 在 09:08），值相同
```

**App 数据全部清空，服务端仍返回同一个 DUID。** 这确认了：服务端是按「设备指纹」识别的，而不是按本地状态。

### 2. 已排除的锚点（全部实测）

| 候选 | 实验 | 结果 |
|---|---|---|
| `android_id` | `settings put secure android_id` 改值 | DUID 不变 |
| `ro.serialno` / `ro.boot.serialno` | `resetprop` | DUID 不变 |
| `ro.build.fingerprint` | `resetprop` | DUID 不变 |
| `ro.product.model/brand/manufacturer/name/device` | `resetprop` 全套改成 Xiaomi | DUID 不变 |
| 本地全部文件 | `pm clear` | DUID 不变 |
| **MAC（Java API）** | hook `NetworkInterface.getHardwareAddress` / `WifiInfo.getMacAddress` / `BluetoothAdapter.getAddress` | **调用 0 次** —— 数盟根本不读 |
| **MAC（sysfs）** | hook `fopen` 监视 `/sys/class/net/*/address` | **无读取记录** |

**MAC 这条线索可以正式排除了。** 之前那轮「改 MAC 后 DUID 不变」的实验是无效的——`ip link set wlan0 address` 被展锐驱动拒绝，MAC 从头到尾都是 `40:45:da:f2:2d:e2`。我拿一个没生效的修改去否证 MAC，这是错误的。

### 3. 数盟的存储只在两处

```
/data/data/com.coolapk.market/shared_prefs/com.coolapk.market_dna.xml
/data/data/com.coolapk.market/shared_prefs/coolapk_preferences_v7.xml
```

（`/data/local/tmp/du_bak/` 等是此前实验留下的备份，与数盟无关。）

## 二、技术突破：现在能抓 TLS 明文了

之前一直抓不到数盟的请求，是因为姿势不对。**找到正确方法**：

```js
// Module.findExportByName(null, 'SSL_write') 在 Android 上返回 null（命名空间隔离）
// 必须用 enumerateExports 精确定位
Process.findModuleByName('libssl.so').enumerateExports()
  .filter(e => e.name === 'SSL_write' || e.name === 'SSL_read')
```

hook 后已成功抓到多个 SDK 的**完整明文请求与响应**：

```
快手   POST /rest/e/v3/open/appCheck   Host: open.e.kuaishou.com
友盟   POST /ext_event                  Host: cnlogs.umeng.com
字节   POST /service/2/app_log/         Host: log.zijieapi.com
```

**这套 hook 是可用的资产**，挂在 `real_ssl.js` / `real_tls.js` 里。

## 三、卡点

数盟的注册请求抓不到，原因有二：

1. **时机** —— 数盟在「同意隐私协议」之后才初始化。改成「先 attach 到协议页、再点同意」后确实抢到了窗口，但点协议会触发**进程重启**（`32548 -> 1452`），重启后的实例上 TLS 零流量（`write=0 read=0`），也没有 `getQueryID`。
2. **可能不走 TLS** —— `libdu.so` 的动态符号表里有 `socket/connect/sendto/recvfrom`，但**没有任何 SSL 符号**。它要么内嵌了自己的 TLS 实现，要么走裸 TCP。而 `real_net.js` 早先抓到它 `connect` 到 `[v6]:443`，说明有 TLS，只是不在系统 `libssl.so` 上。

## 四、给后续的可行方向

**方向 A：hook `libdu.so` 内部的加密函数，而非系统 TLS**
- 加密入口已知：AES 包装 `0xe9218` / 实体 `0xe9408`
- 但实测 **hook 这两个点会立即被杀**（数盟对关键函数做了完整性校验）
- 需要先绕过完整性校验，或者找它内部的「发送前最后一站」（比 AES 更外层，风险更低）

**方向 B：在 `connect` 点定位数盟的网络函数**
- hook `connect` 抓 backtrace（低频安全），找到 `libdu` 里发起连接的那个函数
- 然后在它的上游 hook，拿到加密前的数据

**方向 C：从服务端侧反推**
- 已知协议要素齐全（AES key、device_label 公式字节级一致、body 管线可往返）
- 但 `auni.telecome.cn` 对任何 POST 都返回 400（本机 / 设备 / HTTP / HTTPS / HTTP2 全试过）
- 说明端点对外部请求不开放，或已迁移

## 六、必须承认的

这轮我犯了两个方法错误，都是「用无效实验当否定证据」：

1. **MAC**：`ip link set` 没生效（驱动锁定），我却据此判定「MAC 不是锚点」。
2. **400 判读**：把「POST 一律 400」判成网关拦截，结论摇摆了两次。事后看，`POST /robots.txt` 也是 400 确实说明是前置层行为，但这与「数盟真实请求能通过」并存，说明真正的通行条件我仍未找到。

**核心未解问题依旧**：数盟拿什么字段认定「这台设备是谁」。已知它不看 android_id / serialno / 机型 / 本地文件 / MAC，那剩下的候选集中在：
- 应用签名证书（不可伪造，但所有酷安设备相同，无法区分设备）
- 内嵌 TLS 的客户端指纹
- 完整指纹 JSON 的某个规范化哈希（`p`/`r`/`h` 之一）
- 我尚未枚举到的某个系统标识
