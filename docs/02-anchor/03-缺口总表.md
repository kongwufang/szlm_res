# GAPS · 距离目标的缺口总表

> 日期：2026-10-04 ｜ 目标：**不依赖酷安 app，用自己的 app 找数字联盟取回该设备以前注册过的 DUID**

---

## 零、目标（用户原话）

> 我的目的是替代酷安去数字联盟把那个 id 拿下来，具体实现原理是用设备指纹自己构造请求
> 去请求数字联盟拿到以前酷安注册过的 id。
> 实现闭环验证的时候我需要一个最简单的 app，读取设备信息，找数字联盟请求酷安注册过的 id，
> **即使设备上根本没有酷安（不依赖酷安 app，只需要曾经安装过并注册过）**

## 一、已经打通的部分（有实测背书）

### 1.1 协议层 —— 基本全解

| 项 | 内容 | 验证 |
|---|---|---|
| 端点 | `auni.telecome.cn/a/{mdna,adt,daa,dcc2,dai,audd}/...`<br>`yumao.puata.info/anti_logs`（带 appkey 头）<br>`ccs.umeng.com/ra`（带 appkey 头） | ✅ 抓到明文 HTTP |
| 参数 | `?v=&t=&c=&e=&p=&r=&n=&l=&h=` | ✅ |
| `p` | `MD5("com.coolapk.market" + "." + "37be8a1ee106979a").upper()` = `F9BD0FBDACFE80FCF34370FBCFEE1A98` | ✅ 逐字符 |
| `h` | `MD5(DUID + "." + "889e0b01").upper()`，首次为 `"0"` | ✅ 三条独立证据 |
| `r` | 32 位小写 hex，**每次随机；服务端不校验** | ✅ |
| body 加密①（Java 路径） | `AES-128-ECB(key="GWL8jXHLnzp63QDH", gzip(JSON))`，**无盐** | ✅ 我用项目样本实测 |
| body 加密②（native 路径） | `zlib(JSON) XOR 池常量`（4 个密钥） | ✅ 我解出 34 个样本 |
| 响应解密 | 同池常量 XOR | ✅ |
| 池常量 | `0x109CF0` / `0x10924C` / `0x1090F8` / `0x0FEC5C` 处的**字符串** | ✅ 与 libdu 内存吻合 |

### 1.2 ★ 服务端校验边界（决定性，约 100 次变体实测）

```
【必须对的 —— 只有 6 个字段】
  URL.v      与端点匹配
  body.DUv   精确 == "com.coolapk.market"
  body.3mS   小写 v + 版本 >= 9.x
  body.2cO   "秒.纳秒"，纳秒非零，±12~24h 窗
  body.AAA   "v1.0"
  body.mIS   ★ 唯一钥匙 —— 服务端判据的种子

【完全不校验】
  URL:  p / h / r / n / l / t
  body: 其余 72 个字段（机型 R3d / 厂商 R37 / MAC 三元组 / 内网 IP / 语言 /
        网络类型 / 时间戳 / 各种混淆串 —— 删光改字都不影响）
  75c:  删掉即可
  ⇒ 出口 IP、设备指纹字段、整份 body 内容 都无关
```

**⇒ 含义：您那个 app 的请求体，只需要 6 个字段。其中 5 个都能本地造。**

### 1.3 DUID 的性质

```
· 设备确定性：pm clear 后重注册拿到同一个值（我实测 3 次）
· 服务端签发，客户端算不出来
· 四台设备的 DUID 都已知：
    D1 DUaVFlbAMrmH2Z57PEhm_N9EO4RoUdvNstg5
    D2 DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9
    D3 DU8N1bbZfcNSfbmsBFOhsJslrOSOR3dL6eg5
    D4 DU1pGU7EXcGo9LQWg8PIHk9uBFUqDjnlVJg6
```

### 1.4 ★★ mIS 的定性（关键，已查清）

```
mIS 的值 = 【设备标识种子】
  · 换成另一个已知 36 字符串（如 dLH 的值）→ 返回【另一个 DUID】
  · 连发 3 次结果完全一致 ⇒ 派生是【确定性】的
  · 自造串 / 改 1 字符 / 反转 / 去反斜杠 → 全 0
  ⇒ 服务端按它【查表】返回 DUID
```

### 1.5 ★ 逻辑必然性（用户指出，正确）

```
pm clear 后本地零状态 → libdu 不知道自己是新设备还是老设备
→ 它只能把「能标识本机」的信息放进请求
→ 服务端据此认出设备、返回同一个 DUID
⇒ 请求里【必然存在本地可重算的设备标识】
⚠️ 文档 MIS_ALGORITHM_RESULT.md 的「mIS 不可本地构造」是【过度结论】——
   它把「我们穷举失败」当成了「本地算不出来」
```

## 二、★ 剩余缺口（4 个，按重要性）

### 【缺口 1】mIS 的构造算法 ★★★ 核心

```
已知：
  ✓ 定性：设备标识种子，服务端查表
  ✓ 36 字符，字符集 62~72 种
  ✓ 同一次运行内跨端点一致（mdna 与 audd 相同）
  ✓ 不同次注册不同

已排除（全部有依据）：
  ✗ 固定 XOR 密钥（T = 0x54 → '('，\ = 0x5C → '&'，而 T XOR \ = 0x08，违反双射）
  ✗ 单表代换（同一字符在不同位置映射不同）
  ✗ 纯 base64（字符集 > 64）
  ✗ 明文 XOR 位置密钥流（三种明文假设下唯一确定位置仅 2/4/0，共 36）
  ✗ 候选输入 → MD5/SHA → base64（12 候选 × 3 哈希 × 3 编码，无匹配）
  ✗ 自定义字母表穷举（64! × 随机明文，信息不足，数学上不可解）
  ✗ 我本会话额外用差分分析独立验证：不存在固定逐位 key（pos 5/8 可行 delta = 0）

缺的是：
  ✗ mIS 的【输入】是什么，以及变换是什么
```

**怎么补（明确的实验）：**
```
同一台设备：
   第 1 次：pm clear → 走注册 → 抓 mdna 明文，存下来
   第 2 次：pm clear → 走注册 → 抓 mdna 明文，存下来
   逐字段 diff：
       哪个字段【两次完全相同】 → 它（或它所在的组合）就是本地可重算的设备身份
                                  → 同时也是 mIS 的输入或 mIS 本身
       哪个字段每次不同          → 时钟/随机/会话量
```

**前置：缺口 3（要先能抓到注册期的 mdna）。**

### 【缺口 2】抓不到注册期那条含 mIS 的请求 ★★ 缺口 1 的前置

```
现状（本会话实测）：
  c3 时序： [2s]点按#1 → [21s]点按#2(prefs=34) → [48s]prefs=289
            钩子 [守望+10.5s] 才装上
            抓到的 8 条明文时间戳: 52s/62s/65s/79s/85s/91s/165s/289s
            ⇒ 【21~48 秒那个注册窗口里，一条都没有】

可能原因：
  · 注册那一刻的上报在 attach 完成之前就发出了
  · 或者走了不经 Java Cipher 的路径（native socket）
```

**已备好的三条路：**
```
A. 把 frida 侧轮询挪到 am start 之前 + get_process() 直查（已做，仍不够快）
B. 同时 hook native 侧：libjavacrypto.so 的 EVP_*、libdu.so 的编码器
C. ★ 用 spawn+gating 抢第 0 毫秒
   —— 之前失败是「被检测到注入 → 进程自杀」，
      现在 maps 重定向已补上这个短板，值得重试【我认为最可能】
```

### 【缺口 3】`suffix`（决定 `p` 的 16 位 hex）的派生 ★ 但不影响目标

```
已知：
  ✓ 16 位小写 hex，每设备恒定
  ✓ 不依赖 android_id / serialno / 机型 / 品牌 / 厂商（实测改过都不变）
  ✓ 不读 MAC（数盟根本不读）
  ✓ 在 Java 层生成（native 调用栈断在 JNI 桥）

缺：它的具体输入值 x（数盟内部统一用 MD5(x)[:16] 模式）
```

**★ 为什么它不影响目标：`p` 服务端【完全不校验】（文档 §2.2 实测）。**
**⇒ 您的 app 里把 `suffix` 当常量写死即可。**

---

### 【缺口 4】设备端发送的可接受性 ★ 对您的 app 不是问题

```
文档实测：同一份请求，本机 Python 发送恒为 400，设备端 Java 发送返回 200
⇒ 服务端有反自动化措施（TLS 指纹 / 网络栈特征）
⇒ 端到端验证必须在【Android 设备上】进行
```

**★ 对您的 app 不是缺口：您的 app 本来就跑在设备上。**
**⚠️ 但意味着：纯服务端/PC 侧的方案走不通。**

## 四、关键路径

```
抓注册期 mdna 明文           ← 缺口 2（工程问题，三条路已备好）
   ↓
diff 两次 pm clear 注册的字段 ← 缺口 1 的前提
   ↓
找出跨注册恒定的设备身份字段
   ↓
它就是 mIS 的真身或其输入
   ↓
解出构造公式
   ↓
★ 您的 app 可直接本地算 mIS → 构造请求 → 拿回 DUID（不依赖酷安）
```

**退路（如果 mIS 含服务端签发的随机成分）：**
```
抓一次 mIS + 2cO 子秒 → 永久复用（文档实测派生确定性）
⇒ 仍需酷安在场一次，但之后可脱离
```

## 五、一句话总结

```
协议层：  ✅ 几乎全解（端点/参数/两套加密/校验边界）
请求构造：✅ 只需 6 个字段，其中 5 个本地可造
唯一钥匙：❌ mIS 的构造算法 —— 这是【唯一的真缺口】

而 mIS 必然本地可算（pm clear 后 DUID 不变的逻辑必然性），
所以这是个【有解的问题】，缺的只是【抓到注册期那一条请求】。
```
