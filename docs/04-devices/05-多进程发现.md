# 多进程结构发现 + 当前状态

## 一、关键发现：数盟运行在独立进程

酷安**不是单进程**。实测：

```
pid=29347    libdu=0    libssl=5     ← 主进程（界面）
pid=29602    libdu=3    libssl=3     ← ★ 数盟进程
```

**判据：看哪个进程加载了 `libdu.so`。**

```bash
# 精确定位数盟进程
for p in $(pidof com.coolapk.market); do
  echo "$p: $(grep -c libdu /proc/$p/maps)"
done
```

**这解释了之前反复失败的原因**：`capture_timing.py` 只 attach `pidof` 返回的第一个 pid，
而数盟可能在第二个进程里。之前成功那次是单进程结构，所以抓到了。

**新的做法**：`attach_all.py` —— attach 所有酷安进程，并持续发现新出现的进程。

## 二、本轮实测时间线

```
[0] 启动酷安 -> pids=[17977]，libdu=3      ← 数盟进程先起来
[4s] 进程变成 18410（17977 退出）           ← 进程结构会变
     attach 18410 成功
     [getQueryID] = null                    ← 数盟未完成初始化
[9s+] dna.xml 仍不存在
```

**观察**：`getQueryID` 返回 `null` 说明数盟对象存在但初始化未完成。
这通常意味着它在等待网络就绪或某些前置条件。

## 三、网络问题的完整定位

这轮网络故障排查的结论：

| 层 | 状态 |
|---|---|
| WiFi 关联 | `1702_5G`，`COMPLETED`，RSSI -86，390Mbps |
| IP | `10.0.0.7/24` ✓ |
| 网关 ARP | `10.0.0.1 lladdr f4:6d:2f:34:af:61 REACHABLE` ✓ |
| ICMP | **路由器禁 ICMP，100% 丢包是正常的**，不代表不通 |
| DNS | 解析成功 ✓ |
| 实测 | **酷安能加载内容 = 网络确实通了** |

**教训**：不要用 ping 判断手表网络是否可用。路由器普遍禁 ICMP。
**正确判据**是网关 ARP 是否 `REACHABLE`，以及酷安能否加载内容。

排查中踩的坑：
- `ip link set wlan0 down/up` 会弄断接口且不会自动重新 DHCP，要用 `svc wifi disable/enable` 恢复
- UDP/APK 侧显示 `ASSOCIATION_REJECTION` 时，说明路由器主动拒绝，需要手动重连或换 SSID

## 四、DUID 的稳定事实（再次确认）

`pm clear` 全清后重新注册，服务端返回的仍是：

```
device_id = DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9
```

**这是整条链路上最硬的事实**：本地数据清空不影响服务端判断，它按设备指纹签发。
