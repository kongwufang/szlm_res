## 二、★★★ 重要发现：libdu 在「短命进程」里加载

### 2.1 实测记录（S37，清新数据）

```
★ 协议 '同意协议并继续' @(241,415)
★★★ 发现 libdu！pid=13236 -> 注入   ✗ the connection is closed
★★★ 发现 libdu！pid=14260 -> 注入   ✗ process not found
★★★ 发现 libdu！pid=15205 -> 注入   ✗ unexpected early end-of-stream
```

**⇒ 清新数据 + 点同意，libdu 确实会加载（确认 3 次），
   但它在一个极短命的进程里，做完注册工作立刻退出。**

### 2.2 由此否定的三个方案

```
✗ 事后 attach（等 libdu 出现再挂）—— 进程已死
✗ spawn+gating 的 child-added —— 不触发（该进程不是主进程的子进程，
                                   是系统拉起的服务进程）
✗ 单纯加快轮询 —— 进程存活时间比 adb 往返还短
```

### 2.3 正确方向

```
一旦 /proc 里出现【任何】该包名的新进程，立刻 attach
（那时 libdu 往往还没加载，钩子来得及）
```

## 三、★★★ 修掉一个关键 Bug：进程检测误报

### 3.1 症状

```
sanity check 时发现：45 秒内「发现」153 个新进程，全部 attach 失败
（unable to find process with pid xxx）
```

### 3.2 根因

```python
# 错误写法
grep -l coolapk /proc/[0-9]*/cmdline
```

**Coolapk 自己会频繁执行 `content` 命令**（日志里每 0.5 秒一次
`Calling main entry com.android.commands.content.Content`），
而那些命令进程的**参数里含** `content://com.coolapk.market/...`，
所以 `grep coolapk` 把它们全匹配进来了。

### 3.3 修正

```python
# 正确写法：cmdline 的【第一个 token】必须等于包名或其子进程
for f in /proc/[0-9]*/cmdline; do
    n=$(tr '\0' '\n' < $f 2>/dev/null | head -1)
    case "$n" in
        com.coolapk.market|com.coolapk.market:*) echo "${f#/proc/}";;
    esac
done
```

**修正后：一次只返回 1~2 个 pid（正确）。**

## 四、★★★ 设备操作教训（血泪）

### 4.1 ★★★ 绝不 `rm -rf /data/data/<pkg>`

```
我做了一次 rm -rf /data/data/com.coolapk.market
=> 连目录本身都删了
=> app（非 root，uid 10130）无法重建子目录，启动即崩：

   java.lang.RuntimeException: Unable to create application
     com.netease.nis.wrapper.MyApplication:
     android.database.sqlite.SQLiteCantOpenDatabaseException
   W ContextImpl: Failed to ensure .../databases: mkdir failed: ENOENT
   W SupportSQLite: Invalid database parent file: .../no_backup
```

**修复要三件事都对：**
```
① 目录存在        mkdir -p /data/data/<pkg>
② 属主正确        chown <uid>:<uid>  +  chmod 771
③ ★ SELinux 上下文  restorecon -R /data/data/<pkg>
                   （从 system_data_file 改成 app_data_file:s0:c512,c768）
```

第 ③ 条最容易漏 —— 只做 ① ② 仍然崩溃。

**正确做法：重置 app 数据只用 `pm clear`。**
工具：`fix_appdir.py`（自动完成 ①②③ 并验证启动）

### 4.2 ★★ 系统错误弹窗会挡住一切

```
实测：屏幕上有个 "Application Error: io.github.vvb2060.magisk" 对话框，
      导致 fg() 一直读到错误窗口，所有点击都失效，白跑好几轮。
```

**修法：所有自动化脚本都要先检测并关闭系统弹窗**
```
if "Application Error" in cur or "not responding" in cur or cur == "警告":
    input keyevent KEYCODE_ENTER / KEYCODE_BACK
```

### 4.3 ★ 老设备 toybox 缺 awk/sed

```
10.0.0.37 (SDK 27) 上 `awk: not found`
=> 所有 shell 命令要避免 awk / sed，改用 grep + Python 侧解析
```

## 七、★ 下一步（明确的）

```
要在短命进程里成功挂钩，需要把「发现 -> attach」的延迟压到毫秒级。
当前瓶颈是 adb 往返（每轮 ~80ms）+ frida attach（~300ms）。

三个可选方向：

A. 【降低轮询成本】把监控搬到设备端
   · 设备端 shell 循环：发现新进程就立刻 `frida-server -p <pid> ...`
     或把 pid 写到一个固定文件，Python 读文件（无 adb 往返）
   => 类似之前 device_hunt 的思路（已验证设备端执行可行）

B. 【用 zygote 级挂钩】在设备上常驻一个 frida 脚本，
   用 Interceptor 挂 `fork`/`exec`，任何新进程都能被立即看到

C. 【降低进程存活门槛】找到让该进程存活更久的方法
   · 例如：先让它注册失败（断网），它可能会重试并停留更久
   · 或：用 `am startservice` 直接拉起那个服务进程，反复试

★ 推荐 A（成本最低，且已验证过设备端执行可行）
```

## 八、本轮教训汇总

```
① 设备操作要小心：rm -rf 数据目录 = 破坏 app（还要修 SELinux）
② 自动化前先检查有没有系统弹窗挡着
③ 进程匹配要精确（cmdline 首 token），否则误报上百个
④ 老设备 toybox 缺 awk/sed，shell 命令要简化
⑤ 压测前看电量（D2 被耗到 1%）
⑥ 同一脚本在不同设备上结果可能完全不同 —— 要分别验证
⑦ 「attach 成功」不等于「抓到数据」—— 要确认进程活得够久
```
