## 二、★ 本轮踩到并修掉的 4 个「命令传递」坑（全部实测过）

root 命令在三台设备上都不好写。四个阶段：

```
① su -c '<cmd>'
   PowerShell/adb 把引号吃掉
   → adb: device '/data/data/com.coolapk.market/files/cap' not found

② su -c <cmd>            （命令作为独立 argv）
   被压平后 cmd 拆成多个 argv
   → mkdir: Needs 1 argument

③ su -c sh -c "…"
   adb 把嵌套引号压平，sh 拿不到完整命令
   → 同上

④ ★ 最容易误判的一条：只写 `su -c <cmd>` 时，
   cmd 里的【重定向】仍由外层 shell 以 shell 身份执行
   → echo t > /data/data/.../.wtest 报 Permission denied（假失败！）
```

**最终解法（三台全部 `WRITEOK`）**：

```python
b = base64.b64encode(cmd.encode()).decode()
line = ('echo %s | base64 -d > /data/local/tmp/.c.sh; '
        'su -c "sh /data/local/tmp/.c.sh"' % b)
subprocess.run([ADB, "-s", serial, "shell", line])
```

引号零参与，重定向在 root 内层执行。已固化进 `cross_validate.Cap.sh()`。

## 六、★ 换个更稳的取种子思路（建议下一步）

既然 `mIS` / `2cO` 是种子，而抓 mdna 不稳定，**可以从「客户端侧」直接拿**：

```
思路：反射读 ShuzilmSDKManager 的 ހ()（当前 DUID）
       + 反射读构造 mdna body 的那个「Java 状态对象」
       —— 种子的来源就在那个对象里（mIS / 2cO 都是它的字段）

可行依据：
  · SDKMANAGER_INVOKE.md 已证实 ހ() 能在运行时读到 DUID
  · cap_file.js 抓到的 body 就是那个对象序列化来的
  · 所以反射读该对象比抓网络稳（不需要等上报时机）

要定位的对象：mdna body 的构造者
  —— 已知链路：Java 状态对象 → JSON → zlib → 异或 → HTTP
```

**另一条更省事的路**：让 D1/D2/D3 各保留一份**已注册**状态（不做 pm clear），
然后**只在「删除 dna.xml + 重启」这一条路上抓 mdna** —— 这条路径在
`N_D2` 那一轮曾经成功抓到过 `daa`（当时钩子已在位）。

## 八、教训

```
① 「按钮坐标」必须逐设备取。三台里有两台碰巧同分辨率，但坐标系仍有差异；
   第三台连分辨率都不同。用配置表 + 运行时实测兜底（先 uiautomator 现取，
   取不到再用表里的值）是稳的做法。

② root 命令的传参方式是个独立的技术问题，值得单独解决一次。
   我在这上面花了 4 轮，每次都以为是「权限问题」，其实是「引号/argv 被压平」。
   判据应该是：报错里出现 `device '<路径>' not found` ⇒ 引号被吃；
   出现 `Needs 1 argument` ⇒ argv 被拆。
```
