# 「替设备取 ID」方案 —— 可行性实测

> 用户提出的思路：**用户手机装了酷安就行**，c001apk 不需要服务端生成新 ID，
> 只要把**设备指纹**发上去，把酷安已经申请到的 ID 拿下来即可，不用考虑注册。
>
> 本轮就针对这个思路做实测。**结论：思路成立，但有两个「种子」必须先拿到。**
>
> 日期：2026-10-03

---

## 一、★★★ 发现 1：`mIS` 是【服务端登记过的精确值】，不是格式规则

`proxy_client_probe.py` 实测（最小 6 字段 body）：

| 变体 | 结果 |
|---|---|
| ① 原值 | ★ 真 DUID |
| ⑨ 原值**大写** | ★ 真 DUID（归一化） |
| ② 只改 1 个字符 | **全 0** |
| ③ 原值字符重排 | **全 0** |
| ④ 36 个 `A` | **全 0** |
| ⑤ 36 位数字+字母 | **全 0** |
| ⑥ base64url 形态 | **全 0** |
| ⑦ 去掉反斜杠 | **全 0** |
| ⑧ 去掉引号 | **全 0** |
| ⑩ `dLH` 的值（另一个已知值） | **另一个 DUID** |

**⇒ `mIS` 只有「服务端已知的那几个值」能用。** 它不是格式校验，是**查表**。

---

## 二、★★★ 发现 2：`2cO` 的**纳秒部分**必须逐纳秒精确

`ts_window_probe.py` 实测（最小 6 字段 body，只动 `2cO`）：

```
秒部分 ±43200（±12 小时）   ->  ★ 真 DUID（全过）

纳秒部分（秒不变）：
  全 0（000000000）        ->  全 0
  1                       ->  全 0
  原值 - 1 纳秒             ->  全 0
  原值 + 1 纳秒             ->  全 0
  原值前 3 位 + 000000      ->  全 0
  全 9                     ->  全 0
```

**⇒ `2cO` 的种子不是「登记时刻」（秒），而是那串【纳秒】。**
秒可以漂 ±12 小时，纳秒一个都不能差。

### 2.1 这解释了之前几轮的矛盾

```
min_ts_probe.py（同一轮内，消除跨运行差异）：
  A 完整 body + 2cO=现在         -> 全 0
  B 最小 6 字段 + 2cO=原值        -> ★ 真 DUID
  E 最小 6 字段 + 时间字段 + 原值  -> ★ 真 DUID
  C/D/F 只要 2cO 不是原值         -> 全 0
```

之前 `mono` 那组「±25h 都过」之所以成立，是因为**纳秒没动**（我只改了秒）。
而「现在的时间」必然换掉纳秒 ⇒ 必然全 0。

**⇒ 早先文档里「时间窗 ±24h」的表述不准确**，应改为：

```
2cO = "秒.纳秒"
  · 秒     : 在登记时刻 ±12 小时窗口内（超出未测）
  · 纳秒   : 必须与登记时完全一致（±1 纳秒即失败）
```

## 三、★★ 发现 3：种子不在设备本地

`seed_hunt.py` 在 D2（`com.coolapk.market`）上搜：

```
[1] mIS 的片段（&&&）    -> 只在 3 个 cache/image_cache/*.1 里命中（噪声）
[2] 2cO 的纳秒 997397935 -> 无命中
[4] dna.xml              -> 【不存在】（这台被我反复 pm clear 过）
[5] 含 DU 的键           -> 0 次
[7] mIS 形态的串（W(W(）  -> 无命中
[6] files/ 下 du/szlm 落盘 -> 无
```

**⇒ 种子既不在 prefs、也不在 dna.xml、也不在 files/** —— 至少在这台「无 DUID 记录」
的设备上找不到。

（注：D2 的 `dna.xml` 不存在，也解释了这几轮为什么抓不到 `/a/` 请求 ——
没有本地 ID，SDK 就没进到上报路径。）

## 四、把发现 1+2 合起来看：这是一套「登记记录」模型

```
服务端保存的记录大致长这样：

    (种子)  ──>  DUID
     │
     ├── mIS 的值（36 字符，服务端登记过的）
     └── 2cO 的纳秒（逐纳秒精确）

请求里必须同时给出这两个种子，服务端才回那条记录的 DUID。
```

**⇒ 用户思路的可行性取决于一件事**：

```
这两个种子能不能在【用户手机】上重新算出来 / 重新拿到？

  能  -> 「替设备取 ID」完全可行（手机装了酷安即可）
  不能 -> 只能靠抓包/读酷安的数据，普通用户做不到
```

## 五、缺口重新排序（针对「替设备取 ID」这个目标）

| 序 | 缺口 | 成本 | 决定什么 |
|---|---|---|---|
| **1** | **种子的来源**：`mIS` 与 `2cO` 纳秒是【本地算出的】还是【服务端发的】？ | 中（清一次真机数据看 DUID 是否不变） | **直接决定方案可行性** |
| 2 | 若种子是本地算的：`mIS` 的算法 | 高（native 反混淆） | 能否纯软件复刻 |
| 3 | 若种子是服务端发的：能否从酷安的数据里读出来 | 低（读酷安 prefs/files） | 需要读别的 app 的数据（普通用户做不到） |
| 4 | `mIS` / `2cO` 是否绑设备（换设备是否失效） | 低 | 能否跨设备复用一份 |
| 5 | 一份 DUID 能否在多设备共用 | 低 | 方案是否能批量用 |

## 六、★ 立刻可以做的判定实验（成本中，一次定性）

```
目的：回答「种子是本地算的，还是服务端发的」

做法（在官方酷安上，D2）：
  1) 记录当前 DUID 与 dna.xml（先让酷安正常跑一次注册）
  2) 删 dna.xml（不清 prefs）→ 重启酷安 → 看新拿到的 DUID
        · 与原来相同 ⇒ 种子能重新产出（本地可复现）★ 方案可行
        · 不同       ⇒ 种子是服务端发的（或与本次随机量绑定）
  3) 再 pm clear 一次 → 重启 → 再看
        · 仍相同 ⇒ 种子完全由设备决定 ⇒ 纯算法可复刻
        · 不同   ⇒ 种子含服务端/随机成分
```

**这个实验在 `dev2/TWO_DEVICES.md` 里其实做过一次**（记录是「清空本地数据后仍拿回同一个
DUID」）—— 但那次没有把 `mIS` 与 `2cO` 抓下来对比。

**⇒ 本轮应该补的是**：在「清数据前 / 清数据后」各抓一次 mdna，比较
`mIS` 与 `2cO` 是否变化：

```
都相同   -> 种子由设备决定，可复刻 ⇒ 方案可行
mIS 变   -> mIS 与某次注册绑定，需要服务端
纳秒变   -> 2cO 种子每次重取都变，需要拿到「当次」的值
```
