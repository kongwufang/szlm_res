## 问题的起点

```
pm clear 之后本地零状态，但重新注册拿到的 DUID 不变
⇒ 请求里必然存在【本地可重算的设备标识】
```

问题变成：那个标识是哪个字段？

---

## ⚠️ 第一次尝试（错误结论）

### 做法

在 87 个字段里**逐字段扫描**，看哪个改了会让结果变化。

### 当时的结论

```
mIS 换成另一个已知值  → 返回【另一个 DUID】
mIS 自造 36 字符串    → 全 0
⇒ 判断：mIS 是"唯一钥匙、判据种子"，服务端按它查表
```

**这个结论被写进了多份文档**，并据此做了大量后续推断。

### 错在哪

```
扫描时【一直保持 mIS 为真值】——
那个真值足以命中记录，把其它所有字段的作用统统遮蔽了。

⇒ 典型的观测设计缺陷：被观测的量掩盖了要找的量
```

**一句话**：每次测试都带着一把"正确的钥匙"，当然测不出别的字段有没有用。

---

## 修正后的实验设计

**先把 `mIS` 随机化，再逐字段扫描。**

```
基线：mIS = 随机 36 字符串 + ubF 清空
做法：逐字段换成【同类型的另一个合法值】
判据：看 n_a 何时变成 36 个 0
```

### 结果

```
真锚点（一换就全 0）：
  ★ DUv    → 换个包名            → 全 0
  ★ 2cO    → 换个合法"秒.纳秒"    → 全 0
  ★ sfOo   → 换个 7 位 hex        → 全 0
  ★ foO    → 换个 15 字符混淆串    → 全 0
  ★ 3mS    → 换个版本号           → 全 0
  ★ 75c    → 换个 apiKey          → 全 0

无关（换了照样返回真 DUID）：
  ✗ mIS    → 换成任意合法 36 字符串 → 仍返回真 DUID
```

**⇒ `mIS` 与设备识别无关；真正的锚点是 `(sfOo, foO, 2cO)`。**

---

## 正确的机制

服务端按**三元组**查表：

```
① 命中                → 返回该记录关联的 DUID（与其余 73 字段无关）
② 未命中 + body 完整   → 新建记录，签发【新 DUID】
③ 未命中 + body 精简   → 返回全 0
```

### 最小可用 body

```
DUv + 3mS + 75c + 2cO + sfOo + foO + AAA + BBB
```

**8 个字段就能取回 DUID。**

### 实测验证

```
只发这 8 个字段（含真三值）        → 真 DUID ✓
只发这 8 个字段（三值随机）        → 全 0
完整 79 字段（三值随机）           → 新 DUID ✓
```

**⇒ 要拿新 ID 必须用完整 body。**

---

## 三元组长什么样

| 字段 | 格式 | 示例 |
|---|---|---|
| `sfOo` | 7 位大写十六进制 | `801C14F` / `4A213D3` / `FD2C5E4` |
| `foO` | 15 字符混淆串 | `RP|Q|zQKOJ~I~}Q` / `W***]TZTYX**X(W` |
| `2cO` | `秒.纳秒` | `1791105420.764024281` |

---

## 三元组的性质（关键实验）

### 同一台设备两次注册的对比

```
第一次  sfOo = 801C14F   foO = RP|Q|zQKOJ~I~}Q   2cO = 1791105420.764024281
第二次  sfOo = FD2C5E4   foO = DEo?qBmCp=DoDq>   2cO = 1791108030.968315068

⇒ 三者【都不同】，但 DUID 相同
```

同一批数据里另外两个统计：

```
跨注册【恒定】55 个字段
   包括 AYk/P1J(MAC)、R3d/R37(机型厂商)、w91/gEd/6yY(指纹哈希)、
   ne8、wSK(内网IP)、75c、Qg1/LMi ……
跨注册【变化】21 个字段
   包括 sfOo、foO、2cO、K5f、UOv、dLH、zvW、5Tv、52J、Bos、IJK、
   IAI、aFw、KyU、ibF、dJs、p1m、LAh、90P、za7、Zne
```

### 由此推出

```
服务端能从【新的三元组】认出同一台设备
⇒ 三元组内部编码了设备信息，且服务端能解码验证
```

### 跨设备对照

| 设备 | `sfOo` | `foO` |
|---|---|---|
| A | `4A213D3` | `W***]TZTYX**X(W` |
| B | `801C14F` | `RP|Q|zQKOJ~I~}Q` |

**⇒ 确认是设备相关的值。**

### 另外发现的

```
ne8 在两台设备上【相同】⇒ 它是常量，不是设备指纹
w91 / gEd / 6yY 跨设备【不同】、跨注册【恒定】⇒ 这三个才是设备指纹哈希
```

**但这三个不参与设备识别** —— 见下。

---

## 有没有签名机制？没有

### 做法

把各种可能"被签名保护"的字段全换成随机值：

```
w91 / gEd / 6yY / ne8  → 随机
AYk / P1J（MAC）        → 随机
R3d / R37（机型厂商）    → 随机
wSK（内网 IP）          → 随机
整类设备属性           → 随机
```

### 结果

```
所有变体【照样返回真 DUID】

⇒ 不存在「必须由私钥签出」的字段
⇒ 三元组不是签名，而是【编码】
```

---

## 但这不等于三元组可以随便填

一个容易混淆的点，实测结果很干净：

```
基线（真三值）                              → 真 DUID
只改三值(sfOo/foO/2cO)                     → 全 0（服务器判「不自洽」）
三值 + w91/gEd/6yY 一起改                   → 新 DUID ✓
```

**⇒ 服务端有一层「自洽性检查」：**

- 如果三值未知、但 body 其余部分**看起来像某个具体设备** → 判为伪造 → 全 0
- 如果三值未知、且其余部分**也不指向特定设备** → 当作新设备 → 签发新 DUID

**这就是 `tools/getduid.py` 的 `-r` 模式为什么要连三个指纹一起随机化。**

---

## 一个意外收获

```
完整 body + 随机三值 → 每次都能拿到一个【有效新 DUID】

⇒ 协议本身是开放的：想注册新设备随时可以
```

实测：连发 3 次，拿到 3 个互不相同且有效的 DUID。

---

## 从这里能看出什么

```
✓ 取回某台设备的 DUID = 拿到它的锚点三元组
✓ 不需要设备指纹、不需要任何密钥
✗ 但三元组本身怎么算出来 —— 未解（见下节）

★ 实践含义：
   想取回某设备的 DUID，抓一次它注册时的三元组即可
   想凭空算出来，需要解出 sfOo/foO 的生成算法
```
