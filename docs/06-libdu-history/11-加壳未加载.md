> 日期：2026-10-03 ｜ 设备：D3 LineageOS GSI
> **本轮找到一个此前没注意到的根本事实，它解释了之前所有静态/动态尝试为什么失败。**

## 一、★ 根本发现：`libdu.so` **加壳**，且运行时**从不加载**

### 1.1 `libdu.so` 确实存在于 APK

```
/data/app/~~lDA5-xecSKBCn4ibyRy1nQ==/com.coolapk.market-.../base.apk
    lib/arm64-v8a/libdu.so      1,417,064 字节
```

已成功抽出并拉到本地：`_rev/native/libdu.so`（25 MB/s 拉取成功）

### 1.2 ★ 但对它做静态分析：**0 命中**

```
mIS / 2cO / 3mS / DUv / ubF / nAt / 75c      -> 各 0 次
apiKey (11e7b222…)                            -> 0 次
盐 (37be8a1ee106979a)                          -> 0 次
模板 (889e0b01 / %s.889e0b01)                  -> 0 次
域名 (auni.telecome.cn)                        -> 0 次
shuzilm / cn.shuzilm                           -> 0 次
64 字符字母表候选（60~68 长、uniq≥58）           -> 0 个
"可疑符号"（encode/base64/mis/sign/digest…）     -> 只有 1 个："permission"
```

**⇒ `libdu.so` 是【加壳 / 字符串加密】的**：代码与字符串在运行时才解密。
（这与早先 `PROJECT_README.md` 记过的「`.rodata` 运行时解密」一致，本轮给出了量化证据。）

### 1.3 ★ 而且它**从不加载**

`when_libdu_loads.py` 监控（跨 2 个进程、100 秒）：

```
[ 10s] pid=4022  本 app 的模块 = [libnesec.so, libxgVipSecurity.so]
[ 10s] pid=4022  含 du 的模块 = []        TOTALMODS 314
[ 22s] pid=4227  本 app 的模块 = [libnesec.so, libxgVipSecurity.so, libucrash.so, …]

```

同一时刻，Java 侧有 **38 个 `cn.shuzilm.*` 类**已加载。

## 二、★ 这解释了此前所有失败

| 之前的尝试 | 为什么失败 |
|---|---|
| 扫 `libdu.so` 的 rodata 找字母表 | 库没加载，`findModuleByName` 返回 null |

**⇒ 一句话：`mIS` 的生成逻辑在 `libdu.so` 里，而这个库既加密、又不加载。**

## 三、★ 关于「签名机制」这个判断

你的判断是对的（有机制就有算法），我同意。但要补一个关键区分：

```
「有算法」≠「算法可复现」

可能有三种情形，而现有证据指向哪一种：
  (a) mIS = H(设备特性)               -> 同设备应恒定        ✗ 实测两轮完全不同
  (b) mIS = H(设备特性 ‖ 随机数)       -> 客户端可生成，服务端只看格式
                                          ✗ 自造 mIS 全 0（服务端查表）
  (c) mIS = H(设备特性 ‖ 服务端下发的挑战) -> 客户端有算法但需要服务端参与 ★

XTQ_Watch 两轮 mIS 逐位对比：0/36 位相同
    （若纯随机，按 62 字符期望偶然相同 36/62 ≈ 0.58 位；实测 0 位
      ⇒ 连"公共结构"都没有 ⇒ 每轮从输入到输出都不同）

⇒ 证据最支持 (c)：它是【每次注册重新协商出来的标识】，
   服务端手里有对应记录（所以自造值全 0），客户端拿到的是"已被服务端认可"的那一个。
   => 这种情况下，算法确实存在，但【输入包含服务端参与的部分】，
      客户端无法单方面复现 —— 不是"算法没找到"，而是"算法不可独立执行"。
```

**要证伪 (c)、支持 (b)，需要一个实验**：

```
让 c001apk（或任何第三方包名）走一次真实 SDK 注册，
看服务端是否给它签发一个 mIS + DUID。
  · 若签发（非全 0）⇒ 服务端接受任意客户端自产生的 mIS ⇒ (b) 成立 ⇒ 可以自己算！
  · 若全 0        ⇒ (c) 成立，服务端只认它自己协商过的
```

**而这正是 `SZLM_SDK_SIGNING_VERDICT.md` 七轮实验已经做过的事 —— 结果全是全 0。**
⇒ 现有最强证据就是 (c)。

## 四、★ 还有哪些没试过的（按可行性排序）

### 路径 1：主动加载 `libdu.so`，然后在内存里 dump 解密后的段

```
思路：既然库加密、又不自动加载，那就【手动让它加载】——
      System.loadLibrary("du") 或 dlopen，然后在加载完成的瞬间
      把它的 .rodata 全 dump 下来（那时字符串已解密）。

可行性：libdu.so 的导出符号里应该有 JNI_OnLoad（SDK 靠它注册 native 方法），
        所以手动加载能触发解密的可能性较高。

成本：中（一次 frida 脚本）
风险：库的自我保护可能检测非预期加载环境而退出
```

### 路径 2：在设备上装一个「纯 SDK 探针」应用，逼它走 native 路径

```
思路：c001apk 仓库里已有 `app/src/probe`（`-PshuzilmProbe=true` 的探针）。
     它可以只调 `cn.shuzilm.core.Main.init()` + `getQueryID()`，
     是最干净的"只跑 SDK"环境。
     —— 若这个探针能让 libdu.so 加载，就能在它里面 dump。

可行性：高（探针代码现成，七轮实验都用的它）
成本：低（装个 APK）
```

### 路径 3：接受现状，把结论定下来

```
结论：mIS 的算法在 libdu.so 里（加壳、不加载），
      且即使拿到算法，输入含服务端参与部分（七轮实验 + 自造值全 0 支持这一点）。
      ⇒ 对"普通用户自己算"，结论是否定的。
```
