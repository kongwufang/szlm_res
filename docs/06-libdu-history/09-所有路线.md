# `libdu.so` 捕获 —— 全路线结果汇总

> 日期：2026-10-03 ｜ 设备：D3 LineageOS GSI
>
> **已穷尽 4 类技术路线。唯一未解决的是「时机」—— 库在清数据后约 4~8 分钟才加载。**

---

## 一、★ 一条铁的事实（已多次复现，是整件事的钥匙）

```
【清空内部数据】+【走完同意流程】 -> libdu.so 才会加载
不清数据 -> 缓存里有 ID -> SDK 短路 -> 库永不加载
```

**这条把所有「触发不灵」都解释了**（mdna 不发、zlib 钩子不触发、内存扫不到东西）。

---

## 二、★ 四类路线的结果

| 路线 | 做法 | 结果 |
|---|---|---|
| **A. frida 注入** | 枚举进程 + attach + 进程内 dump | 抓到过 1 次模块（`base=0x6d76028000 size=1798144`），但读取因两个小问题失败（已修） |
| **B. dlopen 钩子** | 钩 `dlopen`/`android_dlopen_ext`/`__loader_dlopen` | 钩子 3 个全装上（逻辑正常），但只挂到子进程 |
| **C. 纯 root /proc** | 扫 `/proc/*/maps` 找 pid + 直接读 mem | 8 分钟未命中（**不依赖注入，逻辑没问题，差时机**） |
| **D. 主动 force-load** | `System.loadLibrary("du")` + dump | 注入成功但 `Java.perform` 内无输出 |

### 2.1 最后一种（C）为什么值得继续

```
它【完全不需要 frida 注入】——
   0.3 秒轮询 /proc/[0-9]*/maps 找 libdu
   命中后直接 dd /proc/<pid>/mem
=> 彻底绕开「注入不上主进程」这个卡点。
   现在唯一的变量是【时机】。
```

## 三、★ 时间线证据（这是本轮最重要的发现）

```
dlopen_longwait.py（成功那次）：
    [    0s] 轮询开始
    [  256s] ✓ com.coolapk.market pid=30780 -> 命中 libdu

本轮各次尝试：
    libdu_persist.py  15 分钟（900 秒）：未命中
    proc_root_grab.py  8 分钟（480 秒）：未命中

⇒ 结论：库的加载发生在【清数据后 4~8 分钟】这个区间，
   而多数尝试在 100~480 秒就结束了 —— 结束得太早。
```

### 3.1 一个被证伪的假设

```
我曾认为「循环重启能提高命中率」—— 实际【相反】：
   · 循环重启版（12 轮 × 100s）：10 轮全部「可读段 0 个」
   · force-stop 打断了进程初始化，库根本没机会加载

⇒ 正确做法：清一次，然后【耐心等 15~30 分钟，全程不打断】。
```

## 七、教训（本轮最有价值的三条）

```
① 「循环重启」是反效果。
   我以为多次尝试能提高命中率，实际 force-stop 打断了初始化。
   ⇒ 面对「加载依赖初始化流程」的目标：不打断、长等待。

② 时间尺度必须匹配。
   库在 4~8 分钟才加载，而我把多数尝试限制在 100~480 秒。
   应当先做一次「只观察不干预」的长跑，测出真实时间线，再定策略。

③ 抓到模块 ≠ 抓完数据。
   「未完成」背后其实是三个小问题叠加（目录被清、段不可读、File API 差异），
   每修一个失败点就前移一步 —— 方向正确，只欠执行机会。
```
