## 一、★★★ 破解的字符串加密算法

### 1.1 解密例程（0x0DA3CC）

```asm
add   x9, x9, #<off>       ; 密文地址 = 0x14000 + off
mov   w10, #-<a>           ; 密钥 A（奇数位）
mov   w12, #-<b>           ; 密钥 B（偶数位）
loop:
ldrb  w13, [x9, x8]        ; 读密文[i]
tst   x8, #1               ; 位置奇偶
csel  w14, w12, w10, eq    ; 偶→B  奇→A
eor   w13, w13, w14        ; XOR
cmp   x8, #<len>           ; 长度
strb  w13, [x11, #-1]!     ; 倒序写入
b.ne  loop
```

```python
def decode(data, addr, kA, kB, length):
    enc = data[addr:addr+length]
    return bytes(enc[t] ^ (kB if t%2==0 else kA) for t in range(length))[::-1]
```

### 1.2 三个关键点（都是"读出来"的，不是试出来的）

```
① 密钥【按位置奇偶】交替：偶数位 kB、奇数位 kA（`csel ..., eq` 决定）
② 明文【倒序写入】缓冲区（`strb w13, [x11, #-1]!` 的 #-1! 是 pre-decrement）
③ 密钥对【逐字符串各自指定】（已见 8 组，写在各自调用点前的 mov 里）
```

**⇒ 这解释了此前所有失败：任何「一套密钥通吃」的尝试必然错。**

### 1.3 已解出的真实字符串

```
'sys.usb.vserialno'       ← USB 虚拟序列号（模拟器检测）
'ro.microvirt.hmac'       ← MicroVirt 模拟器特征
'persist.nox.wifimac'     ← Nox 模拟器 WiFi MAC
'nemud.player_uuid'
'/storage/emulated/0'
```

**⇒ 全部是模拟器检测 + 设备属性读取路径 —— mIS 的输入域。**

## 二、★★★ 打通的调用链

```
① 驱动函数 0x07DBEC
     采集设备属性的核心（6144 字节 / 1536 条指令 / 42 次 bl）
     其中 13 次 bl 指向属性解码器
     特征：开头大量 adrp+ldr 初始化上下文；栈 720 字节
        ↓
② 属性解码器 0x0DA388 ~ 0x0DABC0（13 个）
     每个内联一段「解密循环」，解出一个属性名
        ↓
③ 属性名（getprop 系列：ro.* / persist.* / sys.*）
        ↓
④ 属性名哈希 -> 分派表 0x1143BC
     这是一张【二分查找 switch】：
        mov w14,#0x6d9c; movk w14,#0x4c48,lsl#16   -> 32 位 case 常量
        cmp w9, w26; b.le ...; cmp w9, w21; b.gt ...  -> 二分
        b.eq <handler>
     ⇒ 每个属性名对应一个 32 位哈希，按哈希跳转到取值 handler
        ↓
⑤ 取值（bl 0x152F80 —— 系统属性读取链）
        ↓
⑥ 结果存入 bss 槽（0x162DC8 / 0x162DB0 / 0x162DB8）
        ↓
⑦ ??? -> 汇总 -> 编码 -> mIS     （待打通：最后一段）
```

### 2.1 关键函数清单

| 地址 | 作用 | 判据 |
|---|---|---|
| **`0x1143BC`** | **属性名哈希分派表**（二分 switch） | 32 位 movk 常量 + `cmp/b.gt/b.eq` 二分 |
| **`0x152F80`** | 按名字取值（getprop 链） | 在 0x0DAF70 处被调 |
| **`0x0DAF78`** | 注册回调 `str x0,[0x162DC8]` | 见反汇编 |
| `0x13FE10` | 返回计数并与 28 比较 | `cmp w0, #0x1c` |
| `0x0DB078` | 初始化入口（置 0x162DD8=1） | |
| `0x0DCBE8` | **`strdup`**（已识别） | strlen+malloc+memcpy+strb 0 |
| `0x114B54` | 疑似「启动采集」 | 紧跟初始化之后被调 |

### 2.2 一个重要发现：带 tag 的指针

```asm
0DAF60  and   x0, x8, #0xfffffffffffffffc    ; 清低 2 位
```

**⇒ SDK 内部使用【带 tag 的指针】（低 2 位存类型标记），
   类似 JSValue / 变体类型。说明它有一套自己的值表示层。**

## 四、★ 最后一段怎么打（具体做法）

```
已有交汇点：
  · 驱动函数 0x07DBEC 的尾部（0x07F000~0x07F3EC）
    —— 13 次取属性之后，就是「汇总」的代码
  · 0x1143BC 的 handler 分支（b.eq 目标）—— 每个属性的取值实现
  · bss 槽 0x162DC8/0x162DB0/0x162DB8/0x162DC0/0x162DD0

做法（按顺序）：
  1) 反汇编 0x07F000~0x07F3EC（驱动尾部）
     看 13 个属性值如何被处理 —— 拼接？逐个喂 hash？
  2) 找「长度 36」的常量（mIS 是 36 字符）：
     搜 `cmp wN, #0x24` / `mov wN, #0x24` 附近的字符串构造
  3) 找编码函数：36 字符 + 62 种字符集
     ⇒ 可能是一个自定义 base64 变体（字母表 64 项，其中 2 项不用）
  4) 交叉验证：把 mIS 的字符集统计（62 种）与候选编码函数的输出对比

★ 现在动态也变得可行且精确了：
   库一加载，读 bss 槽（0x162DC8 + 模块基址）就能拿到真实回调地址，
   在那里下断点 -> 直接看调用栈 -> 定位 mIS 生成点。
   （这比之前"盲扫内存找 36 字符串"精确得多）
```

## 六、教训汇总

```
① 「反汇编里读出来的事实」> 「试出来的」
   写入方向（#-1! = 倒序）、密钥选择（csel eq = 偶数位用 w12）——
   都在一条指令里写着。我试了两轮才去看汇编。

② 「找不变量」比「找调用者」有效
   解密函数没有 bl 调用者（三条判据全 0）。
   换方向找「谁批量调用它们」—— 在 779 个函数里精准命中 1 个驱动函数。

③ 函数地址聚集是强信息
   13 个解码器集中在 0x0DA388~0x0DABC0；紧邻的 0x0DAF78 就是「注册/取值」。
   编译期把相关代码放一起 —— 这个规律可直接用于定位。

④ 位运算要停下来看
   `and x0, x8, #0xfffffffffffffffc` 一眼看出是带 tag 指针，
   立刻知道 SDK 有自己的一套值表示层。比继续翻指令更有价值。

⑤ 小样本 + 决定性检验 > 大量尝试
   「两段 key 取模对齐」一次就否定了固定密钥假设，比试 256 个 key 更有力。

⑥ 换机制优于改脚本
   前面 15 种动态方法都在绕「库加载时机」这个不可控因素；
   换成静态分析后，进展是可控的、每步都在缩小范围。
```
