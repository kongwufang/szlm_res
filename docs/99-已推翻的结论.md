## 1. `mIS` 是"唯一钥匙" ⚠️ 最有误导性的一条

### 当时怎么想的

```
✗ 已作废的推理

用真实设备抓到的 body 逐字段扫描 87 个字段：
  · mIS 换成另一个已知值（dLH 的值） → 返回【另一个 DUID】
  · mIS 自造 36 字符串               → 全 0
⇒ 判断：服务端按 mIS 查表，mIS 就是这个"逐设备唯一"的东西
```

**这个结论当时写进了多份文档**，并在此基础上做了大量后续推断
（"mIS 的算法是核心目标"、"需要解出 36 字符混淆串"……）。

### 为什么当时看起来成立

`mIS` 确实能改变结果 —— 这一点是真的。问题在于**它是唯一被验证能改变结果的字段**，
于是被误当成了**唯一有用的字段**。

### 错在哪

```
扫描时【一直保持 mIS 为真值】——
那个真值足以命中记录，把其它所有字段的作用统统遮蔽了。

⇒ 典型的观测设计缺陷：被观测的量掩盖了要找的量
```

**换句话说**：每次测试都带着一把"正确的钥匙"，那当然测不出其它字段有没有用。

### 怎么推翻的

**先把 `mIS` 随机化，再逐字段扫描。**

```
基线 = mIS 随机 + ubF 清空
逐字段改哨兵值，看 n_a 何时变全 0

结果：mIS 换成任意合法 36 字符串 → 服务器照样返回真 DUID
```

补充证据 —— 把 `mIS` 随机化后，**其余 72 个字段完全随机化**，仍然返回真 DUID：

```
只留 6 个锚点字段，其余全随机 → ★★★ 仍返回真 DUID
```

### 正确结论

```
真正的锚点 = (sfOo, foO, 2cO) 三元组
mIS        = 与设备识别【无关】
```

### 影响范围

| 受影响的旧文档 | 处理 |
|---|---|
| 所有 `mIS_*` 系列 | 已归档到 `docs/_archive/`，**内容已作废** |
| 基于"mIS 是核心"的后续推断 | 同上 |

**⚠️ 读归档文档时，凡涉及 `mIS` 是"唯一钥匙 / 判据种子"的表述，一律以本文为准。**

## 2 & 3. `sfOo` / `foO` 是"可删的混淆串"

### 当时怎么想的

```
body 里有 16 个长得差不多的混淆串（mIS / yzW / zvW / 5Tv / 52J / Bos / IJK / …）
既然 mIS 是"钥匙"，剩下的自然被归为"干扰项"，且测试过删掉它们不影响结果。
⇒ 判断：sfOo / foO 也是可删的混淆串
```

### 错在哪

**删掉不影响** ≠ **改掉不影响**。

服务端对**缺失**字段可能是宽容的（走默认路径），但对**给出了错误值**字段会严格比对。
更关键的是：当时的测试方法（保持 `mIS` 为真值）让这些字段的作用根本显不出来。

### 怎么推翻的

用**同类型的另一个合法值**替换（而不是删除），才区分得开：

```
sfOo → 另一个 7 位 hex        → 全 0  ★ 真锚点
foO  → 另一个 15 字符混淆串    → 全 0  ★ 真锚点
2cO  → 另一个合法"秒.纳秒"     → 全 0  ★ 真锚点
DUv  → 另一个包名             → 全 0  ★（已知必需）

对照：mIS → 另一个 36 字符串    → 仍返回真 DUID（无关）
```

**注意这个方法上的差别**：如果不是用"同类型合法值"而是用"哨兵串"，
可能因为**格式不符**而全 0，从而误判为"真锚点"。这是第二次要避的坑。

### 正确结论

```
必需 / 真锚点：DUv, 3mS, 75c, 2cO, sfOo, foO
与识别无关：  mIS, 以及其余 72 个字段
```

## 4. `2cO` 的子秒是"固定设备键"

### 当时怎么想的

```
同一设备保留 2cO 子秒 → 通过
同一设备换掉 2cO 子秒 → 全 0
⇒ 判断：2cO 的子秒部分是【固定的设备键】
```

### 错在哪

把「**必须与某条已存记录一致**」误读成了「**在设备上是固定的**」。

### 怎么推翻的

```
18 个跨 11 天的真实样本：2cO 有 17 个不同值
⇒ 它每次都变，不可能"固定"
```

### 正确结论

`2cO` 是**那一次注册**产生的值，服务端为每一次注册都记了一条
`(sfOo, foO, 2cO) → 设备` 的映射。
所以拿其中**任意一条**去查都能命中 —— 但拿一个**没记录过的新值**就会全 0。

## 5. `75c` 是"设备级主键"

### 当时怎么想的

```
75c 跨端点取值相同、跨 95 分钟相同 ⇒ 像是"设备级唯一标识"
而且删掉它会失败 ⇒ 判断是主键
```

### 错在哪

两个误读：

1. **跨端点/跨时间相同** → 说明它是**常量**，恰恰不支持"逐设备唯一"
2. **"删掉失败"** → 实际测试的是"给了错误值"，不是"删掉"

### 怎么推翻的

```
dump 里的 75c  = 11e7b222083a4b732b4b14811f6fc05995a01415eb
官方 SDK 源码里 API_KEY = 同一个字符串
⇒ 逐字符相同 ⇒ 是硬编码常量
```

并且实测：**缺省 / 空 / null 都能通过**；只有"给了值但不等于 apiKey"才失败。

### 正确结论

```
75c = apiKey 常量
    = 可以省略
    = 给了就必须精确匹配
```

## 6. "服务端做 URL↔body 完整性绑定"

### 当时怎么想的

```
改 body 里任一字节 → 请求失败
⇒ 判断：服务端把 URL 与 body 做了完整性绑定（类似签名）
```

### 错在哪

"失败"的原因不是绑定，而是**改到了必需字段**。
当时没做变量隔离，一次改多个地方。

### 怎么推翻的

逐项隔离测试：

```
p / r / n / l / h / t  → 各有 6~8 种变体，全部通过
HTTP 头               → 21 组变体，全部无影响
非必需 body 字段       → 逐字节改，无影响

⇒ 不存在 URL↔body 绑定
```

## 7. "除 `75c` 外几乎都可伪造"

### 当时怎么想的

在确定 `75c` 是 apiKey 之后，得出了"因此其它字段都可改"的结论。

### 错在哪

**推得太宽**。`75c` 是不是主键，和"哪些字段必需"是两个独立问题。

### 正确结论（约 100 次变体实测）

```
必须正确的只有 6 个：URL.v, DUv, 3mS, 2cO, AAA, 75c
其余 73 个 body 字段 + 5 个 URL 参数 + 全部 HTTP 头：不参与识别
```

## 8. "`mIS` 不可本地构造"

### 当时怎么想的

```
尝试了：固定 XOR / 单表代换 / 纯 base64 / 位置密钥流 /
        哈希候选 / 字母表穷举 —— 全部失败
⇒ 判断：mIS 不可本地构造，必须由服务端下发
```

### 错在哪

**把"我们穷举失败"当成了"在数学上算不出来"。** 这是两回事。

而且有一条**逻辑上的必然性**被忽略了：

```
pm clear 之后本地零状态 → libdu 不知道自己是新设备还是老设备
→ 它只能把【能标识本机】的信息放进请求
→ 服务端据此认出设备，返回同一个 DUID
⇒ 请求里必然存在【本地可重算的设备标识】
```

**⇒ 只要 DUID 在清数据后不变，那个标识就一定是本地算出来的。**

### 正确的表述

```
不是「不可能本地构造」，而是「我们还没找出构造方法」
```

（而且后来发现承这个职责的其实是 `(sfOo, foO, 2cO)`，不是 `mIS`。）

## 9. "`adt` / `daa` 线的加密未解"（假缺口）

### 当时怎么想的

从抓包数据里看到 `adt` / `daa` 端点的 body 解不开，就把它列为"未解缺口"。

### 错在哪

**没有重读已有文档。** 实际上这两条线的加密方式**早就解出并记录过**了，
只是当时的分析脚本用错了池常量。

### 怎么发现的

按项目自己的规则（动手前先读文档）回头核对，发现文档里已有结论，
实测验证也通过 —— **这是一条我自己造出来的假缺口**。

### 正确的做法

**在把某件事列为"未解"之前，先确认它不是"已解但被自己忘了"。**

## 10. "150+ 设备指纹字段是核心成果"

### 当时怎么想的

花了很多精力枚举并记录 body 里的设备指纹字段（机型、厂商、MAC 三元组、
内网 IP、语言、已装应用列表、系统字体清单……），把它们当成项目的核心产出。

### 错在哪

**服务端一个都不读。**

### 怎么推翻的

把整类字段一起随机化，结果毫无影响：

```
5 个哈希（K5f/ne8/w91/gEd/6yY）整类随机化    → 仍返回真 DUID
15 个混淆串整类随机化                         → 仍返回真 DUID
4 个嵌套对象整类清空                          → 仍返回真 DUID
设备属性（MAC/机型/内网 IP/hosts）整类随机化   → 仍返回真 DUID
时间戳整类随机化                              → 仍返回真 DUID
```

### 教训

**"协议里有这个字段" ≠ "服务端用它"。** 必须用变量隔离实验确认，
不能看到丰富的数据就认定它重要。

## 11. "frida 挂着时 `adb input tap` 失效"

### 当时怎么想的

观察到点按没生效，就归因为"frida 占用了输入通道"，
并据此写了一堆 `performClick` / 反射调用的后备逻辑。

### 错在哪

**归因错误**。真正的原因是**按钮坐标变了**（页面状态变化），
而当时用的是缓存的坐标。

### 怎么推翻的

直接测量：点按前后对比 `shared_prefs` 文件数

```
点按前 6  →  点按后 306     ⇒ tap 完全正常
```

### 正确做法

**每次点按前重新 dump UI，确认按钮在场才点。**
（这也顺带解决了"误点《用户协议》链接跳浏览器"的问题。）

## 12. 池常量：是"地址"还是"地址处的字符串"

### 当时怎么想的

文档里记了 `0x109CF0`、`0x110DC8` 这样的形式，被当成了**密钥值**。

### 错在哪

那些是**内存地址**。真正的密钥是**存放在该地址处的字符串**。

### 后果

所有解密尝试全部失败，白白绕了很久。

### 正确做法

```
✗ KEY = 0x110DC8
✓ KEY = "xp7j@&!v5]2k#+3z{n9$q^r%[8f1*d4e:c>0l?m/6)yb-=w}"
```

**⇒ 记笔记时，地址和内容必须写清楚，否则自己都会误读。**

## 从这些错误里提炼的教训

### 方法论层面

```
① 变体测试时，不要让待测字段携带"能独立命中目标"的真值
   —— 否则它会把其它字段的作用全部遮蔽

② "删除不影响" ≠ "替换不影响"
   要区分【字段缺失】和【字段值错误】这两种情况

③ 用"同类型合法值"替换，不要用哨兵串
   —— 否则会因格式不符而全 0，误判为"真锚点"

④ 一次只改一个变量，且做好隔离
   —— 否则分不清是哪个改动导致的失败

⑤ 说"未解"之前，先确认不是"已解但忘了"
   —— 重读自己的文档

⑥ 逻辑必然性 > 穷举失败
   —— "我们没算出来"不等于"算不出来"
```

### 记录层面

```
⑦ 中间结论必须标注【时效性】
   —— 一旦被推翻，要么改掉、要么明确标为作废

⑧ 地址与内容要写清楚
   —— 否则自己回头读都会误读
```
