## 一、类型约束表（87 个叶节点逐个测）

对每个字段做**换类型**（字符串→数字 / 数字→字符串），看是否被 400 拒：

```
类型敏感（换类型就 400）   76 个
类型不敏感（换类型仍 200） 11 个：
    Chh / nur / tth / G8U.MYA / G8U.H4S / 5Tv / J7w
    / fPV / msg.custom / za7 / fxb
```

### 1.1 ★ 结论：JSON 类型必须逐字段精确保持

**⇒ 要构造一份被接受的请求，必须保留每个字段的原始类型。**
这解释了 `minimal_body_probe` 变体②的 400：那轮把 19 个字段改成字符串，
其中任何一个类型不符都会 400。

### 1.2 附加边界（都已实测）

| 测试 | 结果 |
|---|---|
| 追加一个多余字符串字段 | 200，**真 DUID**（多余字段被忽略） |
| 追加一个多余数字字段 | 200，真 DUID |
| 追加一个多余**嵌套**字段 | 200，真 DUID |
| ⇒ **未知字段不会导致失败** | 服务端反序列化是宽松的 |

## 二、★★ 曾经的「体积闸门」是误判 —— 真因是 `mIS` 字段

### 2.1 走过的弯路（记下来，因为它很像真的）

```
观察：只留 5 个必需字段          -> n_a 全 0
      加回 40 个真机原字段        -> n_a 真 DUID
      ⇒ 当时判断为「请求太稀疏就拒」/「体积闸门」

验证 A：加 205 个极短字段（body 446 字节）      -> 仍全 0   ✗ 排除「字段数」
验证 B：加 1 个 1600 字符长值（解压 2991 字节）  -> 仍全 0   ✗ 排除「body 大小」
验证 C：只用真机原字段加回                      -> 通过      ★ 与内容有关
```

### 2.2 二分定位到单个字段

```
以「必需 5 个」（全 0）为基线，逐个加回真机字段：

  必需 + mIS      -> ★ 真 DUID（6 个字段就够！）
  必需 + R3d      -> 全 0
  必需 + AYk      -> 全 0
  必需 + LAh      -> 全 0
  必需 + K5f      -> 全 0
  必需 + ne8      -> 全 0
  必需 + yzW      -> 全 0
  必需 + iYB      -> 全 0
```

反向验证（从「刚好通过的 45 字段基线」里逐个删）：

```
删 mIS   -> 全 0     ← 唯一
删其它 39 个 -> 真 DUID
```

**⇒ 功能必需字段是 6 个：`AAA` / `BBB` / `3mS` / `DUv` / `2cO` / `mIS`**

### 2.3 更正后的完整集合

```
结构必需（删了 n_a 变空）        AAA、3mS
值必需（值不对就全 0）           DUv、BBB、2cO
★ 功能必需（缺了就全 0）         mIS          ← 本轮新增
其余 72 个                       删掉、改 1 字符都不影响
```

最小可用 body = **6 个字段**（body 压缩后约 97 字节）。

## 三、★★★ `mIS` 的值是判据种子（已实测）

### 3.1 键名要求

| 键名 | 结果 |
|---|---|
| `mIS` | 真 DUID |
| `MIS` | 真 DUID |
| `mis` | 真 DUID |
| `mISx` / `xmIS` / `mI` / `IS` | 全 0 |

**⇒ 键名匹配是大小写不敏感的，但不接受前后缀。**

### 3.2 值要求

`mIS` 原值：

```
"W(W(\\&&&T+\\Z*)W&\\QT*ZTX'Q\\TQ*X')&&Q)"      长度 36
```

| 值的变体 | 结果 |
|---|---|
| 原值 | 真 DUID |
| 空串 / `"0"` / `"a"` | 全 0 |
| 改 1 个字符 | 全 0 |
| 反转 | 全 0 |
| 原值的 MD5 | 全 0 |
| 同长度全 `A` | 全 0 |
| **去掉反斜杠** | **全 0** |
| **去掉引号** | **真 DUID** |

**⇒ 值必须精确匹配（引号不影响，反斜杠有影响）。**

### 3.3 ★★ 意外发现：值是一个「种子」，服务端拿它派生 DUID

把 `mIS` 的值换成**另一个混淆串 `dLH` 的值**（同为 36 字符）：

```
mIS = dLH 的值  ->  n_a = DUnkGC0m8phaJExl5EHNnMnt5YNydzbH_3g0
                    ★ 不是全 0，而是【另一个 36 字符的 DUID】
```

进一步测：

| 种子 | 结果 |
|---|---|
| 原值 | `DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9`（已知手表 DUID） |
| `dLH` 的值 | `DUnkGC0m8phaJExl5EHNnMnt5YNydzbH_3g0`（★ 新的） |
| `dLH` 的值（连发 3 次） | **三次完全相同** ⇒ **确定性派生** |
| `dLH` 的值大写化 | 同一个 `DUnkGC0…` ⇒ 大写归一化后同一种子 |
| `dLH` 的值改 1 字符 | 全 0 |
| `dLH` 的值反转 | 全 0 |
| `zvW` / `5Tv`（32 字符）的值 | 全 0 |
| `Bos` / `IJK`（41 字符）的值 | 全 0 |
| 自造：36 个 `0` / 36 个 `A` / `DU`+34×`a` / 长度 35 / 37 / 空 | **全部全 0** |

### 3.4 从 3.3 得到的三条

```
① `mIS` 的值 = 【设备标识种子】：换成另一个 36 字符的已知串，就能拿到另一个 DUID
② 派生是【确定性】的（连发 3 次一致），不是每次随机
③ 服务端只认【它记录过的种子】—— 自造的任意 36 字符串一律全 0
```

### 3.5 关系排查（未命中）

## 四、★ 这与「缺口 1（核心矛盾）」的关系

`FIELD_CRITERIA.md` §九 与 `SESSION_SUMMARY_AND_GAPS.md` 缺口 1 记录的核心矛盾是：

```
服务端返回逐设备唯一的 DUID，但请求里找不到设备标识
```

**本轮的 `mIS` 发现指向一个可能的解释**：

```
`mIS` 的值本身就是一个「设备标识」——
服务端按它查表/派生 DUID。
真机发的 `mIS` 值是原生层算出来的（对应本机手表）；
我们回放时照抄了那个值，所以拿到手表的 DUID。
三星设备发的是另一个 `mIS` 值，所以拿到 DUnkGC0…
  （注：三星那个值我们没有，上面用的是 dLH 的值做演示）
```

**若这条成立，则**：

```
· 「设备标识」确实在请求 body 里（就是 mIS 的值）
· 之前的 sweep 之所以没测出来，是因为：
    - 只改【值】→ 它变成未知种子 → 全 0（被误判为「该字段不生效」）
    - 只用【哨兵值】→ 同样是未知种子 → 全 0
    - 单独【删】→ 缺了必需字段 → 全 0
  ⇒ 三种改法都导致「全 0」，所以看起来像「这个字段无关」，
    实际上是「改了就从「已知种子」变成「未知种子」」
```

**⇒ 这是本轮最重要的修复**：把 `mIS` 从「73 个无关字段」里纠正出来，
并指出**它就是那个「逐设备唯一」的东西**。

### 4.1 待验证（下一步最有价值）

```
① 找出 mIS 的值与原生的关系
   `mIS` 的真机值 = "W(W(\&&&T+\Z*)W&\QT*ZTX'Q\TQ*X')&&Q)"
   它是不是 native 某处的输出？长度 36、含转义字符
   ⇒ 静态侧可在 libdu.so 里找这个字符串的构造点（用已知值反查）

② 用 D1 的抓包验证：D1 发的 mIS 值应该与 D2 不同
   ⇒ 这能一次同时解决「缺口 1」与「D1 的实抓」

③ 逐字符测试 dLH 那个种子的敏感性
   （已知改 1 字符就失败 —— 说明服务端是【精确查表】而不是【模糊匹配】）
```

## 五、脚本清单

| 脚本 | 作用 |
|---|---|
| `type_constraint_probe.py` | 87 字段的类型约束表 + 多余字段/嵌套字段边界 |
| `decoy_probe.py` | 整组删除（找「不能一起少」的字段） |
| `threshold_probe.py` | 二分找临界点（曾误判为体积闸门） |
| `gate_probe.py` | 隔离字段数 vs body 大小（两个都排除） |
| `gate2_probe.py` | 隔离解压后 JSON 大小（排除） |
| `real_field_probe.py` | **真正定位到 `mIS`** |
| `mIS_derive_probe.py` | **验证 `mIS` 值是设备标识种子** |

**方法论**：这一轮又犯了「把相关性当机制」的错 ——
「加够字段就通过」看起来像体积闸门，实际是「恰好加回了那个关键字段」。
**修法**：定位到单个字段后，必须做**反向验证**（从通过的基线里逐个删），
两边都指向同一个字段才算定性。这已在 `real_field_probe.py` 里固化成 ③/④/⑤ 三步。
