# 「mIS 是否由服务端下发」的验证 —— 结果

> 日期：2026-10-03 ｜ 设备：D3 LineageOS GSI
>
> **两条路径都做了：prefs 侧**给出否定证据**；网络侧因抓不到请求而未能完成。**

---

## 一、★ prefs 侧验证（已完成，结论明确）

`mis_in_prefs.py` 扫设备上**全部 314 个 prefs 文件 / 3413 个键值对**：

```
① 明文搜索：已知的 6 个 mIS 值 + 5 个特征片段（JQyPE / BrBrG / TMP"OU / qsp / LLEKIMMKHL）
   -> 0 命中

② base64 多层解码（最多 3 层）后再搜
   -> 0 命中

③ 广义搜索：所有 base64 层里找「36 字符、字符集像 mIS、字符种类 >12」的串
   -> 20791 个候选，但都是别的编码数据（如 '#10;+3iIx6WaF+WJ5rGyNFdJCK9vIzCWt+B/' 这类）
      没有一个与已知 mIS 样本吻合
```

**⇒ 结论：mIS 不与其它配置一起落盘。**

这条否定了「服务端下发后 SDK 把它存进 prefs」这个常见模式。

## 二、网络侧验证（脚本就绪，但抓不到请求）

### 2.1 脚本做了什么

`mis_in_response.js`：

```
① 钩 deflate / compress / compress2 —— 请求的【明文 body】在这里出现
   从中用正则 /"mIS"\s*:\s*"([^"]+)"/ 提取 mIS 值 M，并打印它的上下文
② 钩 SSL_read / SSL_write —— 把之后收到的【所有响应】过一遍，搜 M
   命中就落盘（RESP_HITMIS），并报警
③ 另做宽松匹配：响应里是否出现 M 的前 8 字符
④ 每 20 秒心跳一次，报告 misValue / respStore 状态
```

### 2.2 执行结果

```
[ok] zlib 3 钩子 / TLS 已挂
（150 秒内：无 "提取到 mIS"、无心跳、无命中）
```

**⇒ 钩子装好了，但这一次「应用初始化后重启」没有触发 SDK 上报** ——
与前面几轮一致（mdna 的触发问题）。

### 2.3 为什么没完成

```
mIS 只在 SDK 初始化 / 注册流程里出现，而这条流程：
  · 删 dna.xml -> 触发的是别的路径（daa），不是 mdna
  · pm clear + 冷启动 -> 不触发上报
  · 单纯重启 -> 不触发
  · 上报周期（itime=604800=7 天）没到 -> 不发
⇒ 这是整条线【共同且唯一】的瓶颈
```

## 三、★ 现有证据的综合判读

```
支持「mIS 由服务端参与生成」的证据：
  ① 自造 mIS 全 0，服务端按它查登记表（mis_2co_matrix 实测）
  ② 同设备每次注册的 mIS 都不同 ⇒ 不是「设备 → mIS」的确定函数
  ③ mIS 不落盘（本轮 3413 键值对 × 3 层 base64 全扫，0 命中）
  ④ 不在响应里、不是 Java 字段、不在任何 80 个候选类里
  ⑤ 字符集 62 种、位级无固定位、明文判为高度随机 ⇒ 像哈希/加密输出

支持「客户端生成」的证据：
  ① mIS 出现在【请求】里（是客户端发出去的）
  ② 它是每批重算的（同设备不同注册不同值）

⇒ 综合：mIS 是【客户端在注册时产生、并立刻上报给服务端登记的一个标识】。
   服务端把它记下来，之后的请求用它查表。
   若如此，客户端【有】生成它，但生成过程含【随机数或服务端参与的一次性数据】，
   所以无法凭设备特性/签名复现。
```

## 四、★ 结论

```
对「普通用户自己算 mIS」这个目标：
  不可行 —— 无论它是服务端下发还是客户端含随机成分生成，
  都不存在「从设备特性/签名推导」的路径。

对「把 mIS 抓下来复用」这个方向：
  技术上可行（就是抓包），但需要一次成功的注册期抓包，
  而这条一直卡在触发上。
```

**唯一还值得做的，是把「网络侧验证」补完** —— 它能把最后这个不确定性消掉：

```
需要：一次成功的注册期抓包（mdna 请求 + 之后的响应）
成本：低（脚本已就绪 mis_in_response.js）
障碍：触发时机（不是技术问题，是等周期）
建议：把 D3 保持已注册状态搁置，隔几小时挂一次钩子（脚本可以直接复用），
      撞到周期就自动得出结论。
```

## 六、教训

```
① 「扫 3413 个键值对 × 3 层 base64」这种穷尽式验证，成本比想象的低
   （一条命令级脚本），但结论很硬 —— 值得优先做这类「能直接否定」的验证。

   与其继续换脚本，不如接受「等周期」这个现实，用长驻钩子撞运气。

③ 把「结论」和「未完成的部分」分开写，比含蓄表述更有用 ——
   prefs 侧是确定否定，网络侧是未完成，两者价值不同。
```
