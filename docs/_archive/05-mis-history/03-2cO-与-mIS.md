# 路 A / 路 B 结果：mIS 与 2cO 的最终判定

> 日期：2026-10-03 ｜ 主力设备：D3 LineageOS GSI
> **结论：`mIS` 与 `2cO` 都是「服务端登记过的精确值」，不能本地构造。**

---

## 一、★★★ 决定性实验：2×2 矩阵（`mis_2co_matrix.py`）

| 用例 | 结果 |
|---|---|
| ① `mIS`=原值　`2cO`=原值 | **★ 有效 DUID**: `DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9` |
| ② `mIS`=原值　`2cO`=换子秒 | 全 0 |
| ③ **`mIS`=自造A**　`2cO`=原值 | **全 0** |
| ④ **`mIS`=自造B**　`2cO`=原值 | **全 0** |
| ⑤ **`mIS`=自造C**　`2cO`=原值 | **全 0** |
| ⑥ `mIS`=自造A　`2cO`=换子秒 | 全 0 |
| ⑦ `mIS`=36 个 X　`2cO`=原值 | 全 0 |
| ⑧ `mIS`=36 个 0　`2cO`=原值 | 全 0 |
| ⑨ `mIS`=36 个 !　`2cO`=原值 | 全 0 |

自造的 mIS（36 字符、同一字符集、随机）：
```
'%p!M4aFe/qSdH($w^R1s2qc)x>i`4?HMtL&B'
'9cz&J[P&:,yKm{GH\=2dJUv4Id;IA91dg&h,'
"c8X#I%z>@h~{-ua'VabdAeLmWCz-7$K(r>a;"
```

**⇒ 结论（铁）：**

```
mIS 必须是【服务端登记过的精确值】—— 自造的合法值一律全 0。
配合此前测出的「2cO 子秒也必须是登记过的值」：

    2cO 子秒  ->  哪台设备的记录
    mIS       ->  那条记录下的哪次注册

两者【都要登记过】，服务端才回 DUID。
```

## 二、★ 由此解释了之前所有「反常」结果

### 2.1 为什么同一份请求会返回不同的 DUID

```
同一设备（XTQ_Watch）的 5 个样本，mIS 各不相同：
  JQyPE~yLLEKIMMKHL{~}OHQJEy}P}E{HI|~|
  TMP"OU"Q#JM#P"VRNQ"JQVTNJ~VUNS#~UVJ!
  BrBrGppp?uGEtsBpG<?tE?Cq<G?<tCqspp<s
  R$R$…（另一批）
  …

每个 mIS 对应服务端一条独立记录 ⇒ 该设备名下有多条注册记录。
⇒ repeat_probe 里 A 组（完整 body）与 B 组（最小 body）拿到不同 DUID，
   就是因为它们的 mIS 不同，服务端返回了不同记录 —— 两个都是【有效 DUID】。
```

### 2.2 为什么「自造 mIS」被拒

```
服务端是【查表】：mIS 不在表里 -> 拒绝（全 0）。
这就是 c001apk 七轮实验全部拿 0 的机制。
```

## 三、`mIS` 的性质汇总（本轮全部证据）

| 性质 | 证据 |
|---|---|
| 长度 36，字符集 72 种（0x21~0x7E） | 6 个样本统计 |
| **每次注册/每批重新生成** | 同设备 5 个样本，5 个不同的 mIS |
| **必须是登记过的值** | 自造 A/B/C + 36 个 X/0/! 全部全 0 |
| **不是 XOR 编码** | 同一样本内 `T→(` 与 `\→&`，而 `T^\=0x08` ⇒ 违反双射 |
| **不是单表代换** | 同一样本内 `'3'` 在位 9/19/24/34，输出各不相同 |
| **不是纯 base64** | 字符集 72 种 > 64 |
| **位置密钥流也解不出** | 三种明文假设下，唯一确定的位置只有 2/4/0（共 36） |
| **不在 prefs 落盘** | 33 个云控键 + 3790 个键名全扫过 |
| **不是 Java 字段** | 80 个候选类扫过，无命中 |
| **不在响应里** | 响应只有 `err/n_a/nctl/cdd/dlab/isem/itime` |

## 四、★ 对「普通用户自己算」的最终判定

```
❌ 不可行。

原因：mIS 与 2cO 子秒都是【服务端登记过的值】，不存在「本地构造」的算法 ——
      它们不是从设备特性/签名推导出来的，而是【注册那一刻被服务端记下来的】。

      「改设备特征让 mIS 变」这个实验（路 A）也就失去意义：
      它不是函数关系，而是「登记记录」的关系。
```

### 4.1 那「普通用户」到底能怎么拿到 DUID

```
在【已 root】的设备上：
  直接读 /data/data/com.coolapk.market/shared_prefs/com.coolapk.market_dna.xml
  的 <device_id>，或 coolapk_preferences_v7.xml 的 <SHUZILM_DID>
  —— 这是唯一不依赖服务端的路径（前面已实测成功，三台都读到了）

在【未 root】的设备上：
  没有可行路径 —— 除非：
    · 设备已装了官方酷安 且 c001apk 与它共享 uid（需要签名一致，做不到）
    · 或从系统备份/云同步里取出（取决于是否备份了 app 数据）
```

## 五、路 A 与路 B 的执行情况（如实记录）

### 路 A（改设备特征）—— **因结论已明确而中止**

```
· 先做了「跨样本对照」：同设备 5 个样本的 mIS 各不相同
  ⇒ mIS 不是设备固定值，改特征「跟着变」的假设不成立
· resetprop 可用性已确认（/sbin/resetprop，D3 上）
· 中止理由：既然 mIS 是「登记记录」而不是「设备特性的函数」，
  改特征不会给出新信息
```

### 路 B（动态取值）—— **尝试了两条路，都不通**

```
① 从外部读 /proc/pid/mem 扫内存
   ✗ app 反复重启、pid 一直变；dd 的 seek 不稳；扫 1008MB 无结果

② frida 扫内存（scan_mis.js）
   ✗ 可扫段 1335 个 / 2104 MB，JS 侧滑窗生成候选过多而超时
   （这个方法本身可行，只是需要限制窗口大小 + 分段回调）
```

**⇒ 路 B 如果要做，需要改进：**
```
· 只扫【堆】段（/proc/pid/maps 里带 [heap] 或匿名 rw 且小于 64MB 的）
· 滑窗改成「只在连续 ASCII 段正好 36 或按 36 切分」的固定步长，避免 O(n) 候选
· 候选分批回调，避免单次消息过大
```

## 七、教训

```
① 路 A 在执行【之前】就被数据否掉了 —— 这是好事。
   「同设备 5 个样本 mIS 各不相同」这一条，比花时间改特征跑一遍更省。
   做法：动手前先问「如果假设成立，应该观察到什么；现在数据里有没有反例」。

② 「mIS 是登记记录」这个结论解释了此前所有反常：
   A/B 组不同 DUID、自造值全 0、cx001apk 七轮全 0 —— 同一个机制。

③ 最终结论对目标是否定的（普通用户算不出来），
   但这是【有证据的否定】，价值高于继续猜算法：
   它把「不可能」的边界画清楚了 —— 只剩「读已授权的数据」这一条路。
```
