# `mIS` / `2cO` 逆向 —— 本轮实测结论

> 用户方向：搞清 `mIS` / `2cO` 由什么**设备特性或签名**构造，以便普通用户（无 root）自己算。
>
> 日期：2026-10-03 ｜ 主力设备：D3（性能最好）；样本含 D2 的历史抓包
>
> **本轮把 `2cO` 的性质钉死了；`mIS` 的性质也清楚了，但算法仍未解出。**

---

## 一、★★ `2cO`：时钟读出，但**子秒部分被服务端当作设备键**

### 1.1 它不是固定常量（33 个历史样本证伪了上一轮的结论）

```
纳秒值（14 个互不相同）：110947858 / 13589905 / 17322914 / 291441780
                        334705411 / 380034934 / 4675430 / 515532599 …
⇒ 2cO = 时钟读数（每次重取都变）
```

### 1.2 但服务端按【子秒】索引设备记录（同轮 6 组变体）

```
① 原值                              -> 通过
② 秒 +43200，子秒保留                -> 通过（与 ① 同一个 n_a）
③ 秒 +43200，子秒换成其它样本的值      -> 全 0
④ 秒 +43200，子秒 = 000000001        -> 全 0
⑤ 秒 +43200，子秒 = 999999999        -> 全 0
⑥ 秒 +43200，子秒 = 原值 +1（末位）    -> 全 0
```

**⇒ 结论**：

```
· 2cO 由时钟读出 ⇒ 普通用户【本机能取】
· 子秒 = 设备标识 ⇒ SDK 在【首次注册那一刻】取一次，之后复用
· 整数秒可以漂 ±12 小时
```

**⇒ 对目标的意义（这是好消息）**：

```
用户设备上，2cO 的子秒是【本机可读的一个值】——
只要知道「哪一次采样被记录」，就能在无 root 的情况下复现。
它不需要逆向算法，只需要「同一台设备重复上报时子秒不变」——
而 33 个样本 + 6 组变体都支持这一点。
```

## 二、★★ `mIS`：每批重算，非设备固定值

### 2.1 同一台设备的两批样本，mIS 完全不同

```
批次 A（wire_m55_2 / m55_6）：  "BrBrGppp?uGEtsBpG<?tE?Cq<G?<tCqspp<s"
批次 B（wire_m55_8）：          "R$R!W$!SOLWW%"ROW%OLU!S$LUO&%!"!!#L#"
```

同一设备、同一 DUID、同一 `2cO` 子秒，**`mIS` 却不同**。

**⇒ `mIS` 不是设备固定标识，是每次 SDK 初始化重新算出来的。**

### 2.2 形态

```
长度都是 36；字符分布在 0x22~0x7E
像「27 字节二进制经 base64 变体编码」（27 → 36 正好是 base64 比例）
```

### 2.3 但它确实必需

```
只留 5 个必需（无 mIS）      -> 全 0
最小 6 + 36 个 X            -> 全 0
最小 6 + mIS = ""           -> 全 0
最小 6 + mIS = null         -> 全 0
最小 6 + 原 mIS             -> 稳定返回 B 值的 DUID
```

## 三、★★★ 本轮最关键的发现：服务端是**确定性的**，但会按 body 构造返回**不同记录**

### 3.1 重复性实验（各组连发 6 次，全部稳定）

```
A 完整原 body（78 字段）      -> DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9   (6/6 一致)
B 最小 6 字段 + 原 mIS        -> DU7oGVomxL6iRMnF6Ozl8Xq8VqlikBg1N_g7   (6/6 一致)
C 最小 6 字段 + 历史 mIS      -> 全 0                                   (3/3 一致)
```

**⇒ 服务端不是随机的，也不是缓存抖动 —— 它是按 body 构造确定性返回。**

### 3.2 从 B 补字段能把结果翻到 A

从 B（6 字段）出发，逐个加回 A 的 72 个差集字段，结果呈现**清晰分界**：

```
不翻（仍是 B 的值）—— 前 37 个字段：
    Qg1  LMi  Zrs  EV2  SAN  h6Z  R41  R5a  R53  R63  QgA  qH9
    iZS  ZZA  S6e  90P  YWu  bzt  5mZ  0KQ  Chh  Xl9  D32  LAh
    wlM  nur  tth  c2O  PV8  yzW  AYk  P1J  R37  R3d  K5f  GVp  iYB

翻到 A —— 从第 38 个字段起：
    7S2  ne8  sfOo  foO  w91  G8U  zvW  gEd  5Tv  52J  Bos  IJK
    ura  ibF  IAI  aFw  KyU  6yY  UOv  JPd  J7w  zpA  bf7  wSK
    fPV  Db2  QVn  msg  dLH  4VP  za7  …
```

**⇒ 这个分界不是随机的：**

```
· 前 37 个 = 设备/环境类字段（时间戳 Qg1/LMi、机型 R3d/R37、MAC AYk/P1J、
             网络 YWu/wSK、语言、安装信息 …）
· 第 38 起 = 大量【混淆串】（sfOo/foO/zvW/g8U/52J/Bos/IJK/dLH …）

⇒ 加一个「混淆串」字段，就能让服务端改判到 A 那条记录
```

### 3.3 这意味着什么

```
服务端持有【按设备多条记录】，用 body 的构造（哪些字段在）来决定返回哪一条。
· 完整 body（真实上报）  -> A（DUFPnec5…）
· 最小 body（我们构造）  -> B（DU7oGVom…）
两者都是【有效 DUID】—— 区别只是服务端返回了哪条记录。
```

## 四、★ 对「普通用户自己算」的可行性判断

### 4.1 已经成立的

```
· 2cO 的子秒是【本机可取】的设备值（不需要逆向）
· 加一个混淆串字段就能把结果控制到 A 那条记录（可控）
· 服务端行为确定性（可复现、可调试）
```

### 4.2 还没解出的

```
① mIS 的算法 —— 36 字符、每批重算、看起来像「27 字节 → base64 变体」
   需要找到：那 27 字节从哪来（设备特性？签名？时间？）
② 服务端「多条记录」的索引规则 ——
   为什么加混淆串会翻？是字段数量、还是特定键、还是键名长度总和？
   （本轮只做到「发现分界」，没做到「定性判据」）
```

### 4.3 建议的下一步（成本低、收益直接）

```
实验 1：把 3.2 的分界钉死
  不是「逐个加」，而是「按数量加」——
  从 B 出发，按顺序加 1、2、3…N 个字段，找【第一个翻到 A 的位置】。
  这能区分「数量阈值」与「特定字段」。

实验 2：mIS 的 27 字节还原
  把几个 mIS 字符串按「base64 变体」解码，看能否得到结构化的 27 字节
  （若能，就等于拿到了明文，可以直接找它的构造）
  ★ 关键线索：mIS 值都在 0x22~0x7E，且 36 字符 —— base64 的 64 个字符
    正好可以映射到这个区间上；试试建立映射表。
```

## 六、教训

```
① 上一轮我把「2cO 是固定种子」写进文档 —— 33 个样本一对照就证伪了。
   「常量/种子」这类结论，必须先做跨样本一致性检查。

② repeat_probe 与 which_field_probe 这两步（先验重复性、再验单字段）
   是必要的顺序：先确认服务端确定性，单字段实验才有意义。
   这次顺序做对了，所以 3.2 的分界是可信的。

③ 本轮没解出 mIS 算法，但把它的性质（每批重算、必填、形态）都定下来了 ——
   下一步有明确入口（base64 变体解码）。
```
