# `mIS` 算法逆向 —— 结果

> 日期：2026-10-03
> **结论：`mIS` 的编码算法静态解不出；但它「是什么」已经查清了。**

---

## 一、★ 先把「mIS 是什么」定下来（这是本轮最重要的澄清）

### 1.1 同一设备同一时刻，所有端点的 mIS 相同

```
szlm_report_1.bin  (mdna)  mIS = 'JQyPE~yLLEKIMMKHL{~}OHQJEy}P}E{HI|~|'
szlm_report_6.bin  (audd)  mIS = 'JQyPE~yLLEKIMMKHL{~}OHQJEy}P}E{HI|~|'
                          同一设备 (XTQ_Watch)、同一 2cO 子秒 (291441780)
```

**⇒ `mIS` 是「本次运行」的固定值，不随端点变。**

### 1.2 不同设备不同，同设备不同次注册也不同

```
XTQ_Watch    -> JQyPE~yLLEKIMMKHL{~}OHQJEy}P}E{HI|~|   (291441780)
XTQ_Watch    -> BrBrGppp?uGEtsBpG<?tE?Cq<G?<tCqspp<s   (17322914)   ← 另一次
NX809J       -> W[\Y''(X%S%%U'W&ZP)UXYU(PW[P*WSY&XP&   (380034934)
```

### 1.3 ★ 而且它确实是「服务端登记过的精确值」

```
mis_2co_matrix（上一轮，连发稳定）：
  mIS=原值  -> ★ 有效 DUID
  mIS=自造  -> 全 0（三个随机合法值 + 36 个 X/0/! 全部全 0）
```

### 1.4 ⇒ 合起来的定性

```
mIS = 「(设备, 本次运行)」对应的服务端登记标识
      · 每台设备每次注册有一个
      · 服务端按它查表；不在表里就拒绝
      · 它不随端点变，只随「设备 + 注册轮次」变

⇒ 它更像【服务端下发的会话/注册标识】，而不是「客户端从设备特性算出来的值」。
```

**这个定性直接决定了逆向策略**：如果它是服务端下发的，那客户端侧就不存在
「构造算法」可逆向 —— 能做的是找到**它的传输/存储路径**（而不是公式）。

## 二、静态穷举的结果（全部失败，但都记录了）

### 2.1 已排除的编码方式

| 假设 | 结果 | 依据 |
|---|---|---|
| 固定 XOR 密钥 | ✗ | 同一样本内 `T→(` 与 `\→&`，而 `T XOR \ = 0x08`，违反双射 |
| 单表代换 | ✗ | 同一样本内 `'3'` 出现在位 9/19/24/34，输出各不相同 |
| 纯 base64 | ✗ | 字符集 72 种（> 64） |
| 明文 XOR 位置密钥流 | ✗ | 三种明文假设下，唯一确定的位置仅 **2/4/0**（共 36） |
| 「候选输入 → MD5/SHA → base64」 | ✗ | 12 个候选输入 × 3 种哈希 × 3 种编码，**无匹配** |

### 2.2 位级分析（本轮的定量结果）

```
36 个位置，每一位的取值种类：5~6 种
每一位的「公共置位」= 0x7F（全部 ≤0x7F）
每一位的「公共清位」= 0x00 或某个单位（0x02/0x10/0x20/0x40）

⇒ 没有任何一位固定 ⇒ 整串都是动态内容，无魔数/版本/长度段
```

### 2.3 6 个样本的字符统计

```
用到 62 种不同字符（在 64 以内 —— 与 base64 的字母表大小吻合）
标准 base64 字符里【未出现】的: ADFefghijklmnovwxz3456789   （20 个）
出现的高频字符: Q X & P \ W J E p T U ~ ' M G ? < " V ( ) * …

⇒ 字母表被【打乱】过（用了符号，却少了常见的字母数字）
  这符合「自定义字母表的 base64 变体」，但字母表本身未知
```

## 三、★ 为什么静态解不出（诊断）

```
① 样本太少：6 个（而且来自 3 台不同设备 + 3 次不同注册）
   要解一个「36 字符、自定义字母表」的编码，理想上需要
   【同一明文的多个样本 + 已知明文】，才能建立映射表。

② 没有已知的「明文-密文对」：
   我们不知道 mIS 在编码【之前】是什么（可能是 27 字节二进制、
   可能是另一个字符串、可能是服务端下发的一段数据）。

③ 字符集 62 种、位级无固定位 ⇒ 无法用「找规律」的方式切分结构。

④ 本轮尝试的两条「动态取值」路径也没通：
   · frida 扫内存找已知 mIS 值  —— Memory.scanSync 在大范围下不返回
   · 外部读 /proc/pid/mem        —— app 反复重启、pid 变化、dd seek 不稳
```

---

## 四、★ 要做动态逆向，需要先具备的前提

```
前提 1：能【稳定触发】一次 mIS 计算
   现状：mdna 不可靠触发（删 dna ✗ / pm clear ✗ / 重启 ✗，已多轮验证）
   ⇒ 这是所有动态方法的共同瓶颈

前提 2：知道 mIS 计算的【入口函数】
   · 可以先用「已知 mIS 值在内存里定位」反推调用点
     （本轮尝试失败，但换用 Memory.scanSync 的分段调用应该可行）
   · 或在 libdu.so 里找「输出 36 字符」的函数

前提 3：能对同一个输入观察【多次计算结果】
   · 若同一输入多次算出不同 mIS ⇒ 含随机/时间成分
   · 若稳定 ⇒ 确定函数，可复现
   （这一点对我们最重要：它决定 c001apk 能否复现）
```

## 五、★ 对目标（普通用户自己算）的结论

```
基于本轮 + 上一轮的全部证据：

  mIS 每台设备每次注册一个、服务端按它查表、自造值全 0、
  同次运行跨端点一致、客户端侧找不到任何可复现的构造规律

⇒ 判定：mIS 不可本地构造。
   它要么是服务端下发的，要么是「含服务端参与的一次性注册产物」。
   两种情况下，客户端都无法凭设备特性/签名把它算出来。

⇒ 面向大众的方案仍然只有：
   · 让 c001apk 走一次【真实的注册流程】（得到服务端认可的一条记录）
     —— 但这就回到七轮实验的结论：服务端只认官方包名+签名
   · 或读已授权的数据（需 root）
```

## 七、教训

```
① 我早期用「36 字符 + 受限字符集」去扫 mIS，把别的混淆字段（foO/zvW/52J…）
   的值也当成了 mIS —— 它们的字符集几乎一样。这类错误会污染后面所有推理。
   正确做法：只认 JSON 的 key。本轮 mis_true_samples.py 就是纠正这个。

② 「同设备多个 mIS」这个观察，一度让我以为 mIS 每批重算、含随机成分；
   纠正样本来源后发现：其实是【同一设备的不同次注册】。
   样本的「来源标注」比样本数量更重要。

③ 静态逆向的前提是「有已知明文-密文对」。本项目缺这个前提，
   所以穷举只能排除，不能求解。要先补前提，再谈算法。
```
