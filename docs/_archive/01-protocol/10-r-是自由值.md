# ★ 决定性结果：r 自由，body 决定成败

## 一、四组对照（已复现两次，结果完全一致）

```
A. 原r + 原body   -> HTTP 200  ✓   响应 205 字节
B. 原r + 新body   -> HTTP 400  ✗
C. 新r + 原body   -> HTTP 200  ✓   响应 205 字节
D. 新r + 新body   -> HTTP 400  ✗
```

**实验环境**：设备端 `HttpURLConnection` 发送，`Connection: close`，间隔 25 秒。

## 二、结论（推翻之前的判断）

| 之前的判断 | 实际 |
|---|---|
| 「`r` 与 body 强绑定」 | **错**。`C` 用全新随机 `r` 拿到了 200 |
| 「`r` 需要服务端认可」 | **错**。`r` 完全由客户端自由生成 |
| 「URL 参数与 body 必须成套」 | **部分对** —— 但不是 `r`，是 **body 本身** |

**真相**：

> **`r` 是完全自由的随机数，服务端不校验它。**
> **成败完全取决于 body —— 原样的 body 能过，我构造的 body 过不了。**

## 三、这就把问题精确锁定了

```
原 body（真机抓取，1249 字节）              -> 200
新 body（plain_4.json + 新timestamp，1316） -> 400
```

**两者差在哪，就是服务端真正校验的东西。**

## 四、原 body 的结构分析

```
文件      capture/orig_body.bin
总长      1249 字节
前 32 字节 00ecea3c 8d743a31 25232484 16f1e68e 37a1d6ba 551e7449 3708603d 8fee7fd6
长度 % 16 = 1
```

**关键异常**：`1249 % 16 = 1`。

如果结构是「4 字节盐 + AES 密文」，密文应该是 `1249 - 4 = 1245` 字节 —— **不是 16 的倍数，不可能**。

**说明我对原 body 的结构理解还有偏差**，可能：
- 头部不是 4 字节
- 或者 body 尾部还有额外数据
- 或者密文前另有字段

尝试了 `off=0..63` 的全部偏移、既未找到 gzip 魔数（`1f8b`）、也未找到 JSON 明文。
试过的两个 16 倍数偏移（`off=1`、`off=17`）解出的都是随机字节。

## 五、一个矛盾需要澄清

`Cipher.doFinal` 抓到的上报体加密是 `in=1253 out=1264`（`mdna` 那次）。

- `in=1253` 是 **gzip 压缩后的明文**
- `out=1264` 是 **AES 密文**

而 `SSL_write` 里 `\r\n\r\n` 之后取的 body 是 **1249 字节**。

**`1264 ≠ 1249`，对不上。** 可能的解释：

1. **`SSL_write` 的 body 截取点错了** —— `"\r\n\r\n".indexOf` 在 ASCII 化后的字符串里找 `....`，
   而密文里大量非 ASCII 字节也会显示成 `.`，可能匹配到错误位置
2. **body 不是一次 `SSL_write` 发完的** —— 可能分片
3. **HTTP 头里本身含 `.`**，导致偏移算错

**最可能是第 1 条**：我的 body 起点定位逻辑不可靠。

## 六、下一步（修正采集方式）

**不要再用 `indexOf('....')` 找 body 起点**，改成可靠的定位：

```js
// 直接找字节级的 \r\n\r\n
let bodyOff = -1;
const raw = new Uint8Array(args[1].readByteArray(len));
for (let i = 0; i + 3 < raw.length; i++) {
    if (raw[i] === 13 && raw[i+1] === 10 && raw[i+2] === 13 && raw[i+3] === 10) {
        bodyOff = i + 4;
        break;
    }
}
```

**然后用 `bodyOff + 4(盐) + 1264` 的长度校验**，确认取对了。

拿到正确的原 body 后，解密对比就能直接看出**我构造的 body 缺了什么字段**。
