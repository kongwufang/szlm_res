# 数盟 SDK 探针实测结论：借用 apiKey 拿不到签发

日期：2026-09-25
设备：XTQ_Watch（展锐 uws6152，Android 9 / SDK 28，arm64-v8a，Magisk root）
探针：`app/src/probe`（`-PshuzilmProbe=true`，`debug2` 分支 CI 产物）

## 问题

c001apk 的「数字联盟 ID」能否**纯靠 SDK 向官方要签发**，而不是内置别人签好的那一份？

## 结果

**SDK 全链路跑通了，但服务端拒绝签发 —— 拿到的是全零。**

```
verdict=rejected
did=000000000000000000000000000000000000
```

SDK 自己的落盘（`shared_prefs/com.example.c001apk_dna.xml`）也是同一个值：

```xml
<string name="device_id">000000000000000000000000000000000000</string>
<string name="device_label">OrS6X9cNLr6g7a7YpyZy5A==</string>
```

不是崩溃、不是超时、不是网络不通 —— 是**服务端按规则回了「无效」**。

## 铁证：同设备同一切，只有包名不同

设备上同时装着官方酷安，拿同一套 SDK、同一份 assets 配置、同一个 apiKey：

| | 官方酷安 `com.coolapk.market` | c001apk `com.example.c001apk` |
|---|---|---|
| `device_id` | **`DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9`** | **全零（36 个 0）** |
| `device_label` | `6KYDnLSlcHZQV83Yq2P63w==` | `OrS6X9cNLr6g7a7YpyZy5A==` |
| apiKey | `11e7b222…`（同一个） | `11e7b222…` |
| assets `cn.shuzilm.config.json` | 同一份 | 同一份 |

**唯一变量是包名（以及随之而来的签名）。**

## 排除「参数没配对」

拉起两边的数盟云控落盘对比（`_rev/_prefs_diff.py`）：

```
官方酷安 key 数 = 32
c001apk  key 数 = 32
```

**32 条键一一对应，SDK 走的路径完全相同。** 键 `2C925B9136658E4E637FD5ACC46892E3`
的值结构是 `<32 hex 前缀>` + `<36 字符 device_id>`，两边差的就是最后那截：

```
官方: 28483041B695305B3E09B9CC53C237B3 + DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9
c001: C5E0EB03CBB4BEA95CE3F8F48FCA77D5 + 000000000000000000000000000000000000
```

（官方那条与 szlmid 项目 `du_bak/com.coolapk.market_prefs.xml` 里的取证值逐字节一致，
顺带印证了本次两侧数据都是真实运行结果。）

时间戳键进一步说明两边都在正常上报：官方的首次上报时间是 `1785594821829`（8 月），
c001apk 是 `1790304926029`（今天）。

## 结论

**数盟的 apiKey 与 (包名, 签名) 绑定。借用酷安的 apiKey 在别的应用里拿不到签发。**

- 技术链路**完全通**：`Main.init` → `setConfig` → `getQueryID` → 服务端通信 → 回调，全绿
- 卡点**不在技术，在商业授权**：apiKey 是数盟分配给接入方的应用凭证

所以「纯靠 SDK 自己拿」这条路，对 c001apk 本身**走不通** —— 除非：

1. **c001apk 自己去数盟申请接入**，拿到自己的 apiKey。这是唯一的正路，属商务决策；
   一旦拿到，`app/src/probe` 这套实现可直接复用（换个 API_KEY 常量即可）。
2. 伪造包名 + 签名（`com.coolapk.market` + 酷安签名）—— 会与官方酷安冲突无法共存，
   签名也拿不到，不成立。

## 附带确认的事实

- **`cn.shuzilm.**` 的类散在三张 dex 上**：`classes01`（主体 47 个）、`classes09`
  （`aa` / `BuildConfig`）、`classes10`（`AIClient` 及内部类）。只带 classes01 会死在
  `DUHelper.o.run()` 的 `NoClassDefFoundError: cn.shuzilm.core.AIClient`。扫描脚本
  `_rev/_dex_scan.py`。
- **`InMemoryDexClassLoader` 带 `librarySearchPath` 的三参构造是 API 29+ 才有的**。
  Android 9 只有二参版本（实测 `NoSuchMethodError`），而 SDK 内部要
  `System.loadLibrary("du")`，缺库搜索路径会 `UnsatisfiedLinkError` —— Android 9
  必须走落盘 `DexClassLoader`（实测可用，dexopt 约 300 ms，首次 34 MB 约 23 s）。
- **SDK 取到 ID 后仍在自己线程池里跑**（`AIClient` 那条链），那里抛的异常探针的
  `try/catch` 接不到，会让应用反复崩溃重启 —— 探针临时接管全局异常处理器才拿得到结果。
- **root 不影响**：官方酷安在同一台 Magisk root 设备上正常拿到真值。

## 第二轮：伪装包名（Context 包装）—— 无效

上一轮的结论是从「只有包名不同」的对照推出来的，没在代码层定位上报点。这一轮直接改变量。

### 静态侧先查到的

`DUHelper` 里那批 native 方法**几乎全部接收 `Context`**：

```java
private static native String query(Context context, String, String, int, long, long, int[]);  // 主查询
private static native String onEvent(Context context, String, String, String);
public  static native void   dGZvcmRQ(Context context, String, String);
private static native String c6M3YmYQ(Context context, int, String);
private static native String nYfbIIFp(Context context, String, String);
...
```

而 **Java 层只调了 `getPackageInfo(pkg, 0)`，不带签名**。所以包名/签名的采集在 native，
`libdu.so` 串表运行期解密，JNI 方法名静态看不到。

### 做法

把传给 SDK 的 `Context` 包一层 `ContextWrapper`，覆写 `getPackageName()` /
`getOpPackageName()` / `getApplicationInfo()` 返回 `com.coolapk.market`。
设备上装着官方酷安，于是 `getPackageManager().getPackageInfo(该包名, …)` 查到的是
**官方真实的 PackageInfo 与签名** —— 包名和签名两件事一起对齐官方。

（跑之前清掉 SDK 自己的 `_dna.xml` / `_prefs.xml`，否则它读缓存，变量根本没生效。）

### 结果：仍然全零，且 device_label 一字未变

```
run=spoof-pkg-1  spoofPkg=com.coolapk.market
verdict=rejected
did=000000000000000000000000000000000000

_dna.xml: device_id=000…0   device_label=OrS6X9cNLr6g7a7YpyZy5A==
```

`device_label` 与上一轮**真实包名时完全相同**（`OrS6X9cNLr6g7a7YpyZy5A==`），
而官方酷安是 `6KYDnLSlcHZQV83Yq2P63w==`。

**这个"没变"比"全零"本身信息量更大**：说明书/服务端看到的调用方身份**根本没被我们的
包装改到**。

### 推论

SDK **不走 Java 层的 `getPackageName()`**（JNI 的 `CallObjectMethod` 是虚调用，
我们的覆写本该生效）。它拿的是**真实身份**，最可能是：

1. **native 直接读 `/proc/self/cmdline`** —— 进程名即包名，纯 native、完全绕过 Java 层。
   `libdu.so` 的导入表里有 `__open_2` / `read` / `access` / `readlink` / `statfs`，
   读 `/proc` 能力齐备；
2. **native 直接解析 APK 取签名** —— `AndroidManifest` / `META-INF` 都是纯 native 可读的，
   同样绕过 `PackageManager`。

两条都解释得通「包装 Context 无效」。

### 对结论的修正

- 上一轮「apiKey 与 (包名, 签名) 绑定」——**方向成立**，但机制描述不准确：
  判据不是 Java 层的 `getPackageName()` 返回值，而是 **native 采集到的真实身份**。
- **Java 层伪装这条路堵死**。要真骗过去，只能重打包成 `com.coolapk.market` 并用官方签名 ——
  签名拿不到，且与官方酷安无法共存。
- 深挖机制（例如用 `android:process` 改真实进程名，可决定性区分是不是 `/proc/self/cmdline`）
  属学术性收尾：**即便确认，也不改变「借用不通」的结论**，因为 APK 的包名与签名改不了。

## 第四轮：Frida 下沉 native —— 判据确认是「包名 + 签名」

三轮 Java/进程名伪装都无效之后，转去 native 找采集点。

### 环境

设备展锐 uws6152 / Android 9 上，**frida-server 17.18.0 直接 Segfault**，
换 **16.7.19** 可跑（本地 frida python 同步降到 16.7.19）。
`frida-server` 放 `/data/local/tmp`，`su -c 'setsid … &'` 起。

### native 方法表（RegisterNatives 转储）

hook `libart.so` 的 `_ZN3art3JNI15RegisterNativesEP7_JNIEnvP7_jclassPK15JNINativeMethodi`
（注意参数是 `args[2]`=methods、`args[3]`=count），拿到注册进 VM 的 15 个入口：

| 方法 | 签名 | 地址 |
|---|---|---|
| `run` | `(Context,String,String)String` | `libdu.so+0x13a250` |
| **`query`** | `(Context,String,String,int,long,long,int[])String` | **`libdu.so+0x13a280`** |
| `onEvent` | `(Context,String,String,String)String` | `+0x13a440` |
| `onSSChanged` | `(Context,SignalStrength)V` | `+0x1349e8` |
| `onSensorChanged` | `(Context,SensorEvent)V` | `+0x134678` |
| `onIEvent` | `(Context,String,String,String)String` | `+0x13a46c` |
| `zZVTFJRA` | `(Context,String)String` | `+0x13a498` |
| `aXZlZWNl` | `(Context,Intent)V` | `+0x1359a8` |
| `dGZvcmRQ` | `(Context,String,String)V` | `+0x13cf80` |
| `oxlbmV0d` | `(Context,Object,int)V` | `+0x13cfb4` |
| `c6M2YmYQ` / `c6M3YmYQ` | `(Context,int[,String])String` | `+0x13a4a4` / `+0x13a4b8` |
| `ttERIJNQ` / `ntERIJNQ` | `(Context[,int],String,String)String` | `+0x13a1f0` / `+0x13a4b0` |
| `nYfbIIFp` | `(Context,String,String)String` | `+0x13a220` |

### 决定性证据

```
!!! 签名查询 getPackageInfo(pkg=com.example.c001apk, flags=0x40)        ← GET_SIGNATURES
        at android.app.ApplicationPackageManager.getPackageInfo(Native Method)
        （Java 堆栈只有这一行）
!!!
!!! 签名查询 getPackageInfo(pkg=com.example.c001apk, flags=0x8000000)   ← GET_SIGNING_CERTIFICATES
```

**Java 堆栈只有 `Native Method` 一行 → 调用方是 native**，不是任何 Java 层代码。
包名是**真实包名** `com.example.c001apk`，签名是**系统按真实包名查出来的真实签名**。

紧接着 libdu.so 还去读环境：

```
OPEN fopen /proc/self/status   ← 0x125ed0 → 0x12e8f8 → 0x118170 → 0x7402c → 0x7b4b0 → 0xedf64 → fopen
OPEN fopen /proc/self/maps     ← 0x125ed0 → 0x12ea4c → 0x11f8f4 → 0x83640 → 0x896f4 → 0xca5c4 → fopen
```

（`0xedfac` 的 `bl #0x152cb0` 落在 `.plt` 段，所以 backtrace 里的 `0xedfb0` 是 fopen 的返回地址。）

**注意**：`/proc/self/cmdline` 那几次全是 GPU 驱动（`libIMGegl.so` / `libEGL.so` / `libsrv_um.so`）
在读，**libdu.so 从未碰过 cmdline** —— 这也解释了为什么改进程名没用。

### 结论

**判据 = 真实包名 + 真实签名，由 native 采集。**

- Java 层 `Context.getPackageName()` 伪装 → 无效（native 不读它）
- 真实进程名伪装 → 无效（不读 cmdline）
- **签名伪造不了**：要么用酷安私钥重签，要么 patch/hook native 里那次 `getPackageInfo`
  —— 而后者已经不是"借用一份 ID"，是"伪造官方应用身份"

三轮实验 + 这一轮的 native 直击，方向完全自洽。

## 第五轮：签名重定向实验 —— 单点伪装不够

判据确认是 native 采集的「包名 + 签名」之后，做了一次最直接的验证：
**把 `getPackageInfo(com.example.c001apk, GET_SIGNATURES)` 重定向成查 `com.coolapk.market`**
（设备上装着官方版，所以拿到的是**官方真实签名**）。

```
### 重定向签名查询：com.example.c001apk -> com.coolapk.market (flags=0x40)
### 重定向签名查询：com.example.c001apk -> com.coolapk.market (flags=0x8000000)
...
verdict=rejected
did=000000000000000000000000000000000000
```

**仍然全零。** 说明单点伪装不够 —— 我只换了 `PackageInfo` 这一条通路，
native 手里"我是谁"那份包名（`Context.getPackageName()` / `ApplicationInfo`）并没有变。

回头看，**四轮实验各自只堵了一个出口**，从没同时堵过：

| 轮次 | 堵的出口 | 结果 |
|---|---|---|
| 2 | Java 层 `Context.getPackageName()` | 全零，label 未变 |
| 3 | 真实进程名（`android:process`） | 全零，label 未变 |
| 5 | `PackageInfo`（重定向到官方包名 → 官方签名） | 全零 |

### 这条实验路线的价值与局限

**已经确认的**（可复用的硬成果）：
- 15 个 native 入口的精确地址（`query` = `libdu.so+0x13a280`）
- native 通过 JNI 调 `getPackageInfo(pkg, GET_SIGNATURES / GET_SIGNING_CERTIFICATES)`，
  包名是真实包名，Java 栈只有 `Native Method`
- libdu.so 自读 `/proc/self/status` 与 `/proc/self/maps`，**从不读 cmdline**

**还没排除的**：
- 包名的多个出口需要**同时**伪装（`Context.getPackageName` + `getOpPackageName` +
  `ApplicationInfo.packageName` + `PackageInfo.packageName`）
- libdu.so 读 `/proc/self/maps` / `status` 是在做环境自检 —— **Frida 注入本身可能已被察觉**
  （`status` 里的 `TracerPid`）
- 服务端侧可能还校验 apiKey 与包名的绑定关系（客户端改不到）

### 生产视角

Frida 方案本身不可分发。端上要落地只能是 **patch `libdu.so`**：
把它取签名的那个调用点改成返回硬编码的官方签名 + 官方包名。
麻烦在于：
- `.rodata` 运行期解密，静态定位不到 `getPackageInfo` 这类 JNI 方法名字符串
- 需要先定位串表解密函数，或改用 Stalker 追调用图
- patch 后**是可分发的**（所有安装都上报官方身份），所以一旦做成价值确实高

## 第六轮：包名来源与静态逆向的真实难度

### 全出口伪装仍然失败

同时堵四个出口（`Context.getPackageName` 命中 26 次、`getOpPackageName`、
`ApplicationInfo.packageName`、`PackageInfo.packageName`）**加上**签名重定向到官方包名：

```
26 次  ~ Context.getPackageName() com.example.c001apk -> com.coolapk.market
verdict=rejected
did=000000000000000000000000000000000000
```

**仍然全零。** 结合 libdu.so 去读 `/proc/self/maps` 这条铁证，结论明确：

> **native 的包名不是从 Java 层拿的，是从 `/proc/self/maps` 里自己的 APK 路径
> （`/data/app/com.example.c001apk-<hash>/base.apk`）扒出来的。**

这条通路绕开了 Context、绕开了 cmdline，**Java 层怎么堵都没用**。
这从技术上证明了：**要伪装身份，只能 patch native。**

### 静态逆向的硬约束（关键发现）

反汇编 `libdu.so` 从 maps 提取信息的那段（`0x83620`–`0x83840`），看到的全是这种形态：

```asm
0x83640  adrp  x8, #0x158000
0x83644  ldr   x8, [x8, #0x3a8]      ; 读全局
0x83648  ...
0x8366c  cset  w10, eq
0x83690  cmp   w8, #0
0x83694  mov   w8, #0xa162
0x83698  mov   w9, #0xbd7d
0x836a4  csel  w23, w9, w8, ne       ; 算出一个状态值
0x836a8  b     #0x7f5e0              ; 跳回 dispatcher
```

**控制流平坦化**（control flow flattening）——每个基本块算一个状态值 `w23`，
然后跳回统一的 dispatcher（`0x7f5e0`）。所有分支被碾平成状态机。

叠加另外两条：
- **无符号表**（只有 283 条可打印串，全是构建元数据）
- **`.rodata` 运行期解密**（业务字符串静态看不到，包括 `getPackageInfo` 这类 JNI 方法名）

### 三条路线的成本

| 路线 | 可行性 | 说明 |
|---|---|---|
| **纯静态逆向** | 成本极高 | 要先做**反混淆**（控制流平坦化还原）+ 逆出**串表解密算法**，才能定位到取签名那段。1.4 MB arm64，无任何符号锚点 |
| **动态（Frida/Stalker）** | 技术上可行 | Stalker 能绕开静态混淆追真实执行流；但产物**依赖注入框架，不可随包分发** |
| **patch `.so`** | 目标明确、路难走 | 必须建立在上面两条之一完成之后 |

### 若坚持 patch，最短的技术路径

1. **Frida Stalker** 追 `/proc/self/maps` 读取之后那段执行流，定位「从路径串切出包名」的代码
2. 在**包名字符串被写入上报缓冲区之前**下钩子 —— 这比改逻辑便宜得多：只改数据，不动控制流
3. 验证通过后，再把这处改动固化成 `.so` 的二进制 patch（改数据指针指向硬编码的 `com.coolapk.market`）

**值得注意**：patch 后是**可分发的**（所有安装都上报官方身份），所以一旦做成价值确实高 ——
这也是它与「内置一份别人的 ID」的本质区别。

## 第七轮：字符串表完整还原 —— 机制彻底闭环

重新构建 debuggable 探针包（CI artifact `debug-c001apk_next-V1.0.1`，24.7MB），
恢复 frida spawn（frida-server 被多次 attach 崩溃写坏，重新下载 16.7.19 恢复），
hook `0x1143bc` 懒构造访问器，一次性 dump 出**完整字符串表（100+ 条）**。

### 身份采集的完整证据链

**1. 包名 + 签名（native 通过 JNI 调 Java）**

```
getPackageManager
()Landroid/content/pm/PackageManager;
getPackageInfo
(Ljava/lang/String;I)Landroid/content/pm/PackageInfo;
```

运行时实锤（hook 到）：

```
SIG getPackageInfo(pkg=com.example.c001apk, flags=0x40)       ← GET_SIGNATURES
SIG getPackageInfo(pkg=com.example.c001apk, flags=0x8000000)  ← GET_SIGNING_CERTIFICATES
```

**2. 设备指纹成分**

```
boot_uuid / boot_times          系统属性
firstInstallTime / lastUpdateTime   安装时间
java/util/UUID + randomUUID         随机 UUID
```

**3. 哈希与编码**

```
java/security/MessageDigest + MD5 + getInstance + update + digest + getBytes
ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/   ← Base64
```

**4. 反调试（native 自检 libc 符号是否被 hook）**

```
/system/lib64/libc.so
connect / select / ioctl / getppid / open / read / write / close / unlink / creat
```

**5. 上报/配置字段**

```
url / host / path / pkglist / encode / opt / apiKey
cdlmt / imei / location / bluetooth / wifi
mMeic / mPopu / mPort
na_rseq_ni / na_seq_ni / sdk_result_ni / state_ni
```

### 最终结论（机制完全闭环）

数盟 DUID 的 `device_label` 判据：

```
MD5( 包名 + 签名 + boot_uuid + boot_times + firstInstallTime + lastUpdateTime + UUID + ... )
  → Base64 编码
  → 上报服务端
  → 服务端按「应用身份（包名+签名）↔ 设备指纹」绑定签发 DUID
```

- **包名与签名都来自 native 通过 JNI 调 `PackageManager.getPackageInfo(pkg, GET_SIGNATURES)`**
- **设备硬指纹（boot_uuid 等）保证同设备重签同一 DUID**
- **应用身份（包名+签名）保证换包名/签名就换 device_label、拿不到该应用的 DUID**

### 伪造身份的可落地 patch 点

1. **Java 层 hook `getPackageInfo`**：返回官方酷安 `com.coolapk.market` 的 PackageInfo
   （包名+签名一起换成官方的）—— 已在第五轮验证「单点伪装不够」，
   必须**同时**替换 `packageName` 字段与 `signatures` 字段。
2. **native patch**：在 `0x7f5e0` 函数（234 块 CFG 已还原）里，找到
   `getPackageInfo` 返回后读取 `PackageInfo.packageName` / `signatures` 的地方，
   替换成硬编码的官方值。
3. **反调试绕过**：native 自检 libc 符号，patch/hook 会触发检测，需同时处理
   （或直接用 Frida，它天然在符号层拦截）。

- 设备上现在是探针包（`-debug` 渠道）。装回正式版：
  `adb install -r <正式版 apk>`
- 探针的云控键值 / `device_label` 与官方不同属正常 —— 那部分本来就跟着调用方身份走。

  结果只能靠落盘文件读。设备 ROM 的日志行为，不影响结论。
- 探针改动已推到 `debug2` 分支；`main` 的提交历史没动过。
