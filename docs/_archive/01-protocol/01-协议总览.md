# 数盟协议完整还原报告

真机实测（XTQ_Watch / Android 9 / arm64），frida + tcpdump。
**本轮首次成功复现服务端 200 响应。**

---

## 一、核心突破

**抓到数盟的完整请求明文，并成功原样重放，服务端返回 200。**

```
### 捕获: POST /a/mdna/report?v=8.7&t=m&p=F9BD0FBDACFE80FCF34370FBCFEE1A98&r=91b6545882874d5cb3b9217c388e327a&n=0&l=2&h=0
  >>> 立即原样重放（body 1359 字节，一字未改）
  [结果] HTTP 200  ← 成功
  [响应] <加密数据>

### 捕获: POST /a/dcc2/request?v=2.0&c=1&e=1&p=...&r=41e8c55feeba40db837e22847be350bc&n=0&l=2&h=...
  >>> 立即原样重放（body 536 字节）
  [结果] HTTP 200  ← 成功
```

**对照**：相同格式、只改任意一个参数（哪怕只换 `r`）→ 立刻 400。

## 二、七个上报端点（全部实测抓到）

| # | 端点 | 版本 | 参数 | body 长度 |
|---|---|---|---|---|
| 1 | `/a/mdna/report` | v=8.7 | `t=m` `h=0` | 1290–1368 |
| 2 | `/a/d2api/report` | v=8.7 | `t=a` `e=2` | 3691–4041 |
| 3 | `/a/dcc2/request` | v=2.0 | `c=1` `e=1` | 533 |
| 4 | `/a/dai/report` | v=2.2 | `c=1` `e=1` | 1455 |
| 5 | `/a/audd/valid` | v=1.0 | `t=uid1` | 610 |
| 6 | `/a/daa/report` | v=1.1 | `c=1` `e=1` | 3727 |

**请求格式**：
```
POST /a/<endpoint>?v=<ver>&...&p=<大写32hex>&r=<小写32hex>&n=0&l=2&h=<0或大写32hex> HTTP/1.1
Content-Length: <n>
Content-Type: application/x-www-form-urlencoded
User-Agent: Dalvik/2.1.0 (Linux; U; Android 9; XTQ_Watch Build/PPR1.180610.011)
Host: auni.telecome.cn
Connection: Keep-Alive
Accept-Encoding: gzip
```

**两个贯穿性参数**（七个请求中恒定）：
```
p = F9BD0FBDACFE80FCF34370FBCFEE1A98   ← 设备指纹（关键！服务端靠它认设备）
h = F7AAD8CD5824603F7F2200731D8C045D   ← 会话/签名（mdna 用 h=0）
r = 每次不同（32位小写 hex，形如 UUID 去横线）
```

## 三、body 结构

```
body = 4字节随机盐 + AES(明文)
```

实测四种盐（每请求不同，非固定 magic）：
```
#1 mdna/report   00 ec ea 3f
#3 dcc2/request  5c b9 03 60
#4 dai/report    38 f8 fc fb
#6 audd/valid    4f b2 bb 60
```

**注意**：此前记录的 `00 ec 8a 3f` 只是某一次的值，第 3 字节是变化的。

**加解密状态**：
- **响应解密**：已完全掌握。key = `GWL8jXHLnzp63QDH`（hex `47574c386a58484c6e7a703633514448`），AES-128-ECB/PKCS5，外层 gzip。已用真机 160 字节密文验证通过。
- **请求加密**：**key 未知**。用上面的 key 解不开（padding 错误）。请求用的是另一个密钥。

---

## 四、关键结论：服务端做完整性绑定

综合全部实验，得出确定结论：

**`p` + `r` + `h` + body 密文 是一个整体，服务端校验它们互相一致。**

证据链：
1. 格式完全对齐（URL / Content-Type / UA / body 头）→ 仍然 400
2. 用真实的 `p` + 真实的 body，只换 `r` → 400
3. 一字不改原样重放 → **200**

因此**改 `p` 拿新 DUID 的设想是成立的**，但前提是**同时重新生成与之配对的 body**。这需要请求加密密钥。

## 五、本次打通的技术手段（可复用）

**抓数盟 TLS 明文的正确姿势**：

```js
// 错误：Android 命名空间下返回 null
Module.findExportByName(null, 'SSL_write')

// 正确：用 enumerateExports 精确定位
Process.findModuleByName('libssl.so').enumerateExports()
  .filter(e => e.type === 'function' && e.name === 'SSL_write')
  .forEach(e => Interceptor.attach(e.address, { ... }))
```

**正确时序**（这是之前一直抓不到的原因）：
1. `pm clear` 清空数据 → 制造首次注册场景
2. 启动酷安，**停在隐私协议页**（此时数盟未初始化）
3. **先 attach 并装载 hook**
4. **再点「同意协议并继续」** → 数盟初始化 → 请求发出 → 被捕获

数盟的请求发生在点协议后 **1–30 秒**内，共 7 个。

## 六、安全 hook 地图（拿设备换来的）

| 目标 | 结论 |
|---|---|
| `fopen/open/openat`（隐身） | **必须常开**，否则进程 6 秒被杀 |
| `kill/tgkill`（自杀拦截） | **必须常开** |
| `libssl.so` 的 `SSL_write/SSL_read` | **安全**，且是抓明文的唯一途径 |
| `MD5 0xe1de4` / `strDec 0x1143bc` / `snprintf 0x134944` / `report 0x1447dc` | 安全 |
| **`AES 0xe9218` / `0xe9408`** | **危险** — attach 后立即被杀（完整性校验） |
| `deflate/compress2/gzwrite` | **危险** — 影响全进程 gzip |
| `ioctl` | **危险** — 超高频，脚本卡死 |
| `write` | **危险** — libc 内部高频 |

**数盟的 TLS 用系统 `libssl.so`（BoringSSL），不是 Java Conscrypt。** 判别依据：ClientHello 含 `c009`/`c00a` 两个老式 CBC 套件，而酷安（Conscrypt）不含。

## 七、已排除的 DUID 锚点

| 候选 | 实验 | 结果 |
|---|---|---|
| `android_id` / `serialno` / 机型品牌厂商 / fingerprint | resetprop / settings 改值 | DUID 不变 |
| 全部本地文件 | `pm clear` | DUID 不变 |
| MAC（Java API） | hook 三条读取路径 | **调用 0 次**，数盟不读 |
| MAC（sysfs） | hook fopen 监视 | 无读取 |
| 请求来源 IP / 环境 | 设备端发送 | 与结果无关 |
| TLS 客户端指纹 | 设备 Java 栈 vs 本机 | 与结果无关 |

**锚点是 `p`**（设备指纹，七请求恒定）。而 `p` 的计算方式尚未还原。

---

## 八、下一步的两个方向

**方向 1：拿请求加密密钥**
- hook `AES 0xe9218` 会死（完整性校验）
- 可行替代：在 `libdu` 内找「加密前最后一站」，或在 `SSL_write` 上游回溯调用栈
- 拿到 key 后即可自由构造任意 `p` 的配对 body → 实现「上报新指纹拿新 DUID」

**方向 2：还原 `p` 的算法**
- `p` 是 32 位大写 hex，形如 MD5
- 七次请求恒定 → 与时间无关，纯设备指纹派生
- 已知指纹输入清单在 `FINGERPRINT_REPORT.md`
- 可先用离线暴力匹配（此前 28000+ 组未命中，说明输入可能是完整指纹 JSON 的规范化拼接）
