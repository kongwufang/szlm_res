# 全量抓包：本轮实测与两个真 bug

> 目标（缺口 6）：重抓 `d2api` / `daa` 的 body（旧样本 CL=4001 / 4218，捕获 0 字节）。
> 本轮把抓取管线重写成「全量不截断」，修掉了两个真 bug，**但这两个端点仍未拿到**。
>
> 日期：2026-10-03 ｜ 设备：XTQ_Watch（D2）

---

## 一、★ 修掉的两个真 bug（都会导致静默丢数据）

### bug 1：`SSL_write` 只挂了 `libssl.so`，漏了 `libjavacrypto.so`

`/proc/<pid>/maps` 实测 D2 上酷安**两个库都加载了**：

```
libcrypto.so
libjavacrypto.so
libnetdutils.so
libssl.so
```

第一版脚本在挂上 `libssl.so` 后就置 `done = true`，**导致 `libjavacrypto.so` 被永久跳过**。

**修法**：逐库记录 `hooked[lib]` 状态，未挂上的库每个 tick 继续重试。

**结果**：`libjavacrypto.so` 上导出表里**没有** `SSL_write`/`SSL_read`（挂了 0 个钩子），
所以两个库都覆盖之后，实际有效的还是 `libssl.so` 那两个 —— 但逻辑上的漏洞必须补齐，
否则在别的设备/版本上会漏抓。

### bug 2：★ 消息 ID 在多进程间撞车 —— 已抓到的数据被覆盖

```js
let seq = 0;          // 每个注入实例（每个 pid）都从 1 重数
const id = ++seq;
LOG('### PART:REQB:' + id + ...)
LOG('=== REQB#' + id + ' END')
```

Python 侧用 `(tag, id)` 作键落盘。**不同 pid 的 `REQB#4` 与 `RESP#4` 会互相覆盖。**

**实测证据**：D3 那一轮

```
=== REQ#4  SSL/libssl.so:SSL_write  端点=mdna
  h=0  CL=1413  实际body=1413  整包=1760          ← 数据抓到了
=== RESP#5 libssl.so:SSL_read  len=345
  [落盘] D3_RESP_5.bin            345 字节
（但 D3_REQB_4.bin 从未落盘 —— 被同 id 的另一进程消息覆盖）
```

**修法**：所有消息的 tag 都带进程号 → `REQB@p<PID>`、`RESP@p<PID>`。
Python 侧匹配改成 `k[0].startswith("REQB")`。

**⇒ 这是个「一改就静默丢数据」的 bug，属于 `FIELD_CRITERIA.md` 那类「观测本身有病」错误。**
已固化进脚本。

## 二、抓包管线的其它改进

```
① 全量分块回传：### PART:<tag>:<id>:<off>:<total>:<hex>
   · 每块 4KB 原始字节（8KB hex），远离 frida 消息上限
   · 旧脚本对 body 用 slice(0, 4200)，大 body 直接截断 —— 这就是原样本丢 d2api/daa 的原因
② 落盘后自动用池常量试解 body，解出就写 .json 并打印池地址
③ 端点自动识别：正则 /a/([A-Za-z0-9_]+)/ 从请求行取
④ 头（REQH）与 body（REQB）分开落盘，便于还原
```

## 三、mdna 全量抓到过（1413 字节 body）

```
=== REQ#4  SSL/libssl.so:SSL_write  端点=mdna
  line=POST /a/mdna/report?v=8.7&t=m&p=F9BD0FBDACFE80FCF34370FBCFEE1A98
       &r=b1c0ffea7a334961ab386ebf119e7271&n=0&l=2&h=0 HTTP/1.1
  Content-Length: 1413      实际body=1413      整包=1760
```

对比旧样本 `wire_m58_REQ_9_len1745.bin`（CL=1398）—— 多 15 字节，属正常波动。

**这一条证明管线是通的**：端点识别、body 全量、池常量试解都能工作。

## 四、`d2api` / `daa` 为什么还是没拿到

本轮做了 4 次尝试（`cap_full` / `cap_full2` ×3 / `cap_reg`），观察到的规律：

| 触发方式 | 结果 |
|---|---|
| `pm clear` + app 冷启动 | **只有内置的 3 个启动响应（197/241/605 字节），零 `/a/` 请求** |
| 删 `dna.xml` + HOME/am start | **只有 `mdna` 一个端点** |
| 直接 `am start`（app 已稳定） | 无 `/a/` 请求 |

**结论**：

```
· `mdna` 是「想要 ID」时发的 —— 删掉 dna.xml 就会触发
· 其余 5 个上报端点（含 d2api / daa）**只在 pm clear 后的完整注册流程里发**，
  而那条流程要跨多次进程重启（D2 上实测 pid 26955 → 27431 → 28157 …），
  且每次重启都要重新挂钩子 —— 时间窗很窄
· 4 次尝试里，`/a/` 请求出现在「app 已稳定 + 删 dna」这一路，而 pm clear 那一路
  app 一直在崩、请求没发出来
```

**⇒ 要拿到 d2api/daa，需要「spawn 级 gating」**：
用 `frida.spawn(pkg, gating=True)` 让 app 停在入口，装好钩子再 resume，
才能保证注册流程全程被覆盖。D2 上 `spawn` 一直不可用（短命父进程 / agent 同步超时），
所以这条路在这台设备上走不通。

**替代方案（更省力）**：D2 上有 `xyz.happypass.wifiadb` 之类的工具；
或者用设备上已装的抓包 App。但最直接的还是：

```
在 D1 上做完整注册并抓包（= 缺口 1 的实验）
D1 是 USB + Magisk，不是 WiFi，时序更可控
而且 D1 的 mIS 值应当与 D2 不同 —— 一次实验同时解决缺口 6 和缺口 1
```

## 六、教训

```
① 钩子要覆盖【全部】候选库，且【逐库】记状态 —— 不能一个成功就整体跳过
② 多进程注入时，消息 ID 必须带进程号，否则落盘会静默覆盖
③ 「app 反复重启」这种场景，attach 式注入注定漏 —— 需要 spawn + gating
④ 4 次尝试里 3 次在「换触发方式」上打转，但真正的瓶颈是【注入时机】，
   应该更早换成 spawn/gating 而不是反复调 pm clear 与删文件的组合
```
