### 1.2 这条栈说明了什么

```
★ Coolapk 的 Application 基类是 com.netease.nis.wrapper.MyApplication
  —— 这是【网易易盾】的加固壳（NIS = NetEase Information Security）

⇒ 应用的真正 Application 类被易盾的壳包裹。
   真实的 Application.onCreate 在壳里被调用（反射或 native 调用），
   所以：
     · 常规的 Application.onCreate 钩子抓不到真实实现
     · szlm 的 Main.init 很可能是在【壳内部的 native 代码】里被调用的
     · 这就是为什么我们挂钩 Main 的所有方法都 0 次命中
```

### 1.3 与之前所有观察的吻合

```
✓ libdu.so 是加壳的（字符串加密，.rodata 只 1484 字节）—— 可能同属一个加固体系
✓ Main.init 0 次命中 —— 调用来自 native/壳内部，不走 Java 可见路径
✓ 库会加载（清数据+走同意时）—— 由壳在某个时机触发 dlopen
✓ getTraceInfo 报 pkg="" / bu="" / w=0 —— 因为壳传给 SDK 的 context 不完整
```

## 二、★ 这改变了攻关方向

```
原先的方向：挂钩 Java 层的 ClassLoader / Main.init
    → 已证实无效（壳把调用藏在 native 里）

新方向（三条）：

A. 挂钩【易盾的类】，从壳的入口进去
   · com.netease.nis.wrapper.MyApplication 的方法
   · com.netease.nis.* 的其它类
   · 从壳的 onCreate/attachBaseContext 往后跟，看它调用了什么

B. 从 native 侧下手：挂钩 dlopen / android_dlopen_ext
   · 之前做过，但那时钩子只装在子进程
   · 现在知道主进程可用 spawn+gating 拿到 ⇒ 重做一次
   · libdu.so 被 dlopen 的那一刻 → 抓调用栈（native backtrace）
   · 这能直接定位"谁加载了 libdu"

C. 挂钩 JNI 的 RegisterNatives / FindClass
   · 壳注册 native 方法时会经过这些入口
   · 一旦看到 libdu 相关的注册，就能拿到函数表
```

**推荐：B（dlopen 的 native backtrace）** ——
   它是"谁加载 libdu"最直接的答案，而且不依赖 Java 层。

## 四、★ 下一次的具体做法

```python
# 1) 清数据 + spawn + gating，在入口装：
#    - dlopen / android_dlopen_ext 钩子（native backtrace）
#    - Application 钩子
#    - 易盾类钩子（com.netease.nis.*）

# 2) 走同意触发注册

# 3) libdu 被 dlopen 的瞬间，打印 native 调用栈
#    => 直接看到"谁加载了它"
```

```javascript
// dlopen 钩子的关键部分
const dl = Module.findExportByName(null, 'android_dlopen_ext');
Interceptor.attach(dl, {
    onEnter(a) {
        this.nm = a[0].readCString();
    },
    onLeave(r) {
        if (this.nm && this.nm.indexOf('du') >= 0) {
            LOG('DLOPEN ' + this.nm + ' -> ' + r);
            // ★ native 调用栈
            LOG(Thread.backtrace(this.context, Backtracer.ACCURATE)
                .map(DebugSymbol.fromAddress).join('\n'));
        }
    }
});
```

③ spawn+gating 是唯一能保证"钩子在目标代码之前就位"的方式。
