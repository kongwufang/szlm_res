## 三、★ 关于 mIS 的最终判断

```
事实：
  ✓ 编码函数是通用工具（3 个调用者用法各异）
  ✓ 表来自 token 解析（0x1143BC）
  ✓ 实测抓到 base64url 表
  ✗ 但 mIS 样本与 base64url 不匹配（越界字符 32 个，与标准 base64 相同）

推断：
  · mIS 的字符集【不是】这个编码函数直接产出的
  · 或者 mIS 用的是【另一个 token】解析出的表
  · 或者 mIS 前面还有一层"数据 -> 索引"的映射

★ 结论：需要【运行时】观察 mIS 生成那一刻的现场
   （静态分析已到边界 —— 表是运行时解析的，静态拿不到"哪张表用于 mIS"）
```

## 七、教训

```
① 静态分析有明确边界。
   我把机制还原到"表从 token 解析而来"就到底了 ——
   再往下必须运行时观察。

② 「明文与密文混存」是常见设计。
   0x14300~0x147C3 是明文（权限名、图标、常量），
   而属性名那些是密文（逐串密钥）。
   ⇒ 不能假设"全都加密"或"全都明文"。

③ 意外收获也要记录。
   静态 dump 里发现 'e5bec3748403dcb7f4b9'（20 个十六进制字符）
   和一个嵌入的 PNG 图标 —— 后者说明库里有 UI 资源。
```
