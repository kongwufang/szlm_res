## 一、★★★ 核心突破：字符串解析机制

### 1.1 从调用点 `0x0E8B30` 反汇编得到

```asm
0E8A88  adrp x8, #0x15b000
0E8A8C  ldr  x8, [x8, #0x250]              ; ★ 从 BSS 取 32 位 token
0E8A90  and  x0, x8, #0xfffffffffffffffc    ; ★ 清低 2 位（那 2 位是标志）
0E8A94  bl   #0x1143bc                      ; ★ 哈希分派器 -> 字符串指针
0E8A98  mov  x2, x0                         ; 作为第 3 参数使用
```

### 1.2 还原出的机制

```
BSS token (32 位)
     |
     and x0, token, #0xfffffffffffffffc    ← 清掉低 2 位标志
     |
     bl 0x1143BC                            ← 二分查找分派器
     |
     返回字符串指针
```

**★★★ 这解释了此前所有的困惑：**
```
· 为什么字母表"不在文件里"
    -> 它在 BSS 里只是个 32 位 token，字符串是运行时解析出来的
· 为什么用固定偏移读内存读不到
    -> 必须经 0x1143BC 解析
· 为什么字符串加密算法是"逐串不同密钥"
    -> 那是【另一层】（.rodata 里的密文）；
       token 机制是【更上层】的间接层
```

### 1.3 这个模式在 libdu 里反复出现（可作签名）

```
adrp x8, #0x15b000
ldr  x8, [x8, #<offset>]
and  x0, x8, #0xfffffffffffffffc
bl   #0x1143bc

出现位置：0x0E8A88、0x0EEC28、0x0EEC38、0x0ECD4、0x0ECE4 ...
```

## 二、调用点 `0x0E1224` 完整还原（加密+编码）

```asm
0E115C  stp x29,x30,[sp,#-0x30]!      ; 入口（x0=缓冲, x1=?)
0E116C  cbz x0, <失败>
0E1174  bl  #0x152b30                  ; strlen -> w20
0E1180  cmp w8, #0x2fe                 ; ★ 长度限制 1..766

; ── 阶段 A：NEON 批量 XOR ──
0E11AC  adrp x9, #0x14000
0E11B0  ldr  q0, [x9, #0x210]          ; ★ 16 字节密钥向量
0E11CC  eor  v1.16b, v1.16b, v0.16b    ; ★ 16 字节并行
0E11D0  str  q1, [x12], #0x20          ; 步进 0x20

; ── 阶段 B：尾部 4 字节循环 XOR ──
0E11E0  add  x10, x10, #0x46b          ; ★ 尾部密钥 @0x1446B
0E11E4  and  x11, x9, #3               ; ★ 索引 mod 4
0E11F0  eor  w11, w12, w11

; ── 阶段 C：分配 + 编码 ──
0E1204  lsl  w8, w20, #1
0E1208  add  w0, w8, #0x20             ; ★ 输出 = 2*len + 32
0E120C  bl   #0xdc18c                  ; malloc
0E1224  bl   #0x0e123c                 ; ★ 编码函数
```

## 三、★★ 密钥（已提取）

```
NEON 密钥向量 @0x14210:
    1F 6F 8B A3 00 00 00 00 00 00 00 00 00 00 00 00
尾部 4 字节密钥 @0x1446B:
    1F 6F 8B A3

★ 两者相同 = 1F 6F 8B A3（4 字节）
  后 12 字节为 0 -> "16 字节 XOR" 实际只在低 4 字节起作用
  （等价于 4 字节循环 XOR）
```

## 四、编码函数 `0x0E123C` 内部（控制流平坦化）

```asm
0E123C  sub sp, sp, #0x140              ; 栈帧 0x140
0E1338  <dispatcher>                    ; token 是 32 位常量 (mov+movk)
        cmp w8, w9 / b.eq <case>

0E1704  ldr  x0, [sp, #8]
0E170C  bl   #0x1143bc                  ; ★ 表指针来自 token 解析
0E1754  str  x0, [sp, #0x20]            ; ★ 存表指针

; ── 主循环 ──
0E1984  ldur x8, [x29, #-0x38]
0E1988  ldrb w8, [x8]                   ; 读输入
0E198C  ldr  x9, [sp, #0x20]            ; ★ 表指针
0E1990  and  x8, x8, #0x3f              ; ★ 取 6 位
0E1994  ldrb w8, [x9, x8]               ; ★ 查表
0E19A4  strb w8, [x19, x10]             ; 写输出
0E19B4  add  w8, w8, #3                 ; ★ 输入 +3
0E19D0  strb wzr, [x19, w8, sxtw]       ; 结尾补 0
0E19F0  ret

指令统计: mov 104, movk 95, cmp 49, b 31, ldrb 18, strb 15
```

### 4.1 一个重要观察

```
输入取法：ldrb w8,[x8] 然后 and #0x3f
=> 【一个字节出一个索引】，但输入每次前进 3 字节

这【不是】标准 base64 的位重组（3 字节 -> 4 索引）
=> 说明输入缓冲里存的【已经是归一化的索引】，或
   分组逻辑被控制流平坦化拆散到别处
```

### 4.2 输出大小公式的含义

```
输出 = 2 * 输入长度 + 32
纯 base64 只需 ceil(4n/3)
=> 2n+32 更宽松，说明输出可能比理论 base64 更长
=> 提示：编码不止一层，或有额外附加内容
```

## 六、★ 对 mIS 的推论

```
① 编码函数是【通用工具】，被多处复用（3 个调用者用法各不同）

② mIS(36 字符) 长度固定；base64(27 字节) 正好 36 字符 ✓
   => 27 字节输入 -> 变换 -> 36 字符输出

③ mIS 字符集与抓到的 base64url 不匹配
   => 可能：
      a) 表是【另一个 token】解析出来的（不是 0x0E1754 用的那个）
      b) mIS 的字符集经过了额外处理
```

## 九、教训

```
① 「调用者」比「被调用者」信息量更大。
   编码函数本身只说"查表"；调用者才揭示了
   "表从 BSS token 经 0x1143BC 解析而来"—— 完整机制。

② 记住字节级签名（adrp+ldr+and #~3+bl）就能在任何地方认出这个模式。
   它在 libdu 里反复出现，是"token 解析"的指纹。

③ 「输出 = 2*len+32」这种余量是重要线索。
   说明输出可能比理论 base64 更长 —— 提示还有额外内容。

④ 控制流平坦化不妨碍定位。
   493 条里大部分是 dispatcher 的 token 比较，
   但"表指针/索引/写输出"特征明显，一搜就出来。
```
