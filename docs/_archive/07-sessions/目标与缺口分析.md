## 一、先明确目标（`PROJECT_README.md` §1.2 的原始表述）

| 阶段 | 表述 |
|---|---|
| 最初 | 不用 SDK，自己实现，给**自己的设备**取 DUID |
| 后期 | 为 **c001apk**（第三方 Coolapk 客户端）**提供 DUID 支持**，使其功能与官方 app 对齐 |

**⇒ 目标的本质**：让 c001apk（包名 `com.example.c001apk`，签名是它自己的）
从数盟服务端拿到一个**可用的 DUID**。

## 二、★ 目标达成的必要清单（逐条对照现状）

要让「c001apk 拿到可用 DUID」，必须同时满足：

| # | 必要条件 | 现状 | 差距 |
|---|---|---|---|
| 1 | 能构造出服务端接受的请求 | ✅ **已解决** | 无 —— 5 个字段 + 类型 + 加密链路全解出 |
| 2 | 服务端认「这个应用身份」并签发 | ❌ **未解决** | **这是唯一的硬缺口** |
| 3 | 拿到的 DUID 对 c001apk 可用 | ⚠️ 未验证 | 取决于 2 |

**⇒ 结论：缺口只剩一个，但它正好是核心。**

## 三、★★★ 唯一的硬缺口：服务端按【应用身份（包名+签名）】签发

### 3.1 铁证（`SZLM_SDK_SIGNING_VERDICT.md`，同设备同一切，只有包名不同）

```
同一台设备、同一套 SDK、同一份 assets 配置、同一个 apiKey：
  官方酷安 com.coolapk.market   -> device_id = DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9
  c001apk  com.example.c001apk  -> device_id = 000000000000000000000000000000000000（全零）

  同时：
  官方 device_label = 6KYDnLSlcHZQV83Yq2P63w==
  c001 device_label = OrS6X9cNLr6g7a7YpyZy5A==     ← 也不同
```

七轮实验（重定向包名 / 重定向签名 / 全出口伪装 / native 下沉）全部失败。
**native 侧的确切判据 = 包名 + 签名。**

### 3.2 「device_label 只绑包名」这个早先结论要改

`dev2/TWO_DEVICES.md` 曾记录「`device_label` 两台设备相同」——
但那时**两台跑的都是官方酷安**，所以相同是自然的。

对照 c001apk 的 `OrS6X9cNLr6g7a7YpyZy5A==` ⇒ **`device_label` 是逐应用身份的值**，
不是逐设备、也不是全局常量。

> ⚠️ **2026-10-03 追加实测**（`THREE_DEVICE_XVAL_RESULT.md`）：
> D1 与 D2 **两台不同设备**读到的 `device_label` 都是 `6KYDnLSlcHZQV83Yq2P63w==`
> ⇒ 它**不随设备变**，只随应用身份（包名 + 签名）变。
> 这条把上面的推测从「推」变成「证」，同时排除「逐设备」的可能。


**⇒ 「device_label 只绑包名（+签名）」这条要与「逐应用身份」统一表述。**

### 3.3 这刚好解释了本轮发现的 `mIS`

`FIELD_TYPES_AND_MIS.md` 记录：

```
mIS 缺了          -> n_a 全 0
mIS = dLH 的值    -> n_a = DUnkGC0m8phaJExl5EHNnMnt5YNydzbH_3g0   ← 另一个 DUID
自造 36 字符串     -> 全 0
连发 3 次          -> 完全相同（确定性）
```

**⇒ 把它拼进整体模型**：

```
· mIS 大概率就是 native 算出的【应用身份指纹】（观测到包名+签名）
· 服务端流程：mIS → 查/建「应用身份 → DUID」登记 → 回 n_a
· 官方酷安有登记 → 回真 DUID
· c001apk 的 mIS 是另一个值，且服务端【没有它的登记】→ 回全 0
· 我们回放官方酷安的字节 = 用官方的 mIS → 所以能拿到真 DUID
```

**注意**：这条是**推断**，`mIS 是应用身份指纹` 尚未被直接验证（见 4.1）。

## 四、由这个模型推出的**新缺口**（都是关键且可验证）

### 缺口 A：`mIS` 到底绑什么？—— 未验证

```
三种可能，实验可区分：
  A1 绑【应用身份（包名+签名）】  -> 同设备换包名，mIS 应变化
  A2 绑【设备】                 -> 换设备，mIS 应变化
  A3 绑【两者组合】             -> 都变
```

**判定实验**（成本低）：
```
在官方酷安里读出 mIS（反射或抓 mdna）→ 记为 mIS_official
在 c001apk 里读出 mIS                       → 记为 mIS_c001
同一台设备对比：
  · 不同  -> A1 或 A3：mIS 确实绑应用身份 ★（强证据支持上面的模型）
  · 相同  -> A2：mIS 绑设备，那服务端区分应用身份靠的是别的东西
```

**为什么这条最关键**：它决定「c001apk 能不能靠自己拿到 DUID」——
如果 mIS 绑包名+签名，那 c001apk 天生拿不到（除非服务端登记它）。

### 缺口 B：`mIS` 的生成算法 —— 未解出

```
· 不在字符串池（slot_strings / pool_plain / strings_dump 全未命中）
· +11 / -11 / 取反 / XOR 0x5A / (c-1)XOR i / c XOR i / base64 / hex / 反转 全解不出
· 长度 36，含反斜杠与引号
⇒ 是 native 算出的不透明值
```

**要解它需要**：在 native 侧找到 mIS 的构造点（`libdu.so` 控制流平坦化 +
`.rodata` 运行时解密，静态很难；动态 dump 可行）。

### 缺口 C：服务端是否只认「已登记的应用身份」—— 推断未验证

```
若成立 => c001apk 永远拿不到（除非走别的路）
若不成立（比如只需格式合法的 mIS）=> 那自造 mIS 为何全 0？矛盾
⇒ 「自造 mIS 全 0」这条实测 已经强烈指向「服务端查登记表」
```

### 缺口 D：`h` 能否用别人的值 —— 已知（可自由填）

```
H_SEMANTICS_RESULT.md：h 是自由值，16/16 变体全通过
⇒ c001apk 用官方酷安的 DUID 算 h 也行，不构成障碍
```

## 六、缺口优先级（按「离目标最近」排）

> ⚠️ **本节已被 `PROXY_CLIENT_FEASIBILITY.md` 修正** ——
> 用户澄清了方案：**不需要服务端注册新 ID**，只要把设备指纹发上去、
> 把酷安已申请的 ID 拿下来。于是「c001apk 没登记」不再是障碍，
> 缺口收窄成「两个种子怎么拿到」。以下是修正后的排序。

| 序 | 缺口 | 成本 | 决定什么 |
|---|---|---|---|
| **1** | **种子来源**：`mIS` 与 `2cO` 纳秒是【本地算出的】还是【服务端发的】？ | 中 | **直接决定方案可行性** ——「替设备取 ID」成不成，全看这一条 |
| 2 | 若种子本地可算：`mIS` 的算法 | 高（native 反混淆） | 能否纯软件复刻 |
| 3 | 若种子服务端发：能否从酷安的数据里读出 | 低 | 需要读别的 app 数据（普通用户做不到） |
| 4 | 种子是否绑设备（换设备是否失效） | 低 | 能否跨设备复用一份 |
| 5 | 一份 DUID 能否多设备共用 | 低 | 能否批量用 |
| 6 | `daa` 池常量 / 剩下 72 个字段用途 | 中/低 | **对目标不必要** |

### 6.1 修正后的两个「种子」（本轮实测）

```
mIS  ：必须是【服务端登记过的精确值】
        · 改 1 字符 / 重排 / 全 A / base64 形态 / 去掉反斜杠  → 全部全 0
        · 大写化 → 通过（归一化）
        · 换成另一个已知值 → 返回【另一个 DUID】
        ⇒ 不是格式校验，是查表

2cO  ："秒.纳秒"
        · 秒   ±12 小时（±43200s）都通过
        · 纳秒 ±1 纳秒就全 0
        ⇒ 种子是那串【纳秒】，不是「登记时刻」
```

**⇒ 请求侧确实没有签名，但「拿不到 DUID」的真正原因是这两个种子。**

### 6.2 ★ 立刻可做的判定实验（一次定性）

```
目的：种子是本地算的，还是服务端发的？

在官方酷安上：
  1) 让酷安正常注册一次，抓 mdna 记下 mIS 与 2cO 的纳秒
  2) 删 dna.xml → 重启 → 再抓 mdna
        · mIS 与纳秒都不变 ⇒ 种子由设备决定，可复刻 ⇒ 方案可行
        · mIS 变           ⇒ mIS 与某次注册绑定
        · 纳秒变           ⇒ 2cO 种子每次重取都变，需拿到「当次」值
  3) 再 pm clear → 重启 → 第三次抓
```

`dev2/TWO_DEVICES.md` 记过「清空本地数据后仍拿回同一个 DUID」，但**没把
`mIS` 与 `2cO` 抓下来对比** —— 本轮要补的就是这个对比。
