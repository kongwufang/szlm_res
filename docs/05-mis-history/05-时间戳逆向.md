# `mIS` / `2cO` 逆向 —— 本轮实测（含一处未解释的异常）

> 目标（用户方向）：搞清 `mIS` / `2cO` 由什么**设备特性或签名**构造而来，
> 以便普通用户（无 root）也能自己算出来。
>
> 日期：2026-10-03 ｜ 主力：D3（性能最好）；对照样本含 D2 的历史抓包

---

## 一、★★ 关于 `2cO`：它是**实时时钟**，但**子秒部分是设备的键**

### 1.1 从 33 个历史样本看：纳秒各不相同

```
样本的纳秒值（14 个不同值，节选）：
  110947858 / 13589905 / 17322914 / 291441780 / 334705411
  380034934 / 4675430 / 515532599 / 817030005 / ...

⇒ 2cO 是【实时时钟】读出来的，不是固定常量
```

### 1.2 但服务端拿【子秒】做键（`ts_key_probe.py` 同轮实测）

```
① 原值                            -> 通过
② 秒 +43200（+12h），子秒保留      -> 通过（与①同一个 n_a）
③ 秒 +43200，子秒换成历史样本的值   -> 全 0
④ 秒 +43200，子秒 = 000000001      -> 全 0
⑤ 秒 +43200，子秒 = 999999999      -> 全 0
⑥ 秒 +43200，子秒 = 原值 +1（最后一位） -> 全 0
```

**⇒ 结论（很硬）：服务端按 `2cO` 的【子秒部分】索引设备记录；整数秒可以漂 ±12 小时。**

**⇒ 所以 `2cO` 的性质是**：

```
· 它由时钟读出（所以每次重取会变）
· 但【取一次就得固定下来】—— 子秒成了设备的 ID
· 也就是说：SDK 在【首次注册】时读一次时钟，把子秒当作这台设备的标识存起来
```

### 1.3 对目标的含义

```
普通用户无法「算出」2cO —— 它不是从设备特性推导的，而是注册那一刻的时钟采样。
但它是【本机读一次时钟就能得到】的：
  · 若 SDK 在注册时取时钟 -> 那本机也能取 -> 可行
  · 关键是「哪一次采样被服务端记住」—— 只有注册时那一次
```

## 二、★★ 关于 `mIS`：它是**每批重算**的，不是设备固定值

### 2.1 同一台设备的两组样本，`mIS` 完全不同

（从 `wire_m55_JSONHEX_*.bin` 解出的明文 body，都是 D2 `XTQ_Watch`）

```
批次 A（m55_2 / m55_6）：  mIS = "BrBrGppp?uGEtsBpG<?tE?Cq<G?<tCqspp<s"
批次 B（m55_8）：          mIS = "R$R!W$!SOLWW%"ROW%OLU!S$LUO&%!"!!#L#"
```

同一台设备、同一个 DUID、同一个 `2cO` 子秒，**`mIS` 却变了**。

**⇒ `mIS` 不是设备固定标识** —— 它是每批（每次 SDK 初始化）重新算出来的。

### 2.2 字符集观察（可能指向编码）

```
"R$R!W$!SOLWW%"ROW%OLU!S$LUO&%!"!!#L#"   —— 含 ! $ " % 等
"BrBrGppp?uGEtsBpG<?tE?Cq<G?<tCqspp<s"   —— 含 ? < 等
长度都是 36；字符分布在 0x22~0x7E
```

**形态像「某个 27 字节二进制经 base64 变体编码」**（27 字节 → 36 字符正好是 base64 比例）。

### 2.3 但「mIS 是否必需」的实验结果**自相矛盾**

`mis_necessity_probe.py`：

```
对照（完整原 body）        -> n_a = DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9   ★ 期望值
① 只留 5 个必需（无 mIS）   -> 全 0
② 5 必需 + 原 mIS         -> n_a = DU7oGVomxL6iRMnF6Ozl8Xq8Vq            ← ★ 另一个 DUID
③ 5 必需 + 36 个 X        -> 全 0
④ 5 必需 + mIS = ""       -> 全 0
⑤ 5 必需 + mIS = null     -> 全 0
⑥ 同②                    -> n_a = DU7oGVomxL6iRMnF6Ozl8Xq8Vq            ← 与②一致
```

**⇒ 两个观察同时成立：**

```
(a) mIS 是必需的（去掉/改掉就全 0）        —— 与前面的结论一致
(b) 但同一份「原 mIS」，返回的 DUID 与对照不同：
      对照 DUFPnec5…（完整 body）
      ②/⑥  DU7oGVom…（最小 body）
    而且 ② 与 ⑥ 完全一致 ⇒ 这个新值是【稳定】的
```

### 2.4 对 (b) 的三条候选解释（未验证）

```
① 服务端对「同一设备身份」持有多条记录（历史注册留下的），
   按某种规则返回其中一条；两条请求路径命中了不同记录
② 最小 body 缺少某个次要字段，服务端走了不同的分支（如「首次识别」）
③ 对照那一份的 DUFPnec5… 来自缓存层，而最小 body 那份走了实时查询
```

**⇒ 这是本轮唯一没解释清楚的点，需要单独一轮实验来钉住。**

## 三、★ 本轮否定掉的假设

| 假设 | 结果 |
|---|---|
| `mIS` 是设备固定值 | **✗ 否定** —— 同一设备不同批次不同 |
| `2cO` 是固定种子（整串） | **✗ 否定** —— 它是时钟读出的，33 个样本各不相同 |
| `2cO` 的秒是键 | **✗ 否定** —— 秒 ±12h 全通过 |
| `mIS` 可以从 prefs 读到 | **✗ 否定** —— 33 个云控键 + 3790 个键名全扫过，没有 |
| `mIS` 是 Java 字段 | **✗ 否定** —— 80 个候选类扫过，无命中 |
| `mIS` 出现在响应里（服务端下发） | **✗ 否定** —— 响应只有 `err/n_a/nctl/cdd/dlab/isem/itime` |

## 四、★ 本轮确立的

| 结论 | 证据 |
|---|---|
| **`2cO` 的【子秒部分】是设备键** | 同轮 6 组变体：保留子秒全通过，换子秒全 0 |
| **`2cO` 由时钟读出，但取一次即固定** | 33 样本子秒各异 + 服务端按子秒索引 |
| **`mIS` 每批重算、非设备固定** | 同设备两批样本 mIS 不同 |
| **`mIS` 确实必需**（不能省、不能改） | ①③④⑤ 全部全 0 |
| **`mIS` 不在响应/prefs/Java 字段里** | 三处独立排查 |

## 五、下一步该做的（把 2.3 的异常钉住）

```
实验设计（成本低，一次定性）：
  对【同一份】请求构造，连续发多次，看 n_a 是否稳定
    A 组：完整原 body，连发 5 次
    B 组：最小 6 字段 body（5 必需 + 原 mIS），连发 5 次
  比较：
    · 两组内部各自稳定，但组间不同  -> 服务端有两条记录（解释 ①）
    · 两组都稳定且相同              -> 之前那次是偶发
    · 组内就不稳定                  -> 服务端有轮转/缓存层（解释 ③）
```

**这个实验做完，就能知道「同一设备能拿到几个 DUID」——这直接决定
「普通用户自己算一个 mIS 能不能被接受」。**
