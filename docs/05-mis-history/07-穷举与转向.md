> 日期：2026-10-03
> **穷举已按你的要求快速试完，判定为死路（有数学依据）；转向算法侧时遇到环境瓶颈。**

---

## 一、★ 自定义字母表穷举 —— 判定为死路（有依据，不是"没试出来"）

### 1.1 判定实验

`mis_alphabet_exhaust.py` 把 6 个样本按 base64 的 6-bit 档位切开（36 字符 = 36 档位）：

```
36 个档位，每一位的取值种类：
  档位 0: 5 种    档位 1..13: 6 种    档位 14,15: 5 种
  …（全部 36 位都是 5~6 种）

所有样本都相同的档位：0 / 36
```

各档位「最常见字符占比」的平均值 ≈ **0.17**

### 1.2 这个数字的含义

```
若明文全随机  -> 期望值 = 1/6 ≈ 0.167
若明文全固定  -> 值 = 1.0

实测 ≈ 0.17  ⇒ 【明文高度随机】⇒ 极可能是【哈希】或【加密输出】
```

### 1.3 为什么数学上不可解

```
未知量：
  · 自定义字母表 = 64!（约 1.27 × 10^89）
  · 27 字节明文（每台设备不同）

约束（只有 6 个样本）：
  · 每个样本 36 个字符 = 216 个字符观察
  · 但明文高度随机 ⇒ 字符之间【没有可利用的重复结构】

解空间远大于约束 ⇒ 无解。
（这不是"算力不够"，是信息不足：没有【已知明文-密文对】，
  base64 这类分组编码无法从密文反推字母表。）
```

**⇒ 结论：字母表穷举这条路数学上不成立，不必再投入。**

## 二、★ 转向算法侧：思路与已做的尝试

### 2.1 思路（正确的那条）

```
不猜编码，去【看代码】：
  1. 找到「生成 mIS 的那个函数」
  2. 看它的输入是什么 —— 设备特性？签名？时间？服务端下发？
  3. 从那里判断它能不能被本地复现
```

### 2.2 已做的两次尝试

**尝试 1：找 SDK 里的 64 字符字母表常量**

```
find_encoder.js：
  · 钩 android.util.Base64 的 encodeToString / encode / decode（记录输入输出）
  · 在 libdu.so / libshuzilm.so / libszlm.so / libcrypto.so 的 rodata 里
    找「60~68 长、字符互不重复」的串

结果：只找到 libcrypto.so（base=0x7108ec4000），候选字母表 0 个；
      随后 app 掉线（frida.TransportError: the connection is closed）
```

**尝试 2：扫所有模块**

```
find_alphabet2.js：
  · 遍历 Process.enumerateModules()（351 个模块），不硬编码模块名
  · 每扫完一个模块 setImmediate 让出主线程，单段上限 4MB

结果：打印了优先模块列表后就【停住】——
      351 个模块 × 每个十几 MB 的 rodata，frida 侧扫描把进程拖垮了
```

### 2.3 环境瓶颈（这是当前的主要障碍）

```
① app 极不稳定：反复重启、pid 一直变
② frida 大范围内存扫描 / Memory.scanSync 会让进程掉线
   （前面几次：1335 段 / 2104MB → 超时；这次 351 模块 → 进程掉）
③ mIS 只在 SDK 初始化那一次计算 —— 想抓它就得让初始化发生，
   而初始化只在「首次安装 / 清数据后」发生（mdna 触发问题，已多轮验证）
```

## 三、★ 一个必须先回答的前提问题（它决定还要不要继续）

```
如果 mIS 是【服务端在注册时下发】的，那么：
   · 客户端侧【不存在】"生成算法"可逆向
   · 能做的只有「抓下来 / 读下来」，而这两条路前面都验证过

如果 mIS 是【客户端算】的，那么：
   · 一定存在一个输入集合（设备特性/签名/时间/随机），
     而它每台设备每次注册都不同 —— 说明输入里含【随机数】或【时间】
   · 那样的话，服务端不可能预先"登记"它 ——
     但实测「自造 mIS 全 0」，说明服务端确实在查登记表
   · ⇒ 侧面支持「服务端下发 / 服务端参与生成」
```

**⇒ 现有证据更支持「服务端参与」。这降低了继续逆向的期望值。**

---

## 四、如果还要继续，最有价值的一步（我建议的做法）

```
先做【最小验证】：确认 mIS 是不是「注册响应里下发」的。

方法（成本低）：
  1. 在设备上把 com.coolapk.market 的 dna.xml + prefs 删掉
  2. 挂钩【所有】SSL_read（把响应体存下来）
  3. 触发一次注册（am start；若不行就 pm clear 后启动）
  4. 事后搜所有响应体里有没有出现【当时 mdna 请求里那个 mIS 值】

  或者更直接：把 mdna 请求的 mIS 记为 M，
  然后在【之后**的任何一个响应】里搜 M ——
     · 找到 ⇒ 服务端下发（逆向结束，结论明确）
     · 找不到 ⇒ 客户端生成（值得继续找入口函数）

这条验证只需要一次成功抓包（不用触发多次）。
```

**注意**：这条依赖「能成功抓一次请求」，而这是当前的最大瓶颈。
