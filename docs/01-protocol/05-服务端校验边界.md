# 服务端语义实验结果 —— `h` 是自由值

> 起因：`h` 的算法已解出（见 `H_ALGORITHM.md`），但「服务端是否真的按这个公式校验」
> 一直没验证。本轮把它测了，**结论是否定的**：服务端根本不解析 `h`。
>
> 日期：2026-10-03 ｜ 方法：用设备真机抓到的原始 body 回放，只改单个字段（变量隔离）

---

## 一、实验方法（为什么可信）

```
样本   _rev/dump/wire_m58_REQ_9_len1745.bin      （D2 真机发过的 mdna 请求，body 1398 字节）
载体   PC 侧 HTTPS 直连 auni.telecome.cn（已实测可拿到 200 + 真响应）
变量   每次只改一个字段，其余全部保持原样
自校验 解出 JSON 再重编码 body == 原始 body（逐字节）→ 保证改写实验可信
```

**自校验通过**：`encode_body(decode_body(raw)) == raw` → True。这是本实验的前提，
否则「改了字段却不知道变了几处」，结论不成立。

---

## 二、实验 A：`h` 的 8 种取值，全部被接受

样本 `wire_m58_REQ_9`（mdna，原生 `h=0`）与 `wire_m58_REQ_26`（dcc2，原生 `h=F7AAD8CD…`），
各测 8 个变体：

| 变体 | mdna | dcc2 |
|---|---|---|
| 原值（对照） | 200 | 200 |
| `h=0` | 200 | 200 |
| `h=随机 32hex 大写` | 200 | 200 |
| `h=全 0（32 位）` | 200 | 200 |
| **`h=` 另一台设备（D1）的 h** | **200** | **200** |
| `h=` 空 | 200 | 200 |
| `h=` 真值的小写形式 | 200 | 200 |
| `h=` 真值但少一位 | 200 | 200 |

**16/16 全部 200，响应体逐字节相同**（mdna 204 字节、dcc2 259 字节）。

### 结论

```
★ 服务端【不解析 h】。h 是自由值。
```

连「另一台设备的 `h`」都能通过 —— 说明连「h 与 DUID 是否匹配」都不校验。

**实践含义**：构造上报请求时，`h` 可以随便填（填 `0` 也行）。它不影响服务端行为。
也就是说 —— **一开始担心的「两台设备 h 不一样」这件事，对服务端没有任何影响。**

## 三、实验 B：URL 里只有 `v` 被校验

既然 `h` 不解析，那 DUID 从哪来？逐项变 URL 参数（mdna）：

| 变体 | HTTP | 结果 |
|---|---|---|
| ① 原样（对照） | 200 | 真 DUID |
| ② `p`=随机 32hex | 200 | 真 DUID |
| ③ `p`=去掉 | 200 | 真 DUID |
| ④ `p`=空 | 200 | 真 DUID |
| ⑤ `p`=按别的包名算的 p | 200 | 真 DUID |
| ⑥ `r`=去掉 | 200 | 真 DUID |
| ⑦ `r`=全 0 | 200 | 真 DUID |
| ⑧ `n`=99 | 200 | 真 DUID |
| ⑨ `l`=99 | 200 | 真 DUID |
| ⑩ `n` 与 `l` 都去掉 | 200 | 真 DUID |
| **⑪ `v`=0** | **400** | **被拒（空响应）** |
| ⑫ `t`=x | 200 | 真 DUID |

```
★ URL 里只有 v（协议版本）被校验；p / r / n / l / h / t 全都不解析。
```

**这同时证实了档案里早就记录过的两条**：
- `R_IS_FREE.md` —— `r` 自由（本轮再确认，去掉/全 0 都行）
- `p` 虽然算法解出了（`MD5(包名.37be8a1ee106979a)`），但**服务端不校验它**

## 四、实验 C：真正的判据是 body 里的 `DUv`（包名）

`mdna` 的 body 里**没有 DUID**，也没有 `MD5(DUID)` / `SHA1(DUID)` / `MD5(DUID.889e0b01)`
的任何形式（全查过）。所以对 87 个叶节点里的候选字段做局部改写：

| 改的字段 | 结果 |
|---|---|
| `AYk` / `P1J`（`6F824D:502156:160A84`） | 无变化 |
| `R3d`（机型 `XTQ_Watch`） / `R37`（厂商 `sprd`） | 无变化 |
| `LAh` / `K5f` / `ne8` / `w91` / `gEd` / `6yY` / `wSK`（IP） | 无变化 |
| **`DUv`（包名）** | **★ `n_a` 立刻变成 36 个 0** |

### 边界测试

| `DUv` 取值 | `p` | 结果 |
|---|---|---|
| `com.coolapk.market` | 原值 | 真 DUID |
| `com.example.foo` | **按该包名算出的正确 p** | **全 0** |
| `com.example.foo` | 原值 | **全 0** |
| `com.coolapk.market` | **随机 32hex** | 真 DUID |
| `com.coolapk.market` | **删掉** | 真 DUID |
| `com.coolapk.market.`（加一个点） | 原值 | **全 0** |
| `COM.COOLAPK.MARKET`（大写） | 原值 | **全 0** |
| `coolapk.market`（去 `com.`） | 原值 | **全 0** |
| `com.coolapk.market `（末尾带空格） | 原值 | 真 DUID（服务端 trim 了尾部空白） |

```
★ 判据 = body.DUv 精确等于 "com.coolapk.market"（大小写敏感、前缀不匹配）
★ URL 的 p 完全不参与（哪怕把 p 算成「与新包名一致」也没用）
```

## 五、与既有结论的关系（互相印证）

### 5.1 解释了 SDK 探针为什么拿全 0

`SZLM_SDK_SIGNING_VERDICT.md` 记录：把官方 SDK 装进 `com.example.c001apk`，
拿到 36 个 0；装进官方酷安则拿到真 DUID，**两边 apiKey 一样、assets 一样、设备一样**。

本轮实验给出了同样的现象与更简的解释：

```
body.DUv = com.example.c001apk  →  服务端判「不是这个应用」→ 返回 36 个 0
```

即：**不是 apiKey 与包名绑定，而是服务端拿 body 里的 `DUv` 直接判定应用身份。**
四轮 frida 伪装之所以都失败，本质是在跟这一条打交道 —— 而它只需要改一个 body 字段
就能复现（本实验做的事），反过来也说明：**真要让别的包名拿到 DUID，只能伪造
`DUv` + 签名**，与档案的最终判断一致（签名才是硬约束）。

### 5.2 修正一条此前含糊的表述

| 此前 | 本轮 |
|---|---|
| 「服务端做 URL↔body 完整性绑定，改任一字节即 400」（`CURRENT_BLOCKER.md`） | **不成立**（至少对本端点的 body）。本轮改了 12 个 body 字段 + 12 种 URL 参数，**只有 `DUv` 改变语义、只有 `v=0` 被拒 400**。其余全部 200 且响应一致 |
| 「`h` 是身份声明，可能承担校验」 | **`h` 完全不校验** |
| 「`p` 是设备指纹，服务端用它索引 DUID」 | **`p` 不校验**（算法对，但不是服务端的判据） |

## 六、`h` 的最终定性

```
h = MD5(DUID + "." + "889e0b01").upper()      ← 客户端实现就是这样（三条证据）
                                              ← 但【服务端不校验它】
```

**它是客户端的实现细节，不是协议要求。**

这对几个具体目标的影响：

| 目标 | 影响 |
|---|---|
| 新设备取 DUID | `h` 随便填。真正要满足的是 `body.DUv == "com.coolapk.market"` + 签名 |
| 「两台设备 h 不一样」 | 对服务端无影响，不需要关心 |
| 伪造上报请求 | 不必复现 `h` 的算法，省掉一个验证环节 |
| 反推「服务端认什么」 | 指向 **包名 + 签名**，与 `SZLM_SDK_SIGNING_VERDICT.md` 的最终结论一致；`h`/`p`/`r`/`n`/`l` 都不是 |

## 七、新增脚本

| 脚本 | 用途 |
|---|---|
| `h_semantics_probe.py` | `h` 的 8 变体实验（mdna + dcc2 两组） |
| `p_semantics_probe.py` | URL 参数逐项实验，定位真正被校验的参数 |
| `anchor_probe.py` | body 字段逐项改写，定位设备判据（含重编码自校验） |
| `duv_probe.py` | 钉死「包名 vs p」的边界（精确相等 / 大小写 / trim） |

四个脚本都自带**重编码自校验**（`encode_body(decode_body(raw)) == raw`），
不通过就直接终止 —— 避免在错误的编码上得出错误结论。
