## 一、方法上的两次自我纠错（先说，因为直接影响可信度）

### 纠错 1：leaf 路径 vs 真实键名（`field_boundary_probe.py` 第一版整体作废）

第一版把测试字典的键写成 leaf 路径形式 `"/DUv"`、`"/75c"`，
而 body 里真实的键是 `"DUv"`、`"75c"`（没有前导 `/`）。

后果：23 个用例全都在**新增字段**而不是改写目标字段 → 全部拿到真 DUID
→ 表面上像是「所有字段都不校验」，**结论完全错**。

**修法**：现在脚本开头有键名断言，KEY 不在 body 里就直接终止并打印真实键名。

### 纠错 2：浮点往返丢精度（`refine_probe.py` 的 `2cO` 那一列整体作废）

```python
float("1790969185.997397935")  再格式化回去  →  "1790969185.997397899"
                                                    ^^^^^^ 纳秒丢了 36
```

连「原值」都没还原对，所以那一列全是「全 0」，不能说明任何问题。

**修法**：`ts_probe.py` 改用纯字符串运算（秒部分整数加偏移、纳秒从原串直切），
并且发送前先断言「重建后的原值 == 原始字符串」（实测 True 才继续）。

> 这两条都是「观测/构造本身有问题 → 结论无效」的同一类错误，
> 和 `PROJECT_README.md` §3.5 / §3.6 记录的两条是同源的。

## 二、全字段扫描结果：87 个叶节点里只有 4 个会被读

`mdna` 的 body 共 **87 个叶节点**（78 个顶层字段，含 `iYB` / `7S2.0` / `G8U` / `msg` 嵌套）。
逐个改成哨兵值（数值→`424242`，字符串→`"ZZSENTINELZZ"`）：

```
改变服务端行为的字段（4 个）：
    DUv     包名
    3mS     SDK 版本
    2cO     时间戳
    75c     apiKey

其余 83 个：改了完全无影响（响应逐字节相同）
    含 机型(R3d) / 厂商(R37) / MAC 三元组(AYk,P1J) / IP(wSK) / 语言(fPV)
        / 网络类型(zpA) / 时间戳字段(Qg1,LMi,za7) / 各种混淆串(52J,Bos,IJK,…)
```

**⇒ 服务端只读 4 个字段。** 这一条把「要伪造哪些字段」从 87 个压到 4 个。

## 三、四个字段的精确画像

### 3.1 `DUv` —— 应用身份（要求精确值）

| 取值 | 结果 |
|---|---|
| `com.coolapk.market` | 真 DUID |
| `com.coolapk.market.`（加一点） | 全 0 |
| `com.coolapk.market2` | 全 0 |
| `COM.COOLAPK.MARKET`（大写） | 全 0 |
| `coolapk.market`（去 `com.`） | 全 0 |
| `com.coolapk.market `（末尾空格） | 真 DUID（服务端 trim 尾部空白） |
| 空串 | 全 0 |

```
⇒ 精确等于 "com.coolapk.market"，大小写敏感、前缀不匹配
```

### 3.2 `75c` —— apiKey（**可缺省**，但给了就必须对）

| 取值 | 结果 |
|---|---|
| 真 apiKey `11e7b222…15eb` | 真 DUID |
| **键整体删除** | **真 DUID** |
| **空串** | **真 DUID** |
| `null` | **真 DUID** |
| 改最后 1 位 | 全 0 |
| 去尾 1 位 / 加 1 位 | 全 0 |
| 大写形式 | 全 0 |
| 前 40 位 / 后 40 位 | 全 0 |
| 全 0（42 位）/ 42 个 `a` | 全 0 |

```
⇒ 逻辑是「if (75c 非空) then 必须精确等于该 apiKey」——
   缺省/空/null 视为「未提供」，跳过校验；一旦给出就必须完全正确。
```

**★ 这是本轮第二个可直接用于伪造的结论**：构造请求时 `75c` 直接**删掉**即可，
不需要知道 apiKey。（但注意：这属于**服务端对异常输入不够严格**，不是设计意图。）

### 3.3 `2cO` —— 时间戳（时间窗 ±24 小时，且格式要求严格）

用纯字符串重建（不碰 float），以原值为基准做偏移扫描：

| 偏移 | 结果 |
|---|---|
| `0`（原值） | 真 DUID |
| `+1s` / `-1s` / `+10s` / `+60s` | 真 DUID |
| `±3600s`（±1h） | 真 DUID |
| `±86400s`（±24h） | 真 DUID |
| 换成 now，纳秒保留原格式 | 真 DUID |
| **换成 now，纳秒 = `0`** | **全 0** |
| **纯整数秒（无小数点）** | **全 0** |
| **`秒.0`（小数点后只有 0）** | **全 0** |
| 空串 | 全 0 |

```
⇒ ① 是【时间窗】不是精确值：±24h 内都能过（与 PROJECT_README 阶段七的观察一致）
⇒ ② 格式要求：必须是 "秒.纳秒" 且【纳秒部分非零】——
      "1790987724.0" 和 "1790969185" 都被拒
```

**为什么 `xxx.0` 会被拒**（推断，未验证）：服务端可能按 `strchr('.')` + 校验小数段长度/非零，
或把纳秒解析成整数后要求非零。无论哪种，**造时间戳时必须给一个非零的小数部分**。

### 3.4 `3mS` —— SDK 版本（格式 + 下界）

| 取值 | 结果 |
|---|---|
| `v9.0.1`（原值） | 真 DUID |
| `v9.0.0` / `v9.0.2` / `v9.1.0` / `v10.0.1` | 真 DUID |
| `v8.0.1` | **n_a 为空** |
| `V9.0.1`（大写 V） | **n_a 为空** |
| `9.0.1`（无 v） | **n_a 为空** |
| `v1.0` | **n_a 为空** |
| 空串 | **n_a 为空** |

```
⇒ 要求 v 前缀（小写）+ 版本号 ≥ 9.x（下界，疑似 SDK 最低支持版本）
```

## 四、必要字段集合（可直接用于构造请求）

```
必须满足：
  URL.v         与端点匹配（v=0 → 400）

类型注意：
  任何字段用【数字】替代【字符串】→ HTTP 400（服务端会解析 JSON 类型）
```

## 五、与既有结论的关系

| 既有说法 | 本轮 |
|---|---|
| 「服务端做 URL↔body 完整性绑定，改任一字节即 400」 | **不成立**。改 body 只有两种情况：① 改到 4 个关键字段 → 200 + 全 0；② 类型改错 → 400。其余改动毫无影响 |

## 八、★★★ 重要修正：改值实验 vs 删字段实验，结论不同

### 8.1 三种「失败形态」是不同的东西

`mdna` 的响应有三种状态，含义完全不同：

| 响应 | 含义 |
|---|---|
| `n_a = DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9` | **成功**（真机 DUID） |
| `n_a = "000000000000000000000000000000000000"` | **值被判据否掉** —— 请求结构合法，但某个值不合法 |
| `n_a = ""`（空字符串） | **结构不合法** —— 服务端没进业务逻辑（缺字段 / 类型错） |

前一轮 `sweep_all_fields.py` 用的是**改值**（把值换成哨兵），只触发了中间那种；
`minimal_body_probe.py` 用**删字段**，触发的却是第三种 ⇒ 说明存在**结构必需字段**，
而前一轮的判定标准（"改了 n_a 不变 = 不读它"）**不足以推出「可以删」**。

### 8.2 逐字段删除的结果（`required_fields_probe.py`，87 个字段全测）

```
★ 结构必需（删了 n_a 变空）—— 2 个：
      AAA     原值 "v1.0"
      3mS     原值 "v9.0.1"

★ 值必需（删了 n_a 变全 0）—— 3 个：
      DUv     原值 "com.coolapk.market"
      BBB     原值 "v1.0"
      2cO     原值 "1790969185.997397935"

★ 其它 73 个（含 75c）：删掉照样拿到真机 DUID
      含 机型 R3d / 厂商 R37 / MAC 三元组 AYk,P1J / 内网 IP wSK / 语言 fPV /
         网络类型 zpA / 时间戳 Qg1,LMi,za7 / 全部混淆串 52J,Bos,IJK,… / iYB / 7S2 / G8U
```

### 8.3 更正后的正确集合

```
结构必需（必须存在）          2 个：AAA、3mS
值必需（存在且值要对）        3 个：DUv、BBB、2cO
────────────────────────────────────────────────
合计必须处理的              5 个字段（不是 4 个）

其余 73 个                  连删掉都不影响 —— 服务端既不读值，也不要求存在
75c                          同样在「73 个可删」里（与 §3.2 结论一致）
```

### 8.4 三个版本字段是一个「配套组」

```
AAA = "v1.0"     结构必需
BBB = "v1.0"     值必需（但原值以外的值还没测边界）
3mS = "v9.0.1"   结构必需 + 值有下界（≥ v9.0.0，见 §3.4）

⇒ 它们像是同一份「版本声明」的三个位置，服务端要求它们成组出现
```

### 8.5 ★ 由此推翻两条我此前的说法

| 此前说法 | 现在 |
|---|---|
| 「83 个字段服务端根本不读」 | **不准确**。正确的说法是「**删掉也不影响**」—— 但它们是设备指纹，服务端是否**记录**它们，本实验测不出来（只测了「是否影响本次响应」） |
| 「服务端判据包括设备指纹」（见 `SIGNATURE_CHAIN.md` §三 的候选解释） | **不成立**。MAC / 机型 / 内网 IP 全都可以删掉，照样拿真 DUID ⇒ 服务端**不可能**用它们做设备识别 |
| 「`minimal_body_probe` 的 ② 变体 400，说明数值型字段必需」 | 准确说法：那 400 是**改值**导致的（19 个字段被换成字符串）——**值**类型错会 400；而**删掉**不 400 |

### 8.6 于是「服务端靠什么认设备」这个矛盾依然存在 —— 而且更尖锐

```
换 IP            -> n_a 不变（ip_switch_probe.py）
删 73 个字段     -> n_a 不变（含 MAC / 机型 / 内网 IP）
只留 5 个必需字段 -> n_a 变空（因为还缺别的结构必需字段）

⇒ 请求里没有任何【逐设备唯一】的东西被服务端使用
⇒ 但服务端返回了一个【逐设备唯一】的 DUID（三星 vs 手表不同）
```

**剩下的可能**（未验证，按可能性排）：

```
① 服务端把「这份请求内容」本身当 key，返回它首次见过时登记的那条记录。
   我们的回放字节 = 手表发过的字节 ⇒ 命中手表那条记录。
   这能解释全部现象：换 IP 不变（key 是内容）、删字段不匹配（key 变了）。
   验证法：把任一【非必需】字段改一个字节（如某个混淆串里的一个字符），
           看 n_a 是否变成全 0 或别的值。若变 ⇒ 内容就是 key。

② 某条我们没测到的 HTTP 层信息（如 TLS 会话、SNI、连接复用状态）。

③ 服务端就是按应用身份返回「该应用最近登记的那台设备」——
   家用 IP 下只有手表最近注册过，所以拿到手表的。
```

**① 是本轮最该接着做的实验**：改一个「无关」字段的**一个字符**（不是删、不是换整段），
看 `n_a` 是否变化。这能把「内容即 key」这条测掉。

## 九、★ 「内容即 key」假设**已被测掉**（`key_probe.py`）

对 32 个「删掉无影响」的字段，各改**一个字符**（等长、只动 1 个字节）：

```
LAh   TTTTTTTU        -> TTTTQTTU         真 DUID 不变
yzW   P(:432*R2)3<... -> P(:432*R2)3<...  真 DUID 不变
AYk   6F824D:502156:160A84 -> 6F824D:502Q56:160A84   真 DUID 不变
P1J   同上                                真 DUID 不变
R3d   XTQ_Watch       -> XTQ_Qatch        真 DUID 不变
R37   sprd            -> spQd             真 DUID 不变
wSK   10.0.0.7        -> 10.0Q0.7         真 DUID 不变
...（共 32 个字段，全部「真 DUID 不变」）
h6Z   酷安             -> 酷Q               真 DUID 不变
```

**⇒ 那 73 个字段对服务端完全不可见**：既不读值、也不要求存在、更不参与匹配。

### 9.1 于是之前的候选解释全部被排除

```
✗ 出口 IP                       —— 换 IP 不影响（ip_switch_probe.py）
✗ 设备指纹字段（MAC/机型/IP…）    —— 删掉/改一个字符都不影响（§八、§九）
✗ 整份 body 内容作为 key          —— 改一个字符不影响（§九）
✗ URL 的 p/h/r/n/l              —— 全不校验（H_SEMANTICS_RESULT.md）
✗ 任何 HTTP 头                   —— 21 组变体全无影响（SIGNATURE_CHAIN.md §一）
```

**请求里唯一被服务端使用的，只剩 5 个字段：**

```
AAA (结构必需) / 3mS (结构必需) / DUv (值必需) / BBB (值必需) / 2cO (值必需)
```

而这 5 个字段**没有任何一处是逐设备唯一的** —— 全是包名 + 版本号 + 时间戳。

### 9.2 那 DUID 为什么逐设备唯一？（新的核心矛盾）

```
三星 SM-F731N 跑 c001apk  -> DU1aXs5bbgJWPceuTiqkk7KwFezP72yRDrg7
我们的手表 XTQ_Watch      -> DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9
```

两者在同样 5 个字段下（`DUv=com.coolapk.market`）拿到的 DUID 不同。
**但请求里没有任何足以区分这两台设备的信息。**

⇒ 剩下的解释只能在这三者里（都未验证）：

```
① 那台三星实际用的不是这套 5 字段规则
   · 它跑的是 c001apk + SDK v8.9.7（09-19 的日志），我们现在测的是官方酷安 + v9.0.1
   · 三星有可能是**真的完成了注册**（服务端为其固件/设备建了记录），
     而不是像我们这样「回放一份别人的字节」

② 我们拿到的 DUID 其实【不是手表专属的】
   · 有可能 `com.coolapk.market` 这个应用身份在服务端只登记过一条记录，
     而「同一应用同一记录」这个组合里恰好只有手表
   · 但三星也声明 com.coolapk.market，若只有一条记录，三星该拿到同一个值
     —— 与观察矛盾
   · ⇒ 除非服务端对「已注册客户端」与「未注册的裸请求」走不同分支

③ 首次注册阶段（客户端真的调 DUHelper 那一次）才建立设备记录，
   而记录靠的是 native 层的完整指纹 —— 那一层的输入我们看不到（`libdu.so` 内部）
```

### 9.3 一个能直接判定 ② 的实验（成本很低）

```
用一台【从未装过酷安】的干净设备/环境，用同样 5 个字段的请求发一次：
  · 若返回同一个 DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9
      ⇒ 服务端对这个应用身份只返回「那一条记录」，与设备无关
      ⇒ 也说明：**任何人拿到这 5 个字段 + 包名，都能复用这份 DUID**
  · 若返回全 0 或别的值
      ⇒ 服务端有设备维度，且判据在当前观测之外
```

**其实这个实验已经间接做过一次**：本机 `curl`（PC、非手表、非安卓）
用这 5 个字段就拿到了手表的 DUID ⇒ **偏向「①/② 中『服务端就用这 5 个字段』那一支」**。

⇒ **当前最保守的结论**：

```
在「回放一份已注册请求」这个场景下，
服务端只需要 5 个字段（AAA/3mS/DUv/BBB/2cO）+ 应用身份，
就会返回该应用身份对应的那条 DUID 记录。
请求侧不存在任何签名或设备绑定校验。
```

（至于「那台三星为什么拿到不同值」，需要它的完整抓包才能判 —— 目前没有。）
