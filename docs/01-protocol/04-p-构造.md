# ★ 破解成功：p 的算法完全还原

## 一、最终结论

```
p = MD5( 包名 + "." + suffix )
```

**本机实测（已字节级验证）**：

```python
>>> import hashlib
>>> hashlib.md5(b"com.coolapk.market.37be8a1ee106979a").hexdigest().upper()
'F9BD0FBDACFE80FCF34370FBCFEE1A98'
```

对应真机抓到的实际请求：

```
POST /a/mdna/report?v=8.7&t=m&p=F9BD0FBDACFE80FCF34370FBCFEE1A98&r=...&n=0&l=2&h=0
```

**完全一致。**

---

## 二、怎么抓到的

### 关键转折：从 Java 层转向 native 层

Java 层的四次崩机说明「在热路径上做重活」不可行：

| 尝试 | 结果 |
|---|---|
| `memcpy` / `strcpy` / `strncpy` / `strcat` | 酷安 5 秒 ANR |
| `okhttp3.RequestBody.writeTo`（含递归 bug） | 所有应用卡退 |
| `java.io.OutputStream.write` | 所有应用崩 |
| `Java.array` 复制 ByteBuffer | 所有应用崩 |

### 找到正确的 hook 点

从 `SSL_write` 的调用栈断在 `libjavacrypto.so` 得到线索，拉取该 so 分析，发现它导出标准 OpenSSL 符号：

```
EVP_DigestUpdate      ← 哈希数据输入（x0=ctx, x1=data, x2=count）
EVP_DigestFinal_ex    ← 哈希完成（x0=ctx, x1=md输出, x2=size）
EVP_DigestInit_ex
EVP_md5
```

**native hook 不经过 JNI 边界，开销极低**，实测 90 秒 1263 次调用，进程毫发无伤。

### 一个关键的实现细节

**必须在 `EVP_DigestUpdate` 调用的当下就把内容读出来。**

第一版只记录了指针，到 `EVP_DigestFinal_ex` 时才回读，结果拿到的是**内存复用后的残骸**：

```
74e4653574000000 a0446b3474000000 f8671b3174000000 c062c43374000000 f8671b
（每个 8 字节的高 4 字节都是 0x00000074 —— 明显是地址残骸）
```

改成 `update` 时即时 `readByteArray` 后，立刻拿到了正确内容。

## 三、算法结构详解

### 完整公式

```
p = MD5( 包名 + "." + suffix )
        ^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^
        com.coolapk.market   16 位 hex
```

- **包名**：`com.coolapk.market`（即调用方的包名）
- **分隔符**：一个英文句点 `.`
- **suffix**：16 位小写 hex（8 字节），**每台设备固定不变**
- **编码**：MD5 输出转**大写** hex

### suffix 的性质（实测）

| 性质 | 观测 |
|---|---|
| 长度 | 16 hex = 8 字节 |
| 稳定性 | **恒定** —— 跨请求、跨会话、跨 `pm clear`、跨重启都不变 |
| 依赖 `android_id` | **否**（改过，`p` 不变） |
| 依赖 `serialno` | **否**（改过，`p` 不变） |
| 依赖机型/品牌/厂商 | **否**（改过，`p` 不变） |
| 依赖 App 本地数据 | **否**（`pm clear` 后不变） |
| 依赖 MAC | **否**（数盟根本不读 MAC） |

### 与数盟其他标识的关系

数盟内部统一使用 **`MD5(x)[:16]`** 这个模式。已验证的一例：

```
boot_uuid = fb58c4b7-8f4f-48c8-8e08-40981d23edf2
MD5(boot_uuid)[:16].upper() = D346BC4F2F4C6009
```

而这个值在数盟上报数据里原样出现过（hook MD5 实体时抓到 `boot_uuid` 值 + `D346BC4F2F4C6009` 成对出现）。

**所以 suffix 极可能也是 `MD5(y)[:16]`，只是 y 尚未采集到。**
（尝试 hook 匹配 `MD5(*)[:16] == 37be8a1ee106979a` 未命中，说明它可能在数盟进程启动早期就算好了。）

## 四、`p` 在协议中的位置

回顾之前还原的完整请求格式：

```
POST /a/mdna/report?v=8.7&t=m&p=<p>&r=<32位小写hex>&n=0&l=2&h=0
Content-Length: <n>
Content-Type: application/x-www-form-urlencoded
User-Agent: Dalvik/2.1.0 (Linux; U; Android 9; XTQ_Watch Build/PPR1.180610.011)
Host: auni.telecome.cn
Connection: Keep-Alive
Accept-Encoding: gzip
```

- **`p`** = `MD5(包名 + "." + suffix)` —— **本次破解**
- **`r`** = 每次随机，32 位小写 hex
- **`h`** = `mdna` 用 `0`，其余端点用固定值

**`p` 是设备标识**，服务端靠它认设备。

## 五、现在能做什么、不能做什么

### 能做的

**给定任意一台设备的 suffix，可以用纯 Python 算出它的 `p`：**

```python
import hashlib

def calc_p(package_name: str, suffix: str) -> str:
    """suffix 为 16 位 hex"""
    return hashlib.md5(f"{package_name}.{suffix}".encode()).hexdigest().upper()

assert calc_p("com.coolapk.market", "37be8a1ee106979a") == "F9BD0FBDACFE80FCF34370FBCFEE1A98"
```

**不需要 SDK、不需要 frida、不需要 hook。**

### 不能做的

**无法为一台「新设备」凭空造出有效的 `p`** —— 因为 suffix 来自设备本身，
而它的具体来源（哪个硬件标识或系统值的派生）还没定位到。

这其实正是数盟的设计意图：**`p` 不可伪造，只能从真实设备上读出来。**
