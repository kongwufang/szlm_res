# p（设备指纹）构造链还原报告

目标：还原数盟上报参数 `p = F9BD0FBDACFE80FCF34370FBCFEE1A98` 的计算方式，
     以便用纯自研代码复现「上报新指纹 → 换取新 DUID」。

---

## 一、静态分析：p 的构造链（已完全确定）

`libdu.so` 反汇编结果：

```
0x13bf74  bl 0x1143bc              ; strDec -> fmt
0x13bf78  mov x27, x25
0x13bf7c  mov x25, x0              ; 保存 strDec 结果
0x13bf80  ldr x0, [x19, #0xf0]
0x13bf84  bl 0x1143bc              ; strDec -> d2
0x13bf88  ldr x4, [x19, #0x198]    ; snprintf 第4参 = d1
0x13bf8c  mov x5, x0               ; snprintf 第5参 = d2
0x13bf90  add x0, x19, #0x4c0      ; 输出缓冲
0x13bf94  mov w1, #0x100           ; size = 256
0x13bf98  mov w2, #0x100           ; size = 256
0x13bf9c  mov x3, x25              ; fmt
0x13bfa0  bl 0x134944              ; snprintf
0x13bfa4  add x1, x19, #0x4c0      ; 输入 = snprintf 产物
0x13bfa8  mov x0, x26              ; 输出
0x13bfac  bl 0xe23c4               ; MD5 包装
0x13bfb0  mov x25, x0              ; => p
```

**公式**：

```
p = MD5( snprintf( strDec(slot_a), ctx[0x198], strDec(ctx[0xf0]) ) )
```

- `fmt = strDec(slot_a)` —— 运行时解密的格式串
- `d1 = ctx[0x198]` —— 对象上下文字段
- `d2 = strDec(ctx[0xf0])` —— 运行时解密的字符串
- `ctx` = `x19`，是某个 C++ 对象的 this 指针

紧随其后的 `0x13bff4`（strDec）+ `0x13c014`（snprintf）+ `0x13c020`（局部函数 `0xf53f0`）
是 `r` 的构造，`p` 作为第 4 个参数进入。

## 二、hook 安全性实测（关键）

| 地址 | 功能 | 结果 |
|---|---|---|
| `0x13bfa0` | snprintf（p 的格式化点） | **危险** — `script.load()` 时连接直接断开 |
| `0x13bfac` | MD5 包装（p 的哈希点） | **安全** — 正常装载 |
| `0x13bf74` / `0x13bf84` | 两次 strDec | **安全** |
| `0x13c014` | snprintf（r 的格式化点） | **安全** |
| `0xe1de4` | MD5 实体 | **安全** |

`0x13bfa0` 被完整性校验保护，挂它会触发检测。**这是本次唯一被挡住的关键点。**

## 三、抢注时序（技术要点）

**必须用同步的模块观察器，不能用轮询：**

```js
Process.attachModuleObserver({
  onAdded: function (mod) {
    if (mod.name === 'libdu.so') installHooksNow(mod.base);   // 同步立刻装
  }
});
```

**原因**：`p` 在 `libdu` 构造期就算好了。用 `setInterval` 每 500ms 轮询，
等发现 `libdu` 时它的构造期早已跑完。改用观察器后立刻抓到了 160 条指纹采集调用。

## 五、离线爆破 p 的结果（全部失败）

用 25 个已知设备标识，尝试：

| 轮次 | 方法 | 组数 | 结果 |
|---|---|---|---|
| 1 | 单值 + 大小写变形 | 125 | 未命中 |
| 2 | 双值组合（14 种分隔符、双向） | 8400 | 未命中 |
| 3 | 三值组合（6 种分隔符） | 82800 | 未命中 |
| 4 | 加盐（salt / 包名 / apikey 等 13 种） | 650 | 未命中 |
| 5 | JSON 规范化（2–4 字段组合） | — | 未命中 |

**结论**：`p` 的输入不是这些标识的简单组合，**而是经 `strDec` 运行时解密的格式串 + 上下文对象字段**。
这正是静态分析给出的结论——输入里有运行时才存在的值，无法离线推算。

## 六、未完成的部分与原因

**`p` 的计算点没触发。** 观察日志显示点「同意协议并继续」后**进程重启了**（日志里 pid 变为 5337），
而 hook 是装在重启前的实例上的，新实例上没有 hook。

**修正方向**：在 `capture_timing.py` 的循环里检测 pid 变化后，
必须**重新 attach + 重新 load 脚本 + 重新触发**。当前脚本有重连逻辑，但新脚本需要保持同样的重连时机。

## 八、离「纯自研实现」还差什么

**两个未知量**：

1. **`p` 的输入三元组**（fmt / d1 / d2）—— 修好重连时序后一次可抓全
2. **请求体加密密钥** —— 响应 key 已知，请求 key 不同

拿到这两个，就能用纯 Python 完整复现：构造任意指纹 → 算出 `p` → 加密 body → 发请求 → 取回新 DUID。
全程不需要 SDK、不需要 frida。
