# `h` 参数逆向 —— 完整结论

> 状态：**算法已完全解出**（三级独立证据）。本文件把「证据链」和「它是什么」分开写清楚，
> 并记录一个本轮新发现的结构性质（`h` 与端点无关）。
>
> 日期：2026-10-03 ｜ 设备：D1 `TK Watch`（Android 8.1 / API 27）、D2 `XTQ_Watch`（Android 9 / API 28）

---

## 一、算法本体（最终形态）

```
h = MD5( DUID + "." + "889e0b01" ).upper()
       │              │
       │              └─ 常量，libdu.so 字符串池 池地址 0x0feb2c，形态是模板 "%s.889e0b01"
       └─ 运行时值：服务端签发的设备唯一 ID（36 字符，DU 开头）

输出：32 位大写十六进制
```

**首次注册时 `h = "0"`**（字符串零，不是 32 个 0）—— 因为那一刻还没有 DUID。

### 1.1 三条独立证据（互相印证）

| # | 证据类型 | 具体内容 | 原始出处 |
|---|---|---|---|
| 1 | **池里的模板** | `0x0feb2c  "%s.889e0b01"` —— 从 libdu 加密串池解出，`%s` 位就是要填的 DUID | `pool_plain.txt:1907`、`slot_strings.txt:2568` |
| 2 | **运行时 MD5 输入** | hook `libdu.so` 的 MD5 实体，实测捕获的输入原文 = `"DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9.889e0b01"` | `mem29_out.txt:146`、`mem29b_out.txt:145` |
| 3 | **离线试算** | `MD5("DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9.889e0b01").upper()` = `F7AAD8CD5824603F7F2200731D8C045D`，与实抓请求里的 `&h=` 逐字符相同 | `_resp_probe_out.txt` |

> 证据 2 的原始行（`mem29_out.txt:146`）：
> ```
> [MD5] 输入指针=0x73afcc0250  字符串="DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9.889e0b01\0\0\0…
> ```
> 注意尾部大量 `\0` —— 说明 libdu 的写法是「先把模板和 DUID 拼进一个定长缓冲、再整块 MD5」，
> 而不是精确长度。这解释了另一个细节：**MD5 的输入长度是按缓冲里的实际 C 字符串算的**，
> 所以不会把填充的 `\0` 也算进哈希（三处证据的哈希值一致即为此佐证）。

### 1.2 调用链（静态）

```
0x407ac（HTTP 流程）
  └─ 0x1447dc（构造 body）
       ├─ 0x143a9c  ★ 计算 h 的地方
       │    ├─ 引用池模板 "%s.889e0b01"
       │    └─ 调用 0xe23c4（MD5 包装）
       ├─ 0x142f68 → 端点分发（11 个端点）
       ├─ 0x13d828 → 序列化/缓冲区填充
       └─ 0x1448b4 → 拼接助手
```

### 1.3 URL 里的位置（池模板 `0x105374`）

```
%s%s&p=%s&r=%s&n=%d&l=%d&h=%s
     │     │     │   │   └── h（本文件的对象）
     │     │     │   └────── l
     │     │     └────────── n
     │     └──────────────── r（32 位小写 hex，每次随机，服务端不校验）
     └────────────────────── p（设备/应用指纹，见下）
```

## 二、`h` 与 `p` —— 一族同构公式

```
p = MD5( 包名 + "." + 常量A )   常量A = 37be8a1ee106979a  （16 hex = 8 字节）
h = MD5( DUID + "." + 常量B )   常量B = 889e0b01          （ 8 hex = 4 字节）
```

### ★ 两条常量在池里是**紧邻**的

`slot_strings.txt` 的转储顺序（同时也能看到 URL 模板）：

```
0x0015c728  v9.0.1
0x0015c730  37be8a1ee106979a      ← 常量A（p 的 suffix）
0x0015c738  %s.889e0b01           ← 常量B（h 的模板）
0x0015c740  %s%s&p=%s&r=%s&n=%d&l=%d&h=%s
```

**三条字符串紧挨着**，说明它们在源码里就是同一个请求构造上下文里的字面量。

### 2.1 两条常量的关系：**没有关系**

本轮做了穷举排查，结论是它们各自独立、都是硬编码的随机 hex：

| 检查 | 结果 |
|---|---|
| 互为子串（`889e0b01` ⊂ `37be8a1ee106979a`？） | ✗ |
| 共享 ≥4 字符子串 | ✗（空集） |
| 是同一 8 字节序列的前半/后半 | ✗（`e106979a` ≠ `889e0b01`，`37be8a1e` ≠ `889e0b01`） |
| 等于某个常见字符串 MD5 的前/中/后 8 位 | ✗（`duid` / `DUID` / `shuzilm` / `cn.shuzilm` / `coolapk` / 包名 / 自身 / 空串 全试） |
| 常量A 等于某串 MD5 的前 16 位 | ✗ |

⇒ **不要试图从一条推出另一条**，两条都要从池里取（`0x102b20` 与 `0x0feb2c`）。

### 2.2 两条常量也**不在**池的其它地方复用

全池（2408 条）里搜：
- `37be8a1ee106979a` 只出现在 `0x102b20` 这一处
- `%s.<8hex>` 形态的模板**全池只有一条**，就是 `%s.889e0b01`
- `889e0b01` 也只出现在这一处

⇒ 没有第二种用法，不存在「同一个盐还有别的用途」这种隐藏路径。

## 三、★★★ 本轮新发现：`h` 是**设备级**的，与端点无关

把 6 个实测请求的 `&h=` 全列出来：

| 端点 | n | l | h | Content-Length |
|---|---|---|---|---|
| mdna（**要 ID**） | 0 | 2 | **`0`** | 1398 |
| d2api | 0 | 2 | `F7AAD8CD5824603F7F2200731D8C045D` | 4001 |
| dcc2 | 0 | 2 | `F7AAD8CD5824603F7F2200731D8C045D` | 546 |
| dai | 0 | 2 | `F7AAD8CD5824603F7F2200731D8C045D` | 1420 |
| audd | 0 | 2 | `F7AAD8CD5824603F7F2200731D8C045D` | 655 |
| daa | 0 | 2 | `F7AAD8CD5824603F7F2200731D8C045D` | 4218 |

**同一个设备的 5 个上报端点，`h` 一字不差。**

这排除了两种常见猜测：

| 猜测 | 是否成立 | 依据 |
|---|---|---|
| `h` 是**请求体**的哈希（签名） | ✗ | 5 个端点 body 长度 546~4218 全不同，`h` 却相同 |
| `h` 是 **端点/路径**的哈希 | ✗ | 路径不同，`h` 相同 |
| `h` 是 **DUID 的持有证明** | ✓ | 只吃 DUID 一个输入；`mdna` 时还没有 DUID，所以是 `0` |

### 3.1 由此得到的语义

```
第一次（mdna）：  "我没有 DUID，请给我一个"        -> h = 0
之后（5 个端点）："我有 DUID，证明给你看"          -> h = MD5(DUID + ".889e0b01")
```

⇒ **`h` 的语义 = 身份声明（identity assertion）**，不是防篡改签名。
这也解释了为什么服务端「改 body 任一字节即 400」的绑定**不是** `h` 承担的 ——
它另有机制（之前档案里记的 `isem`/`denv` 字段更可能是那道校验）。
**把「h 负责防篡改」这个设想从候选里划掉。**

### 3.2 两台设备对照（跨设备验证）

| | D1 `TK Watch` | D2 `XTQ_Watch` |
|---|---|---|
| DUID | `DUaVFlbAMrmH2Z57PEhm_N9EO4RoUdvNstg5` | `DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9` |
| **`h`** | `CA0D929678DB1B51E3B5F2FBFA582002` | `F7AAD8CD5824603F7F2200731D8C045D` |
| **`p`** | `F9BD0FBDACFE80FCF34370FBCFEE1A98` | **相同** |

- **`h` 随 DUID 变** ⇒ 绑定设备
- **`p` 不随设备变** ⇒ 绑定应用（两台 suffix 都是 `37be8a1ee106979a`，因为同一包名同一签名）

D1 的 `h` 是**公式推导值**（该设备的首次注册请求没抓到，原因见
`dev2/TWO_DEVICES.md` §四）；D2 的 `h` 是**实抓值**。

## 四、输出格式的两个细节（已核对）

```
h = MD5(...).hexdigest().upper()      ← 32 位【大写】
```

- **大写**：实测值 `F7AAD8CD5824603F7F2200731D8C045D` 全大写；对照 `r` 是 32 位**小写** hex。
  两者大小写相反，是同一个请求里两个参数的不同约定 —— 抄代码时容易写错。
- **固定 32 位**：MD5 输出固定 16 字节，补零在前（与 `cn.shuzilm.core.aa.a()` 的
  `BigInteger(1,digest).toString(16)` + 补前导 `0` 的写法一致，见 `CRYPTO_ITEMS.md` §1.1）。
  即：**补零在前**，不是在后。

## 五、还没做的实验（唯一剩下的方向）

`h` 的**算法**已经到顶了，剩下的是**服务端语义**——即服务端拿 `h` 做什么。
这需要设备端发包实验（本机 Python 直连恒 400，必须在设备端发）。

| 实验 | 预期 | 能判定什么 |
|---|---|---|
| ① 上报端点发 `h` 的**随机替换值**（如全 0 / 全 F / 随机 32 hex） | 若 200 → 服务端不解析 `h`；若 400/拒绝 → `h` 是真校验点 | `h` 是否被服务端读取 |
| ② 把 `mdna` 的 `h` 从 `0` 改成**任意 32 hex** | 若仍签发 DUID → `h` 在首次注册时被忽略 | 首次注册路径是否校验 |
| ③ 用**另一台设备的 `h`**（D1 的值配 D2 的 DUID）发 | 若被拒 → 服务端确实校验 `h==MD5(DUID+盐)` | **`h` 的绑定关系**（最关键的一条） |
| ④ `h` 正确、但 body 里 `ubF` 改成别的 DUID | 看是否以 body 的 `ubF` 为准 | `h` 与 body `ubF` 是否一致性校验 |

**实验③是唯一能证明「服务端确实按这个公式校验」的**。前三条只需要改 URL 参数，
工程上比改 body 简单得多（设备端发即可）。

**现成的实验脚手架**：`_rev/szlm_send.py`（构造+发送+解响应）、
`_rev/auto_p.js`（设备端 `HttpURLConnection` 发送，已验证能拿 200）、
`_rev/cap_all.js`（`sendall` 批量下发对照请求）。

## 六、一句话总结

```
h = MD5(DUID + "." + "889e0b01").upper()

· 盐 889e0b01 是从 libdu 串池 0x0feb2c 挖出的模板 "%s.889e0b01"，不是猜的
· 计算点 libdu+0x143a9c，MD5 包装 libdu+0xe23c4
· 与 p 同构（p 的盐 @0x102b20），两条常量在池里紧邻、但互相无导出关系
· 输出 32 位大写 hex，补零在前
· ★ 语义：设备级「身份声明」，与端点/body 无关（5 个端点取同一值）
· 首次注册 h="0"
```
