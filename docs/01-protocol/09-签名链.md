# 签名链追查（未果，但排除了两大块）

> 目标：定位「签名校验」在哪。前提是 `FIELD_CRITERIA.md` 已证明
> **body 的 87 个字段里只有 4 个被读，且都是明文比对级别**，没有一处像签名。
>
> 日期：2026-10-03

## 一、排除项 1：签名不在 HTTP 头里

对请求头做了 21 组变量实验，全部**没有任何影响**：

| 变体 | 结果 |
|---|---|
| 完整原始头（对照） | 真 DUID |
| 最小头集（只有 CT + UA + Accept） | 真 DUID |
| 逐个去掉 `Content-Length` / `Content-Type` / `User-Agent` / `Connection` / `Accept-Encoding` | 全部真 DUID |
| `User-Agent` = 空 / `curl/8.0` / `python-urllib/3.12` / 截断的 Dalvik | 全部真 DUID |
| `Content-Type` = `application/octet-stream` / `application/json` / `text/plain` / 空 | 全部真 DUID |
| **加** `device_label` / `X-Sdk-Api-Key` / `apiKey` / `sign` / `X-App-Token` / `X-App-Device` / `X-App-Id` | 全部真 DUID |

**⇒ 请求侧没有任何签名通道。**
`curl` 用最小头集都能拿到真 DUID —— 连特征伪装都不需要。

## 三、那服务端凭什么返回 DUID？—— 两个独立的事实

### 事实 A：返回的 DUID 逐设备唯一（本节初判「应用级」，§五 已更正）

把 szlm 已知的全部 DUID 列出来：

| DUID | 出处 | 设备 |
|---|---|---|
| `DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9` | D2 · 官方酷安 | XTQ_Watch |
| `DUaVFlbAMrmH2Z57PEhm_N9EO4RoUdvNstg5` | D1 · 官方酷安 | TK_Watch |
| `DU1pGU7EXcGo9LQWg8PIHk9uBFUqDjnlVJg6` | Phh-Treble · 官方酷安 | 第三台 |
| `DUS0SE7YX-suVRkHV5dMwUfV-UY1Mw61_Ogc` | `active_out.txt` · `getQueryID` 实测 | 另一台/另一记录 |
| **`DU1aXs5bbgJWPceuTiqkk7KwFezP72yRDrg7`** | **`logcat_pub.txt:35209`** `didCode` | **三星 SM-F731N**（跑 c001apk） |

全部 36 字符。

> ⚠️ **本节最初据此推断「DUID 是应用级的（同一包名只有一条记录）」—— 这个推断是错的。**
> §五 的 `didCode` 证明：三星设备与手表**都声明 `com.coolapk.market`，却拿到两个不同 DUID**。
> 所以 DUID **确实逐设备唯一**，只是请求里找不到对应的设备标识 —— 详见 §五、§七。

### 事实 B：但那台设备**无法发出** DUID 的请求 —— 因为请求里没有它

```
mdna body 的 87 个叶节点  →  没有 DUID，也没有 MD5/SHA1(DUID) 的任何形式
mdna URL 的 6 个参数       →  p/r/n/l/h 全不校验，且都是常量或随机值
请求头                     →  全不校验
```

**矛盾**：服务端返回了一个逐设备唯一的 DUID，而请求里没有任何逐设备唯一的东西
（唯一设备相关的只有 `wSK=10.0.0.7` 这个内网 IP，且改它不影响）。

### 两个候选解释

```
① 出口 IP
   服务端按【应用身份 + 出口 IP】回捞该 IP 下这台设备的登记记录。
   支持：curl 从家里发就能拿到手表的 DUID；真机也是从这个 IP 注册的。

② 服务端首次登记记录 + 请求里未识别的设备标识
   但请求侧已全查过（87 字段 + 6 参数 + 全部头），没找到这样的标识。
```

**⇒ 目前 ① 更可能，但仍需 §七 的换 IP 实验来判定。**

### 待验证的判据实验（唯一能区分「IP」与「服务端记录」的）

```
把 mdna 请求从【另一个出口 IP】发出（如手机热点 / 云端），看是否：
  · 仍返回同一 DUID        --> 判据是「应用身份 + 服务端登记」，与 IP 无关
  · 返回全 0 或别的 DUID    --> 判据包含出口 IP
```

本次没做（需要换网络），但方法很简单：
`_rev/szlm_send.py --ep mdna` 换个网络跑一次，对比 `n_a`。

## 四、顺带发现：只有 mdna 会返回 DUID

三个能解出响应的端点，字段结构完全不同：

```
mdna  (池 0x110DC8)   err / n_a / nctl / ocdd / cdd / o_a / dlab / denv / isem / itime
                      ★ n_a 与 cdd 就是 DUID；dlab 是 device_label
                      ocdd / o_a 是「旧 ID」相关（本次都是空）

dcc2  (池 0x109CF0)   LCS / CdN / 2sW / VrJ / NXF / f1V
                      VrJ 是 192 字符的配置块（会落盘到 prefs）

audd  (池 0x1090F8)   WP3 / YdJ / n9j / Y4c / xGh
                      Y4c 是 32 字节 base64url 的动态 token（会变化）
                      xGh=2592000（30 天，疑似有效期）
```

**⇒ DUID 只在 mdna（「要 ID」端点）下发。** 其余端点只做配置下发与校验。

`ddlab`（`device_label`）在响应里也是常量 `6KYDnLSlcZQV83Yq2P63w==` ——
与两台设备本地 `dna.xml` 里的值一致，再次印证它只依赖包名。

## 五、★★ 重要线索：`didCode` —— SDK 上报的完整设备指纹

`logcat_pub.txt:35209` 里 `ShuzilmSDKManager` 那行日志**远不止一个 DUID**，
它带出了 `didCode` 这个结构化对象：

```
shuzilm did result, result =DU1aXs5bbgJWPceuTiqkk7KwFezP72yRDrg7,
    agreePrivacy=true, useDDI=true,
    didCode={"x1":"0","x2":"fb4a17e6-b3fc-4bd4-8ce6-cd68881e9d4d","x3":"samsung,SM-F731N",
             "x4":"CN","x5":true,"x6":true,
             "x7":"QkRCOTI0Q0IzQUE2QzgyQTA3Nzg3QzNCNDlFOEJCMjZhZTViNWIxZi0wMjFmLTQ3YTItOTA2NC1jOGY2ZmVlODVlYjM=",
             "x8":"wlan0,0,2409:8a55:3850:45d0:f66d:2fff:fe34:af61-10.0.0.1-",
             "x9":35,"x10":"1,74","x0":"1789802842679",
             "x11":"Q0ZDRDIwODQ5NUQ1NjVFRjY2RTdERkY5Rjk4NzY0REEw",
             "x12":"com.coolapk.market","x13":"v8.9.7","x14":""}
```

### 逐字段解码

| 键 | 原文 | 解码后 | 含义 |
|---|---|---|---|
| `x0` | `1789802842679` | — | 毫秒时间戳 |
| `x2` | `fb4a17e6-…-cd68881e9d4d` | — | UUID（未发现与其它字段的哈希关系） |
| **`x3`** | `samsung,SM-F731N` | — | **厂商,机型** → 三星 Galaxy Z Flip5 |
| `x4` | `CN` | — | 国家 |
| `x5` / `x6` | `true` / `true` | — | 布尔标志（疑：隐私同意 / 某项开关） |
| **`x7`** | base64 | `BDB924CB3AA6C82A07787C3B49E8BB26` + `ae5b5b1f-021f-47a2-9064-c8f6fee85eb3` | **`MD5(内容)+内容` 封装**，内容是 36 字符 UUID |
| **`x8`** | — | `wlan0,0,<IPv6>-10.0.0.1-` | 网卡 / **出口 IPv6** / 网关 |
| `x9` | `35` | — | 数值（疑：某项计数或版本） |
| `x10` | `1,74` | — | 两个数值（疑：网络类型,信号） |
| **`x11`** | base64 | `CFCD208495D565EF66E7DFF9F98764DA` + `0` | **`MD5("0")+"0"`** —— 与手表上 `nctl` 同构（手表是 `MD5("2")+"2"`） |
| **`x12`** | `com.coolapk.market` | — | **SDK 对外声明的包名**（而进程实际跑在 `com.example.c001apk` 里） |
| **`x13`** | `v8.9.7` | — | **数盟 SDK 版本** |
| `x14` | （空） | — | 预留 |

### 两点验证（都通过）

```
x7 :  MD5("ae5b5b1f-021f-47a2-9064-c8f6fee85eb3") == BDB924CB3AA6C82A07787C3B49E8BB26   ✓
x11:  MD5("0")                                    == CFCD208495D565EF66E7DFF9F98764DA   ✓
```

**⇒ `MD5(内容) + 内容` 这套自校验封装在 didCode 里同样是通用规则**，
与手表 prefs / 响应字段（`n_a` / `nctl` / `lut` / `ss2` / `clso`）里的完全一致。
这条规则现在有了跨设备、跨来源的第四处独立印证。

### 这个 didCode 改变了什么

#### ① 它不是我们的设备 —— 是一台三星

```
x3 = samsung,SM-F731N     ← Galaxy Z Flip5
x8 = 2409:8a55:...        ← 中国联通 IPv6 段
DUID = DU1aXs5bbgJWPceuTiqkk7KwFezP72yRDrg7
```

**而我们手表上的 DUID 是 `DUFPnec5dST2pTeImYGBClyhOnoUecHYyWg9`。**

⇒ **两台不同设备，在 `x12` 都声明 `com.coolapk.market` 的情况下，拿到的 DUID 不同。**

这**动摇了「DUID 只由包名决定」的简化说法** —— 至少说明：
服务端是能区分设备的（响应里的 DUID 确实逐设备唯一）。

#### ② 它解释了「为什么 c001apk 能跑」——但带一个矛盾

这台三星上跑的是 `com.example.c001apk`（Compose UI），却把
`x12` 声明成 `com.coolapk.market`，**并且真的拿到了一个 DUID**。

⇒ 与 `SZLM_SDK_SIGNING_VERDICT.md` 的「四轮伪装全失败」**看似冲突**。

**可能的调和**（未验证）：

```
· 那台三星上装的 c001apk 版本用的是【官方酷安的签名】或某种等价物；
· 或者 v8.9.7 时代的服务端判据比现在松（日志时间是 09-19，SDK v8.9.7）；
· 或者 x12 只是「声明」，真正的判据在 didCode 之外（如 native 采集的真实包名/签名），
  而那台设备恰好真的满足。
```

#### ③ `x8` 里带出口 IP —— 而且我们回放时也碰到了一个 IP 巧合

`didCode.x8` 明确包含**出口 IPv6 + 网关**，说明**设备侧会主动上报网络位置**。
我们的回放里 `body.wSK = 10.0.0.7`（内网 IP），且改它无影响 ——
但那可能只是因为它不是服务端用的那份。

**⇒ 出口 IP 这条线索的分量上升了。** 与 §三 的推断一致：
服务端很可能按「网络位置 + 应用身份」回捞登记记录。

## 六、另一个未展开的线索：`useDDI`

同一行日志里 `useDDI=true`：

```
· 三个 szlm 请求 body 里都搜不到 ddid / ddi / uuid / did
· `RequestSessionIDUpdater: shuzilm 更新Cookie ddid=ff7eb528-…`
```

**`ShuzilmSDKManager`** 是**酷安侧的封装类**（`ShuzilmSDKManager.kt`），

`$updateRetryJobStatus` 重试任务（`shuzilm network requesting，try to reload did`）。

`_rev` 以前一直直接看 `cn.shuzilm.*`，**这个封装层没看过** —— 是新的切入点。

## 七、结论与下一步

### 本轮确定下来的

```
1. 请求侧没有签名
   · HTTP 头 21 组变体全无影响（含最小头集、UA 换成 curl、加 sign/apiKey 头）
   · body 87 个字段只有 4 个被读，且都是明文比对级别
2. 服务端对 mdna 的判据 = body 的 DUv / 3mS / 2cO / 75c + 【应用身份记录】
3. DUID 只在 mdna 下发；其余端点发配置/校验数据
4. MD5(内容)+内容 封装在 didCode 里也是通用规则（第四处印证）
5. 设备侧会主动上报出口 IP 与网关（didCode.x8）
```

### 还没定位的（按价值排序）

```
① 服务端凭什么把设备 DUID 关联到请求
   两台不同设备（三星 / 手表）声明同一包名，拿到不同 DUID
   ⇒ 判据包含【设备相关】的东西，但请求里唯一设备相关的是出口 IP
   ⇒ 判据实验：换一个出口 IP 重放同一请求（手机热点 / 云端），看 n_a 是否变化
       · 变   -> 判据含出口 IP
       · 不变 -> 判据是「应用身份 + 服务端登记」，与 IP 无关

② ShuzilmSDKManager（酷安自己的封装）—— 从没看过
   Init → load → did result 三步 + 重试任务；
   `did result` 带出的 didCode 就是它的产物。

③ useDDI / DDI 模式

④ d2api / daa 的 body 仍未抓到（采样被截断，CL=4001/4218）
```

### 对原目标（c001apk 拿到可用 DUID）的意义

```
以前的判断：不替换身份 → 拿不到；替换身份 → 被签名挡住
本轮修正：请求侧压根没有签名可挡
          DUID 逐设备唯一，但请求里唯一设备相关的只有出口 IP
⇒ 卡点从「密码学签名」变成了「网络位置 + 服务端登记记录」
⇒ 而且已经实测证明：curl 最小头集从本机发出，就能拿到真机的 DUID
```
