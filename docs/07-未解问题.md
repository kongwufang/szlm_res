## 已解决 ✅

### ~~1. `sfOo` / `foO` 的生成算法~~ → 已解

```
foO  = ANDROID_ID 前 15 位，每字符在 95 个可打印 ASCII 的环上偏移 K，再 shuffle 重排
sfOo = MD5_UPPER(str(全部 16 位码位之和))[:7]   ← 是校验值，用来确定被去掉的第 16 位

⇒ ANDROID_ID 可以完整还原，且能被 sfOo 校验确认
```

**实测**：

```
D1H  K=12  →  ANDROID_ID = 288daec8ec176396   (sfOo 'FD2C5E4' 命中)
```

### ~~2. `w91` / `gEd` / `6yY` 三个哈希的输入~~ → 已解

```
w91 = /system/fonts 文件名列表的 MD5
gEd = libreference-ril.so 或 libc.so（32 位）的 MD5
6yY = Widevine deviceUniqueId（hex 原样）
```

**⇒ 难怪之前做 73080 次组合穷举零命中：输入根本不是报文里的字段，是文件系统内容。**

## 仍未解

### 1. `K` 的生成规则

```
已知：K ∈ [5, 56]，同一份报文里所有 mode 2/3/10 字段共用
已测：15 个不同的 K 值，看不出与 2cO / K5f / dLH 的直接关系
推测：可能是随机，或由某个内部序列号派生
```

**影响**：无。自动定位 `K`（穷举 + 格式校验）已能解开全部实测样本。

**下一步**：

```
拿同一批样本，统计 K 与各字段的相关性
特别关注：K 是否与 2cO 的某几位、或 dLH 的某个字节有关
```

### 2. 为什么 D1C 的 `foO` 差一个字符

```
D1H  foO → 288daec8ec17639      ← 与 D1C 应该是同一个 ANDROID_ID
D1C  foO → 288daec08ec1769      ← 位置 7 是 '0'，D1H 是 '8'
```

两份来自**同一台设备**，`ANDROID_ID` 不该不同。

**可能原因**：

```
① D1C 那次抓包的 foO 字段有 1 个字符在采集过程中损坏
② D1C 的 K 对 dLH 是 25，对 foO 可能是 26（编码层略有差异）
③ 设备在两次注册之间恢复过出厂设置（但那样 DUID 应该变）
```

**倾向 ①** —— D1C 那份是较早的采集，当时钩子还有 bug。

### 3. `2cO` 的纳秒部分

```
已知：必须是"新值"，也不能是纯整数秒
未解：纳秒部分的精确来源；服务端的时间窗具体怎么算
```

**附带观察**：不同来源的 `2cO` 小数位数不一样

```
我们的样本   1791105420.764024281   （9 位）
另一批样本   1793367275.234000000   （9 位，末 6 位是 0）
adt 报文     1789800740.2893029     （7 位）
```

**⇒ 格式不完全统一，可能随版本/端点变化。**

## 这些未解问题影响使用吗？

**不影响。**

```
取回【某台设备的 DUID】：只需要它的锚点三元组（抓一次即可）
还原【设备指纹】：用 tools/unenc.py 自动定位 K，全部字段都能解
凭空算出【新的三元组】：那才需要知道 sfOo/foO 是怎么生成的
                      —— 现在知道了：ANDROID_ID + 编码
```

**⇒ 只要能拿到设备的 ANDROID_ID，就能算出它的 `foO`。**
