## 三条未解

### 1. `sfOo` / `foO` 的生成算法

**已知**：

```
· 每次注册都【变】（同一设备两次注册的值不同）
· 格式固定：sfOo = 7 位大写 hex；foO = 15 字符混淆串
· 内部编码了设备信息 —— 服务端能从新值认出同一设备
· 不含签名（随机值不会被拒，只会被判为新设备）
· foO 的字符集是 mIS 字符集的子集 ⇒ 同一套混淆机制
```

**已排除**（零命中）：

```
· 不是任何已知字段的单值哈希
  （93 个候选 × MD5/SHA1/SHA256/SHA512 × 3 种编码）
· 不是任何两两组合的哈希
  （4278 对 × 7 种分隔符 × 4 种哈希 = 239568 次）
· 不是 mdna 报文里任何 hex 字段的前缀
```

**下一步建议**：

```
hook libdu 的 MD5 —— 偏移 0xe23c4（包装）/ 0xe1de4（实体）
寄存器约定（已实测确认）：
  x0 = 输出缓冲（跨调用恒定）
  x1 = ★ 输入数据（每次变化，位于栈区）
  返回值 r = 字符串指针（不是 x0 缓冲）

⇒ 读 x1 就能看到 libdu 到底把什么喂进了哈希
```

### 2. `w91` / `gEd` / `6yY` 三个设备指纹哈希的输入

**已知**：

```
· 跨注册【恒定】 + 跨设备【不同】 ⇒ 是设备指纹
· 分别是 MD5 / MD5 / SHA256
· 但【不参与设备识别】—— 整类随机化后服务器照样返回真 DUID
```

**已排除**：

```
把 29 个已知设备属性做组合穷举：
  · 单值 × 4 种编码 × 3 种哈希
  · 两值 / 三值组合 × 9 种分隔符 × 两种顺序 × 3 种哈希
  共 73080 次 —— 零命中

⇒ 输入不是这些字段的简单拼接
```

**推测**：输入是 libdu 采集的**更底层设备属性**，可能包括：

```
boot_uuid / boot_times
包名 + 签名后缀
签名证书 DER
boot classpath 清单
系统字体清单
固件驱动标识
已装应用列表
```

**下一步**：同问题 1 —— hook MD5 读输入。

---

### 3. `2cO` 的匹配规则

**已知**：

```
· 是"秒.纳秒"形式的时钟读数
· 必须与某条已存记录【精确一致】才能命中
· 换一个没记录过的新值 → 全 0
```

**未解**：

```
· 纳秒部分必须是新值吗？还是只要匹配某条记录就行？
· 服务端是否会在新注册时"顺手"把新三元组也记进去？
· ±24h 的时间窗具体怎么算的？
```

## 附带：两个不影响使用的小问题

### `p` 后缀的来源

```
p = MD5(packageName + "." + 16位后缀).upper()
```

那 16 位后缀（`37be8a1ee106979a`）由 libdu 生成，派生规则未解。

**已排除**：不依赖 android_id / serialno / 机型 / 品牌 / 厂商 / MAC。

**影响**：无。**服务端不校验 `p`**，自研实现时当常量即可。

`yumao.puata.info/anti_logs` 与 `ccs.umeng.com/ra` 的 body
前 10 字节固定为 `2aeb393b33373531693d`，未进一步分析。

**影响**：无。不是主流程。

## 这些未解问题影响使用吗？

**不影响。**

```
取回【某台设备的 DUID】，只需要它的锚点三元组：
   抓一次它注册时的 mdna 即可
   （或者调用官方 SDK）

想做的是【凭空算出】三元组，那才需要解出算法
```

`tools/getduid.py` 已经能用固定三元组取回 DUID，
也能用随机三元组拿新 DUID —— 这两个场景都不需要解出算法。

## 如果要继续攻关

**优先级 1 —— hook libdu 的 MD5**

这是唯一还没试过、且直指核心的手段。

```
目标函数：libdu.so 偏移 0xe23c4 与 0xe1de4
做法：    Interceptor.attach，在 onLeave 读返回值 r（字符串指针），
          onEnter 读 x1（输入数据）
已确认：  x0 是输出缓冲（跨调用恒定），不能当输入读；
          必须读【返回值】而不是 x0，否则拿到的是缓冲里的垃圾
```

**优先级 2 —— 找混淆表**

16 个混淆串（含 `foO`）看起来是同一套机制生成的。
若能还原那套编码，可以一次性解开全部。

线索：运行时抓到过 token → 字符串表，索引用的字母表是**标准 base64**
（`ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/`）。

**优先级 3 —— 交叉验证**

用更多设备、更多次注册扩充样本，例如：

```
· 同一设备的第 3、第 4 次注册
· 同一设备但在不同网络环境
· 伪造设备属性后注册（看三元组是否随之变化）
   ⇒ 若三元组跟着变，说明它确实编码了那些属性
```
