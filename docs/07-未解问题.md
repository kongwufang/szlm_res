## 已解决 ✅

### ~~1. `sfOo` / `foO` 的生成算法~~ → 已解

```
foO  = ANDROID_ID 前 15 位，按 (P%100%57+1) 在 mod-95 环上偏移，再按 (P//100%4) 重排
sfOo = MD5_UPPER(str(全部 16 位码位之和 + P%100//10))[:7]   ← 校验值，用来确定第 16 位
P    = 2cO 最后 3 个字符去掉 '.' 后 atoi
```

**⇒ ANDROID_ID 可以完整还原，且能被 `sfOo` 校验确认。**

### ~~2. `w91` / `gEd` / `6yY` 三个哈希的输入~~ → 已解

```
w91 = /system/fonts 文件名列表的 MD5
gEd = libreference-ril.so 或 libc.so（32 位）的 MD5
6yY = Widevine deviceUniqueId（hex 原样）
```

**⇒ 难怪之前做 73080 次组合穷举零命中：输入根本不是报文里的字段，是文件系统内容。**

### ~~3. `K` 的生成规则~~ → 已解（**由 People-11 完成**）

```
K       = P % 100 % 57 + 1
variant = P // 100 % 4        ← 四种重排
P       = 2cO 末 3 位 atoi
```

**⇒ 参数就藏在同一份报文的时间字段里，不需要穷举。**

## 仍未解

### 1. 非标准设备上 `P1J` 与 `ANDROID_ID` 对不上 ⚠️

按公开分析，`P1J` = `SHA1_UPPER(ANDROID_ID)` 取 `[1:7]:[13:19]:[7:13]`。

**在标准设备上验证成立：**

```
AID = 7be317f3baa70ddb
SHA1 = 2B191B533291E36B16A46E4A22C277C3ABC0C0BE
[1:7]:[13:19]:[7:13] = B191B5:36B16A:33291E   ✓ 与实际 P1J 一致
```

**在这台手表上对不上：**

```
实测 P1J = 13A365:CCAF40:AD4AA9
⇒ 要求 SHA1_UPPER(AID) 形如 ?13A365AD4AA9CCAF40…
⇒ 解出的两个候选 AID 都不满足
```

**而且两份报文算出的 AID 不同：**

```
D1C (P=281)  →  288daec08ec17693
D1H (P=68)   →  288daec8ec176390
```

**同一台设备不该有两个 AID。**

**可能原因：**

```
① D1 是廉价安卓手表（TK Watch，Android 8.1），ANDROID_ID 可能不是标准 16 位 hex
   ⇒ "16 个 hex 候选补末位"这个套路对它不适用
② 两段采集之间设备恢复过出厂设置，ANDROID_ID 被重新生成
   （DUID 不变是正常的 —— 那由三元组决定，不由 AID 决定）
③ 某一份采集时钩子还有 bug，字段损坏
```

**下一步**：换一台标准手机抓一次验证。

### 2. `2cO` 纳秒部分的精确来源

```
已知：是 clock_gettime(CLOCK_REALTIME) 的纳秒，不补零
     P 由末 3 位决定，所以纳秒末三位实际是"编码密钥"
未解：服务端是否利用这个值做时间窗校验、怎么算
```

**附带观察**：不同来源的 `2cO` 小数位数不一样

```
我们的样本   1791105420.764024281   （9 位）
另一批样本   1793367275.234000000   （9 位，末 6 位是 0 —— harness 时钟只有毫秒精度）
adt 报文     1789800740.2893029     （7 位）
```

## 附带：两个不影响使用的小问题

### `p` 后缀的来源

```
p = MD5(packageName + "." + 16位后缀).upper()
```

## 这些未解问题影响使用吗？

**基本不影响。**

```
取回【某台设备的 DUID】：               只要它的锚点三元组（抓一次即可）
还原【标准设备上的字段】：              P 从 2cO 直接算，全部可解
还原【非标准设备（如廉价手表）上的 AID】：需要保留"自动搜索"的回退
凭空算出【新的三元组】：                需要设备的 ANDROID_ID —— 现在能把 AID 编成 foO 了
```
